# Локальная лаборатория ФОЛИО `Paint_Rus`

`folio-rus-lab` — отдельный Java-модуль для управляемых экспериментов с заброшенной копией базы ФОЛИО. Он не подключается к production-модулю проекта, принимает запросы только через `127.0.0.1:18081` и не позволяет клиенту выбирать сервер или имя базы.

База назначения в приложении зафиксирована как `Paint_Rus`. Проект рассчитан на Microsoft SQL Server 2000 SP3 или новее (build не ниже `8.00.760`), compatibility level 80, `SQL_Ukrainian_CP1251_CI_AS` и jTDS 1.3.1.

## Граница безопасности

Это лаборатория для заброшенной копии `Paint_Rus`, доступной только через защищённый VPN. Она может работать на общем SQL Server instance при условии, что используемый SQL-login фактически имеет доступ только к `Paint_Rus`.

- При старте приложение проверяет точное имя `Paint_Rus`, SQL Server 2000 SP3+, compatibility level, collation и кодовую страницу.
- Членство SQL-login в любой фиксированной серверной роли — жёсткая остановка запуска.
- Server-wide и database-level cross-database ownership chaining должны быть выключены; если эти настройки нельзя прочитать, запуск также останавливается.
- API отбрасывает команды выхода в другую базу/на сервер, но этот фильтр является **best effort**: произвольный T-SQL невозможно полностью изолировать внутри общей инстанции только разбором текста.
- Guard останавливает запуск, если данный SQL-login имеет доступ хотя бы к одной другой рабочей пользовательской базе. Доступ к штатным демонстрационным базам SQL Server `Northwind` и `pubs` явно разрешён и показывается отдельным предупреждением; `Paint_Ua` в исключение не входит. Само наличие других баз или linked/remote server фиксируется диагностически, но не блокирует старт.
- Нужен SQL-login без фиксированных серверных ролей и без mappings в другие пользовательские базы. Уникальный пароль не заменяет это ограничение доступа.
- VPN и loopback-only API приняты как внешняя граница этой лаборатории. Отдельный disposable instance/VM остаётся более сильным вариантом на будущее, но не требуется для текущего запуска.
- Перед первым сохраняющим экспериментом проверьте backup/restore и отсутствие других сессий. Не считайте базу безопасной только из-за её имени.

`ROLLBACK` уменьшает риск, но не делает неизвестную процедуру обратимой. Внешняя транзакция получает случайный transaction-scoped sentinel: если процедура завершила исходную транзакцию и создала новую с тем же `@@TRANCOUNT`, сервис не выдаст ложное `ROLLED_BACK`, а остановит сценарий как `TX_BOUNDARY_BROKEN`. Уже сохранённые внутренней процедурой изменения при этом могут остаться. Все пользовательские вызовы namespaces `sp_`, `xp_` и `dt_` запрещены; локальные procedures ФОЛИО разрешаются, но их тело всё равно нужно предварительно разобрать.

## Подготовка секретов

Все реквизиты остаются только в локальном игнорируемом файле `.env.folio-rus-lab`. Не добавляйте его в Git, Skill, SQL-файлы, сообщения чата или отчёты.

Для SQL Server-конструкций, которым требуется несколько JDBC batch в одном
соединении (например, временная `CREATE PROCEDURE` и её последующий rollback-тест),
используйте отдельную строку:

```sql
-- FOLIO_LAB_NEXT_BATCH
```

Лаборатория допускает не более 10 непустых batch, проверяет весь запрос общей
SQL-policy и выполняет их в одной управляемой транзакции. Обычный клиентский
разделитель `GO` остаётся запрещён.

```sh
cd /Users/admin/Documents/Toleran/Proect_Lavka/kreul_com_ua/folio-rus-lab
cp env.example .env.folio-rus-lab
chmod 600 .env.folio-rus-lab
openssl rand -hex 32
```

Откройте `.env.folio-rus-lab` локально и замените все `REPLACE_...`: адрес SQL Server в VPN, порт, SQL-login, пароль и сгенерированный `FOLIO_RUS_API_TOKEN`. Имя базы настраивать нельзя — оно зафиксировано в коде.

Токен должен содержать не менее 32 символов. Docker хранит переданные переменные в метаданных контейнера, поэтому доступ к Docker на ноутбуке также считается привилегированным.

### Где изменить пароль SQL-login

В SQL Server Enterprise Manager откройте узел самого сервера, затем `Security` → `Logins` → нужный login → `Properties`. Задайте новый пароль и подтверждение. Пароль нельзя изменить в `Databases` → `Paint_Rus` → `Users`: там находится пользователь базы, сопоставленный серверному Login, а не отдельная учётная запись с собственным паролем.

На вкладке `Database Access` оставьте разрешение только для `Paint_Rus`, снимите mappings с остальных пользовательских баз и не добавляйте fixed server roles. Если этот Login использует старая программа или другая база, смена пароля нарушит их подключение. После смены обновите только локальный `.env.folio-rus-lab` и не публикуйте его.

## Запуск через Docker

Сначала подключите VPN, затем из каталога `folio-rus-lab` выполните:

```sh
FOLIO_RUS_ENV_FILE=.env.folio-rus-lab docker compose up --build
```

Без `FOLIO_RUS_ENV_FILE` используется безопасный `env.example` с нерабочими placeholders — настоящее подключение случайно не запустится. Порт опубликован только на loopback ноутбука:

```text
127.0.0.1:18081 -> container:8080
```

Остановить лабораторию:

```sh
docker compose down
```

Контейнер работает от непривилегированного пользователя, с read-only файловой системой, временным `/tmp`, удалёнными Linux capabilities и `no-new-privileges`.

## Swagger — ручное управление

После успешного старта откройте в браузере:

```text
http://127.0.0.1:18081/swagger-ui.html
```

Swagger UI и OpenAPI-описание доступны только через локальный порт. Для вызова защищённых методов нажмите `Authorize` и вставьте значение `FOLIO_RUS_API_TOKEN` без слова `Bearer`. Токен не сохраняется между перезагрузками страницы. Сами `/api/v1/...` методы остаются закрыты bearer-аутентификацией. Машиночитаемая схема доступна по `http://127.0.0.1:18081/v3/api-docs`.

## Диагностические логи

Наблюдать за процессом можно в отдельном окне:

```sh
docker compose logs -f api
```

Для каждого запуска выводятся этапы `LAB_SQL_START`, `LAB_DB_CONNECTED`, `LAB_PREFLIGHT_OK`, `LAB_TRANSACTION_READY`, `LAB_BATCH_DRAINED`, `LAB_RESULT`, `LAB_SENTINEL_CHECK` и финальное состояние. `allowedDemoDatabases` отдельно показывает доступные `Northwind`/`pubs`; `otherAccessibleDatabases` считает только запрещённые рабочие базы. Связать строки одного запуска можно по `runId`; конкретный запрос — по `sqlSha256`.

Логи намеренно не содержат SQL-текст, значения ячеек, пароль базы или API-token. Видны тип результата, количество строк/колонок, update counts, объём и транзакционное состояние — этого достаточно для диагностики процесса без распространения содержимого базы.

## Если Docker не видит VPN

Docker Desktop иногда не наследует маршрут VPN. Сначала проверьте доступность SQL Server с самого macOS. Затем выберите один из вариантов:

1. Разрешите Docker Desktop использовать VPN-маршрут в настройках VPN/firewall.
2. Создайте на macOS локальный TCP-туннель до SQL Server и укажите контейнеру `FOLIO_RUS_DB_HOST=host.docker.internal` и порт туннеля.
3. Запустите модуль нативно через Java 17/Maven из IDE, передав те же переменные окружения. Пароль и токен задавайте через защищённую конфигурацию запуска или скрытый prompt, не аргументами командной строки.

Нативный API также должен слушать только loopback. Docker и нативный процесс одновременно не запускайте на одном порту.

## Локальный CLI

Утилита `bin/folio-rus-lab` использует только Python standard library. Она запрещает удалённый API URL и никогда не принимает SQL текстом в аргументе командной строки.

Проверка HTTP-сервиса не требует токена:

```sh
bin/folio-rus-lab health
```

Для защищённых команд CLI автоматически читает только API-token из защищённого `.env.folio-rus-lab`; пароль базы он не передаёт в командную строку и не выводит. Файл должен иметь права `600`.

При желании token можно передать через переменную окружения. Чтобы значение не попало в history, вставьте его в скрытый prompt:

```sh
IFS= read -r -s FOLIO_RUS_API_TOKEN
export FOLIO_RUS_API_TOKEN
```

Проверка базы и ограничений login:

```sh
bin/folio-rus-lab preflight
```

### Полный безопасный preview учётных цен

После установки в `Paint_Rus` отдельных процедур
`dbo.LAVKA_I_UCHET_1_TOVAR_SAFE` и `dbo.LAVKA_I_UCHET_TOVAR_SAFE` лаборатория
может проверить весь склад по одному SKU:

```sh
bin/folio-rus-lab safe-preview --warehouse-id 23
bin/folio-rus-lab safe-preview-status
```

`POST /api/v1/accounting-prices/safe-preview` только ставит фоновую задачу в
очередь. Текущее состояние возвращает
`GET /api/v1/accounting-prices/safe-preview/status`.

Для каждого артикула Java открывает отдельную транзакцию, вызывает безопасную
procedure и обязательно выполняет `ROLLBACK`. `return_code=20` не останавливает
остальные товары: точные SKU, `RECNO`, дата, формула, числитель, знаменатель и
количества добавляются в `problems[]`. Отрицательный хронологический остаток
также возвращается как отдельная проблема. Любая неизвестная SQL-ошибка или
нарушение границы транзакции останавливает задачу со статусом `FAILED`.

Первая версия намеренно поддерживает только склад с `N_2=1000` и
`N_4 IS NULL`. Это лабораторный rollback-preview, а не разрешение выполнять
перерасчёт или переносить procedures в `Paint_Ua`.

Выполнение SQL из UTF-8 файла; по умолчанию используется режим `ROLLBACK`:

```sh
bin/folio-rus-lab execute --file ./query.sql
```

Безопасный захват return status локальной процедуры поддерживается в форме
`EXECUTE @rc = dbo.ProcedureName ...`. Вызов процедуры через переменную
(`EXECUTE @procedureName` либо `EXECUTE @rc = @procedureName`) остаётся
запрещён как dynamic SQL.

Можно подать SQL через stdin:

```sh
printf 'SELECT DB_NAME() AS database_name\n' | bin/folio-rus-lab execute
```

Ограничения одного запуска задаются явно:

```sh
bin/folio-rus-lab execute \
  --file ./query.sql \
  --timeout-seconds 30 \
  --max-rows 5000 \
  --max-bytes 5242880
```

Сохраняющие режимы требуют одновременно указать режим и подтверждающий флаг:

```sh
bin/folio-rus-lab execute \
  --file ./experiment.sql \
  --mode COMMIT \
  --allow-persistent-changes
```

`SELF_MANAGED` предназначен только для разобранных сценариев, которым действительно нужны собственные границы транзакции. Не используйте его для исследования неизвестной procedure.

CLI возвращает JSON и коды завершения:

- `0` — HTTP-операция успешна;
- `1` — API вернул ошибку;
- `2` — локальная ошибка клиента, настроек или связи до запуска SQL, в том числе недоступный `preflight`;
- `3` — после отправки SQL результат не доказан: связь потеряна, ответ повреждён либо сервер вернул состояние с возможным сохранением изменений:
  - `ROLLBACK_EXECUTION_OUTCOME_UNKNOWN` — результат запроса и откат не подтверждены;
  - `PERSISTENT_OUTCOME_UNKNOWN` — для `COMMIT`/`SELF_MANAGED` изменения могли сохраниться.

При коде `3` не повторяйте тот же SQL. Сначала восстановите связь и отдельным новым `ROLLBACK`-запросом выполните read-only postcondition check по бизнес-ключу, количеству строк и ожидаемому состоянию. Только после этого решайте, нужен ли другой корректирующий сценарий.

Если SQL error одновременно не позволяет доказать continuity sentinel, ответ
сохраняет строгий `state=TX_BOUNDARY_BROKEN`, но поле `error` дополнительно
содержит исходные `sqlState`, `vendorCode` и очищенное сообщение SQL Server.
Это диагностическая информация, а не доказательство rollback: независимый
postcondition check всё равно обязателен.

Другой локальный URL можно задать через `FOLIO_RUS_API_URL` или `--base-url`, но hostname всё равно должен быть `127.0.0.1`, `localhost` или `::1`.

## Рекомендуемый экспериментальный цикл

1. VPN, backup/restore gate и `preflight`.
2. Read-only baseline через `ROLLBACK`.
3. Одно контролируемое действие штатным UI ФОЛИО или один заранее разобранный SQL-сценарий.
4. Повторный снимок тех же ключей и сравнение before/after.
5. Проверка результата штатным UI/отчётом.
6. В Skill переносится только обезличенный воспроизводимый инвариант; сырые результаты остаются локально.

Не публикуйте логи или ответы API без проверки: данные ФОЛИО могут содержать имена, телефоны, адреса, сетевые пути и другие чувствительные значения.
