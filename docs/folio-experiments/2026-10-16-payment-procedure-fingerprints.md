## Результат сравнения

Снимок для сравнения — локальный приватный CP1251 RPT от 2026-08-11 (Paint_Ua).

Совпали точные нормализованные SHA-256 всех четырёх объектов и каждого
syscomments-фрагмента. Не использовалось одно лишь compact/semantic совпадение.

В RPT данные разбиты на 200-символьные части с 319-символьным префиксом строки.
При восстановлении исходника нельзя добавлять CRLF между каждой частью.
Три части длиной 198 символов потеряли завершающий source CRLF при экспорте:
`INSERT_PLAT` fragment 1 / part 7; `i_ins_plat` fragment 1 / part 7 и fragment 3 /
part 3. Восстановление именно CRLF (не двух пробелов) дало точное совпадение
хешей фрагментов и всей процедуры. Необходимость восстановления проверялась
хешем, не принималась предположением о семантической эквивалентности.

## Synthetic payment с внешним rollback

Повторный preflight `2026-10-16T14:30:58.613479168Z` подтвердил те же условия
изоляции. Владелец отдельно подтвердил, что Paint_Rus свободна от пользователей
и других пишущих интеграций. Восстановление backup самостоятельно не проверялось.
Свежая схема/defaults/FK/identity и отсутствие триггеров для затронутых таблиц
проверены до записи; широкие права не выдавались.

Воспроизводимые входы (только лаборатория Paint_Rus, не production):

- [baseline / независимый postcheck](2026-10-16-payment-baseline.sql);
- [synthetic fixture и native INSERT_PLAT](2026-10-16-payment-rollback.sql).

Перед любым повтором нужны новый preflight, отсутствие конкурентной работы,
сверка четырёх хешей и нулевой baseline. Execute — только default `ROLLBACK`.
Не применять `COMMIT`, не переносить этот SQL на Paint_Ua. Lab управляет
`XACT_ABORT` и внешней транзакцией; SQL не меняет transaction session settings.
Rollback не возвращает использованные IDENTITY, поэтому возможны разрывы ID.

Опыт: одна synthetic строка на 4 UAH, новый клиент/товар/склад, платёжный склад
5 при отличающемся складе счёта. Реальные документы и остатки не изменялись.
`TMP_MOVE.KOLTREB_PR` в этом native пути передаёт `SCL_MOVE.RECNO`, а не количество.
Номер платежа выделила штатная процедура; коррекция существующего платежа отключена.

Run `7954789f-3002-4d71-89ea-03819b75124f`, состояние `ROLLED_BACK`:

- native return `0`; шапка `SCL_PLAT`: сумма 4, склад 5, bank income,
  учитываемая, `UCHET_MOVE=1`;
- ровно одна `SCL_PMOV`, количество 1 / сумма 4, **склад исходной строки счёта**;
- `SCL_MOVE`: `KOLC_OPL=1`, `SUM_OPL=4`, `OPLATA_SCH=1`;
- `SCL_NAKL`: `CHAST_OPLT=1`, `OPLATA_SCH=1`, дата оплаты заполнена;
- физический остаток 10 и свободное количество 9 не изменились;
- свой TMP-ключ очищен процедурой; `SCL_ADDP` не создана (это согласуется с
  разобранным исходником, но не доказывает достаточность реквизитов любого платежа);
- native `@@TRANCOUNT` сохранился 1 → 1; lab итог 0 → 0.

Независимое новое соединение, run `5cfead75-5f2f-4c16-9333-e63bed50233c`:
все 10 synthetic entity counts равны нулю. Постоянного пробного прихода нет.
Повторный запуск не выполнялся ради идемпотентности: native procedure её не даёт.

## Production read-only сверка полей и stopping condition

Источник: Paint_Ua, 2026-10-16; банковский образец владельца (склад 5, документ
за 13.10.2026) прочитан без изменения. Подтверждено точное соответствие:

| Поле UI | Колонка / значение образца |
| --- | --- |
| Вид операции | `CODCEL_POR = МАЛАФОП` |
| Тип операции | `VID_DOC = РЕАЛИЗАЦИЯ` |
| Приход по банку | `TYPE_POR=1`, `NOT_NAL=1` |
| Учёт / учитывать сумму в долгах | `STND_UCHET=1`, `UCHET_MOVE=1` |

`VALUTROUBL=1`, `IS_NALPROD=138` также наблюдались в образце, но смысл последнего
флага не доказан; не превращать его в default без отдельного разбора. Synthetic
опыт использовал `CODCEL_POR=TST`, `IS_NALPROD=NULL`, а не полный боевой шаблон.

Для выбранного оплаченного Woo-заказа серверная очередь подтверждает успешную
live-оплату без зарегистрированного возврата. Но сохранённый технический ID
счёта отсутствует в активной `SCL_NAKL`, его строк нет в `SCL_MOVE`; запись
`LAVKA_FOLIO_ACCOUNT_REQUESTS` осталась. В `SCL_ARCN` найден соответствующий
счёт по номеру, дате, сумме, времени создания и WFP/order-маркеру, **с другим ID**.
Нельзя автоматически подменять технический ID архивным или повторять create.
Production payment не создавался. Требуется восстановленный штатно активный
документ либо другая явно выбранная оплата; после выбора заново читать состояние.

## Что это ещё не доказывает

Успех одного rollback-примера не означает готовый WayForPay → ФОЛИО API.
Остаются golden-master UI/отчёта долга, полный production template и свежие
production procedure fingerprints/schema, committed idempotency с unknown-outcome
reconciliation, конкурентность, нумерация при конкуренции, частичные/split/архивные
и валютные сценарии. Нужны Java write contract и PHP consumer с default-off.
Нельзя повторять callback, чек или создание счёта ради восстановления оплаты.
