# Диагностика складов распродажи и режима `SCLAD_R.N_2=1100`

Дата проверки: 2026-08-23.

## Граница эксперимента

- Paint_Ua исследовалась только `SELECT`-запросами.
- `SCLAD_R.N_2`, документы, остатки и учётные цены Paint_Ua не изменялись.
- Golden-master выполнялся только на изолированной Paint_Rus во внешней
  транзакции лаборатории с обязательным rollback.

## Исправление названия поля

У `NSF_ORG` нет колонки `N_2`. `NSF_ORG` хранит счётчики документов, в том
числе `N_3`. Метод учётной цены склада хранится в `SCLAD_R.N_2`.

## Фактические настройки Paint_Ua

| Склад | Название | `SCLAD_R.N_2` | `N_4` | Расшифровка |
|---:|---|---:|---|---|
| 1 | Киев | 1000 | `NULL` | `AVERAGE`, period 0, `includeTax=false` |
| 5 | Одесса | 1000 | `NULL` | `AVERAGE`, period 0, `includeTax=false` |
| 7 | Киев ОПТ | 1000 | `NULL` | `AVERAGE`, period 0, `includeTax=false` |
| 15 | Одесса Хранение | 1000 | `NULL` | `AVERAGE`, period 0, `includeTax=false` |
| 19 | Киев распродажа | 1100 | `NULL` | `AVERAGE`, period 0, `includeTax=true` |
| 20 | Одесса распродажа | 1100 | `NULL` | `AVERAGE`, period 0, `includeTax=true` |

Формат ФОЛІО подтверждён определением процедуры и Java-декодером:

```text
N_2 = 1000 + includeTax*100 + periodMode*10 + calculationMode
```

Поэтому `1100` является поддерживаемой веткой средней цены, а не LIFO, FIFO,
фиксированной или партионной ценой.

## Решение по маршрутам

### Product snapshot

Склады 19 и 20 должны участвовать. Snapshot не пересчитывает налог и не
вызывает `I_UCHET_TOVAR`: он читает уже сохранённые в ФОЛІО учётные суммы и
строит read-only fingerprint/экономические метрики. Java допускает точные коды
`1000` и `1100`; прочие коды возвращают структурированную диагностику:

- `errorCode=PRODUCT_SNAPSHOT_ACCOUNTING_MODE_UNSUPPORTED`;
- фактический `accountingRawCode`;
- `accountingMode`;
- рекомендацию исключить склад до отдельного golden-master и не менять `N_2`
  автоматически.

### Native range/full

Алгоритм `1100` совместим, и Java передаёт `includeTax=true` в параметр
`@uch_nal`. Но действующие safe-процедуры должны быть обновлены: ранняя версия
защитного guard принимала только `@uch_nal=0` и возвращала код 32. До ручной
установки обновлённой `LAVKA_I_UCHET_*_SAFE` в конкретную базу native route
для `1100` считается неразвёрнутым и не должен выполнять apply.

## Paint_Rus golden-master

В Paint_Rus найден реальный незгруппированный склад с `N_2=1100`. На чистом
SKU с одним учитываемым приходом внутри внешней транзакции временно искажены
`SCL_MOVE.SUM_UCHET` и итоговые учётные поля `SCL_ARTC`. Затем штатная
`I_UCHET_TOVAR` вызвана с `uchet_rsc=0`, `period_rsc=0`, `uch_nal=1`.

Подтверждено до rollback:

- `return_code=0`, `otr_date=NULL`;
- учётная сумма прихода восстановлена из исходной суммы документа;
- сумма карточки и средняя учётная цена восстановлены;
- физический остаток не изменён;
- количество строк `TMP_MOVE` до/после одинаково;
- окружающая транзакция сохранена.

Лаборатория вернула `ROLLED_BACK`. Независимое новое соединение подтвердило
исходные значения карточки/движения и неизменный baseline `TMP_MOVE`.

Read-only Java source snapshot того же склада завершён отдельно: 35 398 SKU,
6 316 учитываемых движений и 61 правило цены, без orphan-строк.

Отдельный rollback-probe уже установленной в Paint_Rus ранней
`LAVKA_I_UCHET_TOVAR_SAFE` с `uch_nal=1` вернул ожидаемый fail-closed контракт:
`return_code=32`, `problem_code=UNSUPPORTED_SCOPE_OR_MODE`, транзакция
сохранена и откатана. Это подтверждает, что одной новой версии Java
недостаточно: существующий safe-объект действительно требует upgrade.

## Оставшийся release gate

1. Установить обновлённую safe-процедуру только в Paint_Rus.
2. Выполнить per-SKU safe rollback-preview с `@uch_nal=1` и проверить
   структурированные zero-denominator/negative-stock warnings.
3. Только после этого подготовить DBA upgrade для Paint_Ua и выполнить первый
   rollback-preview склада 19 или 20 в окно без работы менеджеров.
4. Apply Paint_Ua не запускать в рамках этой диагностики.
