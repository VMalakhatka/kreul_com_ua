# Golden-master: `I_UCHET_TOVAR` и `Divide by zero`

Дата проверки: 2026-08-17.

Стенд: изолированная база `Paint_Rus`, Microsoft SQL Server `8.00.760`,
compatibility level 80, `SQL_Ukrainian_CP1251_CI_AS`, CP1251.

Все DML и вызовы процедуры выполнялись через `folio-rus-lab` во внешней
транзакции. После каждого проблемного запуска выполнялся независимый read-only
postcondition check новым соединением.

## Подтверждённый сценарий ошибки

Для существующего обезличенного товара небольшого тестового склада внутри
rollback-транзакции:

1. все его учитываемые движения, кроме одного, временно исключены из расчёта;
2. оставшееся движение временно превращено в обычный учитываемый приход с
   количеством `0`;
3. начальное количество и начальная учётная цена временно установлены в `0`;
4. вызвана `dbo.I_UCHET_TOVAR` в режиме средней цены `N_2=1000`.

Результат: SQL Server вернул `SQLState=22012`, `vendorCode=8134`, сообщение
`Divide by zero error encountered.` Это доказывает одну реальную ветку ошибки:
нулевое приходное движение при нулевом знаменателе средней цены.

Эксперимент не доказывает, что production-инцидент Paint_Ua вызван именно этой
веткой. Пустая карточка без движений не является ошибкой.

## Подтверждённый quarantine

В том же синтетическом сценарии создан временный тип товара с
`CHECK_SAVE=0, SHOW_OSTATOK=0`, а проблемной карточке временно назначен этот
тип. После этого `I_UCHET_TOVAR`:

- не выполнила расчёт проблемного SKU;
- продолжила обход следующих карточек;
- завершила диапазон без ошибки 8134.

Независимый postcondition check подтвердил:

- временная строка `TIP_TOVR` отсутствует;
- ни одна карточка не сохранила временный тип;
- исходные поля движения восстановлены;
- исходные поля карточки восстановлены;
- новое соединение имеет чистый `@@TRANCOUNT`.

## Транзакционный вывод

При самой ошибке 8134 лаборатория не смогла доказать continuity transaction
sentinel и корректно вернула `TX_BOUNDARY_BROKEN`. Последующий независимый
снимок подтвердил, что фактических изменений не осталось, но это нельзя было
считать доказанным из первого ответа.

Следствие для Java:

- после исключения процедуры не выполнять компенсирующие `UPDATE/DELETE` в
  `finally` на том же соединении;
- сохранять исходный SQLException 8134;
- передавать управление transaction manager для rollback;
- после неопределённого исхода проверять postconditions новым соединением;
- явное восстановление временного quarantine выполнять только после успешного
  возврата процедуры.

## Дополнительная проверка полного прохода

Склад с режимом `N_2=1000`, `N_4 IS NULL` был полностью пройден несколькими
rollback-порциями. Ошибка 8134 на фактических данных стенда не обнаружена.
Процедура несколько раз вернула `otr_date` для отрицательной хронологии и
корректные `new_art`; последняя порция вернула `new_art=NULL`. Все порции
завершились подтверждённым `ROLLED_BACK`.

## Paint_Ua: зависимость от диапазона

Production rollback-preview склада 5 от 2026-08-17 дошёл до 71%, не
зафиксировал ни одной порции (`committedChunks=0`) и получил 8134. Первая
версия изоляции свела кандидата к одной карточке, но exact-проба этой карточки
оказалась чистой. Это опровергло предположение, что любой `Divide by zero`
обязательно принадлежит одному независимому SKU. Возможна зависимость от
последовательности соседних карточек либо переносимого внутреннего состояния
legacy-процедуры.

Безопасное правило обновлено:

1. сначала весь оставшийся диапазон обязан повторно воспроизвести 8134;
2. ищется кратчайший подтверждённый префикс с неизменной левой границей;
3. затем левая граница сдвигается только пока оставшийся непрерывный диапазон
   сам воспроизводит 8134;
4. quarantine получает один SKU или весь минимальный подтверждённый диапазон;
5. неподтверждённый предполагаемый SKU никогда не пропускается автоматически.

Unit golden-master покрывает как независимый SKU, так и связанную пару: в обоих
случаях исходная порция и все isolation-пробы откатываются, после quarantine
preview продолжает остальные товары и завершается с warnings.
