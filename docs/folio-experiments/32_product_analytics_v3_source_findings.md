# Product analytics v3 source findings

Проверено: 2026-08-31. Исследование выполнялось read-only сначала на
`Paint_Rus`, затем на `Paint_Ua`. Настройки, документы, движения, остатки и
учётные цены ФОЛІО не изменялись.

Использованные запросы:

- `30_product_analytics_v3_source_probe.sql` — схема и кандидаты источников;
- `31_product_analytics_v3_fill_probe.sql` — заполненность и контрольные
  справочники.

## Подтверждено и включено в schema v3

| Поле API | Источник ФОЛІО | Правило |
|---|---|---|
| group levels 1–6 | `SCL_ARTC.NGROUP_TVR`, `NGROUP_TV2..NGROUP_TV6` | trim; код одновременно является отображаемым именем до появления отдельного словаря |
| department | `SCL_ARTC.DEPARTAM` | строковый стабильный код; имя равно коду |
| product type | `SCL_ARTC.TIP_TOVR`, left join `TIP_TOVR.SIGNIFIC` | имя из `TIP_TOVR.TIP_TOVAR`, fallback на код |
| unit | `SCL_ARTC.EDIN_IZMER` | код и имя равны исходному значению |
| package quantity | `SCL_ARTC.EDN_V_UPAK` | nullable decimal |
| minimum order quantity | `SCL_ARTC.MIN_PARTIA` | nullable; в проверенной Paint_Ua фактически не заполнено ненулевыми значениями |
| min/max stock | `SCL_ARTC.MIN_TVRZAP`, `MAX_TVRZAP` | decimal на уровне SKU × склад |
| current supplier | `SCL_ARTC.DOP2_ARTIC` | не смешивать с контрагентом документа |

`TIP_TOVR` в проверенной Paint_Ua не содержит строк справочника, хотя коды в
карточках встречаются. Поэтому fallback на исходный код обязателен.

Новые измерения участвуют в отдельном `analytics_digest`. Они не меняют
`source_digest` и не переводят товар в `DIRTY` для перерасчёта учётной цены.

## Подтверждённая бизнес-семантика min/max stock

- `MIN_TVRZAP=0` запрещает заказ на конкретный склад.
- `MIN_TVRZAP=1` разрешает заказ только по прогнозной потребности.
- `MIN_TVRZAP>1` задаёт дополнительный запас сверх прогноза.
- Для склада 7 «Киев ОПТ» `MIN_TVRZAP=0` является запретом заказа SKU для всей
  сети.
- `MAX_TVRZAP>=9999` означает отсутствие верхнего ограничения.
- `MAX_TVRZAP<9999` является верхним пределом будущего запаса после заказа.

Интерпретация выполняется в Java API и не меняет исходные значения ФОЛІО.

## Исследовано, но не включено

- `brand_code/brand_name`: канонический источник производителя не подтверждён;
  поля сохраняются `null`, эвристика по названию запрещена.
- Дополнительные штрихкоды: таблица `SCL_CODE` исследована, но её правила
  множественности и выбора основного кода ещё не подтверждены.
- `SCL_NAKL.CONTR_POR`, `OSNOVANIE`, `CONTRLDATE`, `L_CP1_PLAT`,
  `L_CP2_PLAT` заполнены частично, но бизнес-смысл не подтверждён как стабильный
  аналитический фильтр.
- Склад-источник/получатель transfer, продавец, SCM lead time, открытая поставка,
  и return COGS требуют отдельного исследования.

## Подтверждено для schema v4

- основной GTIN карточки: `SCL_ARTC.DOP3_ARTIC`; это тот же источник, который
  текущая Woo-синхронизация передаёт как `global_unique_id` и сохраняет в
  `_wc_gtin_code`;
- `seller` из аналитического черновика не является поставщиком и переименован
  в `salesManager`; источник менеджера продаж пока не подтверждён;
- товар в пути вычисляется по складу 9 «Транспорт»: положительный остаток
  подтверждается только когда весь положительный входящий поток внутри
  горизонта является `PURCHASE_RECEIPT` от организации типа `Т` или `I` и нет
  необъяснённого положительного начального остатка;
- смешанное происхождение и остаток старше горизонта не используются как
  подтверждённая поставка и возвращаются отдельными статусами.

GTIN и транзит являются аналитическими данными. Они не входят в fingerprint
перерасчёта учётной цены и не меняют ФОЛІО.

Такие возможности возвращаются endpoint-ом `capabilities` как
`supported=false` с причиной `SOURCE_NOT_CONFIRMED`.

## Golden-master

На временной MariaDB последовательно применены миграции V1–V11. Затем локальный
Java API построил read-only snapshot schema v3 для склада 5 `Paint_Rus`:

- 7 546 товарных карточек;
- 8 279 исторических движений в fingerprint;
- 76 008 месячных строк;
- поколение опубликовано атомарно со статусом `ACTIVE`;
- ФОЛІО не изменялась.

Проверены реальные запросы MariaDB:

- `capabilities` возвращает schema v3, группы 1–6, типы, единицы и поставщиков;
- поиск по SKU/названию;
- cursor pagination;
- исключение общей группы `Я_НЕИСП` уменьшило совокупность с 7 546 до 2 208 SKU;
- `appliedFilters` содержит нормализованный `EXCLUDE`;
- итоги относятся ко всей совокупности, а не только к странице.

Для проверки SQL многоскладской агрегации одна контрольная строка snapshot была
скопирована только внутри временной MariaDB в два синтетических склада. Query
по складам 5, 6 и 7 вернул один общий SKU, `warehouseRowCount=3` и три строки
`warehouseBreakdown`. Это не создавало складов и не меняло данные Paint_Rus.

В проверенном архивном складе Paint_Rus за выбранные последние 24 месяца не
оказалось movement facts, поэтому финансовые строки там нулевые. Семантика
`ONE_OFF_ORDER`, transfer, return и независимых флагов движения покрыта
модульными тестами классификатора и агрегатора. Многоскладское суммирование,
пересчёт ratios, три склада, исключение группы и несовместимые версии поколений
покрыты тестами service contract.

Перед включением на WordPress требуется после деплоя построить schema v3
snapshot нужных складов `Paint_Ua` и выполнить ручную сверку 10 SKU с ФОЛІО.
