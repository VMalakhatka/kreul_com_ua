# Golden master: полный перерасчёт учётных цен `I_UCHET_TOVAR`

## Идентификация

- Дата проверки: 2026-08-15.
- База: только изолированная копия `Paint_Rus`.
- SQL Server: legacy SQL Server 8, compatibility level 80, кодировка данных
  Windows-1251.
- Режим склада: средняя учётная цена, точный `SCLAD_R.N_2=1000`,
  `SCLAD_R.N_4 IS NULL`.
- Все изменяющие пробы выполнены внутри внешней транзакции с rollback.
- `Paint_Ua` не использовалась и не изменялась.
- Реальные партнёры, документы, адреса подключения и учётные данные в этот
  протокол не включены.

## Подтверждённый контракт процедуры

Штатная полная процедура — `dbo.I_UCHET_TOVAR`. Она принимает настройки
учётной области и режима, а прогресс и остановку сообщает через return status и
INOUT/OUT-параметры:

- `n_group`, `id_sclad` — область расчёта;
- `usredn`, `uchet_rsc`, `period_rsc`, `uch_nal` — настройки алгоритма;
- `art` — входной курсор и последний обработанный/проблемный артикул;
- `n_cur`, `n_tot` — прогресс порции и общий объём;
- `new_art` — курсор продолжения;
- `otr_date` — дата, на которой штатный алгоритм обнаружил отрицательную
  хронологию.

Процедура может обработать несколько SKU за один вызов. Размер порции зависит
от времени выполнения внутри legacy-кода, поэтому одинаковые границы порций в
двух проходах не гарантируются.

`n_cur` относится к одному вызову и должен накапливаться вызывающим кодом.
`n_tot` определяется первым вызовом с `art=NULL` и затем должен оставаться
согласованным до завершения прохода.

## Эксперимент 1: чистый полный rollback-проход

На подтверждённом складе средней цены процедура была вызвана повторно до
`new_art=NULL`. Наблюдения:

- return status завершённых вызовов равен `0`;
- курсор двигался вперёд и завершился штатно;
- накопленный `n_cur` совпал с `n_tot`;
- `otr_date` в чистом проходе отсутствовал;
- внешняя транзакционная граница сохранялась;
- rollback вернул состояние базы к исходному.

Вывод: `I_UCHET_TOVAR` можно безопасно использовать для точного preview только
при отдельной внешней транзакции на каждую порцию и обязательном rollback.

## Эксперимент 2: восстановление приходных учётных сумм

На тестовом товаре был подготовлен контролируемый приход с учётной суммой,
отличающейся от исходной суммы документа. Внутри rollback-транзакции
`I_UCHET_TOVAR`:

- восстановила приходные `SCL_MOVE.SUM_UCHET/SUM_UCVAL` из исходных данных
  документа и настроек учёта;
- пересчитала связанные расходы и итоговую цену карточки;
- после rollback все изменения исчезли.

Вывод: native-full действительно отличается от `i_uchet_add(mode=2)`. Последний
использует уже сохранённые `SUM_UCHET/SUM_UCVAL` как исходные данные, а
`I_UCHET_TOVAR` умеет пересчитать сами приходные учётные суммы.

## Эксперимент 3: отрицательная хронология

На тестовом диапазоне с подтверждённым отрицательным хронологическим остатком
процедура вернула проблемный `art`, `otr_date` и `new_art`. До возврата этих
OUT-параметров она уже успела изменить данные проблемного SKU внутри текущей
транзакции.

Контрольный rollback полностью восстановил значения до вызова.

Выводы:

1. Нельзя коммитить порцию с заполненным `otr_date`.
2. Нельзя считать предупреждение «проверкой до записи»: сигнал возвращается уже
   после частичного DML процедуры.
3. Нельзя откатить проблемную порцию и продолжить apply с `new_art`: вместе с
   проблемным SKU откатываются корректные изменения других SKU этой порции.
4. Для apply обязателен полный точный rollback-preflight. Любая найденная
   проблема блокирует начало apply.
5. Если новая проблема появилась уже во втором проходе, текущая порция должна
   откатиться, а job — остановиться. Предыдущие commit всего склада уже не
   откатываются.

## Наблюдение по `TMP_MOVE`

В лабораторной копии `TMP_MOVE` имела значительный legacy baseline ещё до
эксперимента. В подтверждённом режиме средней цены native-вызовы не меняли этот
baseline.

Следовательно, для native-full нельзя использовать условие «глобальная
`TMP_MOVE` должна быть пустой». Это дало бы ложную блокировку на существующей
базе. Безопасность обеспечивается внешней сериализацией, транзакцией,
OUT-контрактом и сравнением защищённых данных, а не удалением чужих строк
`TMP_MOVE`.

## Зафиксированная безопасная схема Java

### Preview

1. Проверить имя базы, exact allow-list, `N_2=1000` и `N_4 IS NULL`.
2. Получить эксклюзивный mutex перерасчёта.
3. Для каждой порции открыть транзакцию, вызвать `I_UCHET_TOVAR`, прочитать все
   OUT-параметры и проверить контракт.
4. Всегда выполнить rollback порции.
5. При `otr_date` сохранить диагностику и продолжить preview только через новую
   rollback-транзакцию, чтобы собрать остальные проблемы.
6. Успех возможен только при штатном завершении курсора и равенстве накопленного
   `n_cur` и `n_tot`.

### Apply

1. Сначала выполнить весь алгоритм preview.
2. Если найдено хотя бы одно отрицание — не начинать apply.
3. При чистом preflight начать новый проход с `art=NULL`.
4. До apply снять защищённый baseline всего склада.
5. В каждой порции повторно проверить базу, настройки склада, транзакционную
   границу, OUT-контракт и поступательное движение курсора; затем сравнить
   защищённые поля фактически обработанного диапазона с baseline.
6. Коммитить только чистую порцию, а после завершения повторно сверить весь
   baseline склада.
7. При новой проблеме откатить текущую порцию и остановиться.
8. При неизвестном исходе транзакции не повторять и не продолжать
   автоматически.

Time-based границы preflight и apply могут различаться. Безопасность не должна
зависеть от совпадения количества или состава порций.

## Что не подтверждено

- FIFO, LIFO, партийный и фиксированный режимы;
- склады с заполненным `SCLAD_R.N_4`, включая значение `0`;
- параллельный запуск с настольным ФОЛИО;
- безопасный auto-resume после рестарта Java, потери связи или неизвестного
  исхода commit;
- применение native-full в `Paint_Ua`.

До отдельных golden-master экспериментов эти случаи должны блокироваться
конфигурацией или precheck.

## Операционный вывод

Первый rollout должен оставлять native apply выключенным. Разрешается только
rollback-preview на `Paint_Rus`. Реальный apply требует проверенной резервной
копии, отдельного feature flag и окна без ручного перерасчёта.

Файл приложения `folio-accounting-price.log` полезен для диагностики, но не
является транзакционным checkpoint: MSSQL commit и запись лога не атомарны.
