# Отрицательная коррекция: детерминированная арифметика SAFE

Дата: 2026-09-07. Статус: **кандидат подготовлен; 15 SQL-сценариев на
временных таблицах Paint_Rus пройдены. В установленные процедуры Rus/Ua
изменения не внесены. Production rollout ещё не разрешён.**

Обновление после этого этапа: пользователь установил 33 в Rus; затем
[13 сценариев прошли через настоящий установленный wrapper](37_installed_safe_negative_correction_golden_master.md)
с отдельным rollback и независимой сверкой после каждого. Начальная запись
выше описывает состояние на момент теста временных таблиц. Paint_Ua не менялась.

## Причина и границы изменения

В средней цене приход и возврат одновременно присваивали `@sum0`, `@kol0`
и вычисляли `@last_uc` из этих же переменных с повторным прибавлением движения.
При остатке 2 и отрицательном приходе -1 предварительная проверка видела 1,
но SQL Server 2000 мог вычислить знаменатель цены как `(2-1)-1=0`.
Нельзя полагаться на порядок зависимых присваиваний в одном SELECT.

Новый вариант замораживает числители и знаменатель до изменения накопителей:

```sql
SELECT @lavka_denominator=ISNULL(@kol0,0)+ISNULL(@kolc_predm,0),
       @lavka_numerator=@sum0+@sum_predm,
       @lavka_currency_numerator=@sum0v+@sum_valut
-- Existing near-zero guard returns code 20 with the movement diagnostics.
SET @last_uc = @lavka_numerator / @lavka_denominator
SET @last_val = @lavka_currency_numerator / @lavka_denominator
SET @sum0 = @lavka_numerator
SET @sum0v = @lavka_currency_numerator
SET @kol0 = @lavka_denominator
```

Возврат использует ту же последовательность с `@sum`/`@sumv`.
Правило выбора исходной суммы, NULL-семантика числителей, налоги,
физические количества, документы и контракт 20 OUT/input-параметров не меняются.
Нулевой/почти нулевой знаменатель сохраняет `ZERO_ACCOUNTING_DENOMINATOR`,
`AVERAGE_RECEIPT`/`AVERAGE_RETURN`, RECNO, дату, SKU, числитель, знаменатель,
количество до/движение и следующий SKU.

**Не подменять нулевой знаменатель единицей или NULLIF с последующим
сохранением нулевой стоимости.** Код 20 требует rollback всего SKU владельцем
транзакции; сама процедура не делает COMMIT/ROLLBACK.

## Лабораторный тест

Генератор извлекает **полное тело** кандидата 33; не содержит независимой
переписанной реализации средней цены. Для исполнения:

- имена семи таблиц заменяются на локальные `#`-таблицы;
- недостижимый вызов периода заменяется аварийным assert;
- RETURN заменяется фиксацией return code и переходом к проверкам;
- входные параметры задаются синтетическим сценарием;
- ни одна установленная процедура не вызывается и не изменяется.

```sh
python3 folio-rus-lab/tests/test_negative_correction_sql.py
folio-rus-lab/bin/folio-rus-lab health
folio-rus-lab/bin/folio-rus-lab preflight
python3 folio-rus-lab/tests/test_negative_correction_sql.py --emit-sql |
  folio-rus-lab/bin/folio-rus-lab execute --timeout-seconds 30 --max-rows 100 --max-bytes 20000
```

Режим только управляемый ROLLBACK, БД строго Paint_Rus. Тестовые таблицы
существуют исключительно в текущем соединении. Все 15 сценариев выполняются
в одной внешней транзакции; это **не** тест независимых commit/rollback Java
между SKU и **не** полный installed-procedure golden-master.

Проверяются вычисленные количества/суммы/цены (допуск 1e-8), оба валютных
результата, полный диагностический контракт при коде 20, следующий SKU,
неизменность физического остатка/резерва/начального количества, числа и
checksum защищённых полей строк движения, другой карточки и `#TMP_MOVE`.
Checksum — дополнительный контроль fixture, не криптографическое доказательство.
Реальные документы и TMP_MOVE не затрагиваются, поэтому этот тест не является
отдельным доказательством postconditions на реальных таблицах.

## Неизменённый вопрос стоимости отрицательной коррекции

Legacy-условие `@old_uc>=@sum_predm+1e-10 OR @old_uv>=@sum_valut+1e-10`
может предпочесть сохранённую учётную сумму 0 отрицательной сумме документа.
Тест намеренно фиксирует оба результата: 37.44 при сохранённом нуле и 18.67
при применении -18.77. Это не две взаимозаменяемые «правильные цены».
Патч не выбирает новую учётную политику и не разрешает изменять документы.

Также исправление влияет на `last price` при полном выбытии: раньше она могла
содержать результат повторного учёта движения. На положительных движениях
количество/накопленная сумма могут совпасть, но последняя цена — отличаться.
Это нужно учитывать при сравнении golden-master, а не ослаблять все postchecks.

## Gate перед Paint_Ua

1. Согласовать/зафиксировать эталон стоимости отрицательной коррекции, включая
   выбор старого SUM_UCHET. Проверить в штатном отчёте ФОЛИО/с ответственным
   за учёт. Не исправлять исторический документ только ради обхода ошибки.
2. Проверить backup/restore и baseline изолированной Paint_Rus; установить 33
   отдельно под уполномоченным пользователем. Подтвердить actual body/version.
3. Выполнить installed wrapper golden-master на синтетических карточках:
   чистый SKU, отрицательная коррекция, настоящий нулевой знаменатель,
   следующий чистый SKU; плюс положительные движения, возвраты, валюта,
   оба режима 1000/1100 и полное выбытие. Сверить физические остатки, документы,
   SCL_PRIC, TMP_MOVE и отдельные транзакции. После rollback — независимый read.
4. Только после успешного gate и отдельного согласования установить 34 в
   Paint_Ua в окно обслуживания. Java redeploy не устанавливает этот SQL.
5. Повторить native-range preview для проблемного SKU; inspect warnings,
   postcheck и стоимость. Apply — отдельное действие, не часть установки.

До прохождения gate применяется уже реализованный безопасный пропуск SQL8134
с подтверждённым rollback/журналом. Отсутствие деления на ноль само по себе
не подтверждает экономическую правильность перерасчёта.
