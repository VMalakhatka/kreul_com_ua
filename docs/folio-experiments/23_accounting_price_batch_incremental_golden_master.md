# Golden-master: пакетный и инкрементальный перерасчёт учётных цен

Дата проверки: 2026-08-19.

Стенд: изолированная `Paint_Rus`, SQL Server `8.00.760`, compatibility level
80, `SQL_Ukrainian_CP1251_CI_AS`, CP1251. Strict preflight был успешен до и
после экспериментов. `Paint_Ua` не изменялась.

## Пакет из 25 чистых SKU

Двадцать пять последовательных вызовов `dbo.LAVKA_I_UCHET_TOVAR_SAFE` были
выполнены внутри одной внешней транзакции:

- rollback run: `202dd06c-c768-42e5-a261-ccca81a4ad75`;
- повторный rollback с обязательными postconditions:
  `ec97a91f-7e3c-4d41-b67e-1313211d1bb6`;
- commit run: `6aaafa3d-222f-4a9b-aca2-28eccf53fe7b`;
- обработано 25 SKU и 1 113 legacy progress units;
- return code `0`, предупреждений нет;
- защищённые количества карточек, структура и исходные поля движений не
  изменились;
- состав `TMP_MOVE` не изменился;
- commit завершился с чистым `@@TRANCOUNT=0`, независимый preflight после
  commit подтвердил strict isolation.

Время выполнения одинакового вычислительного диапазона составило примерно
10–13 секунд. Следовательно, объединение Java-транзакций уменьшает сетевые и
служебные расходы, но основное время расходуется внутри алгоритма ФОЛИО для
каждого SKU.

## Пакет с отрицательной хронологией

Порция была начата за пять SKU до ранее подтверждённого товара с отрицательной
хронологией:

- rollback run: `9d2285b4-7ca4-4262-93df-1f8175a64f60`;
- пять чистых SKU прошли, шестой вернул `otr_date`;
- вся порция была откатана;
- защищённые карточки, движения и `TMP_MOVE` не изменились;
- отдельный rollback-вызов со следующего `new_art` успешно обработал следующий
  чистый SKU и завершил диапазон (`4ecb3421-e1fe-453c-8f7b-225f96d4d9a0`).

Подтверждён безопасный алгоритм: откатить проблемную порцию, сохранить
диагностику, при apply переиграть её по одному SKU либо остановить текущую
порцию, затем продолжить с подтверждённого `new_art`.

## Скорость fingerprint-сканирования

Read-only SQL построил агрегированный fingerprint входных данных склада с:

- 35 409 карточками;
- 1 447 773 учитываемыми движениями;
- временем 9,6 секунды;
- rollback run: `e9d36625-2161-422a-addf-7943cbf91924`.

Это на порядки быстрее полного запуска процедуры по каждому SKU. Поэтому
основной рабочий режим после первого успешного полного apply должен быть
инкрементальным: сравнить сохранённый снимок входных данных и пересчитать только
SKU, fingerprint которых изменился.

Нельзя отбирать изменения только по `DATE_PREDM`: документ может быть добавлен
задним числом, старая строка может быть исправлена или удалена. Снимок должен
включать состав строк и все входные поля расчёта, а также настройки склада и
глобальные зависимости курсов. После изменения глобальной зависимости весь
склад помечается dirty.

`CHECKSUM_AGG/BINARY_CHECKSUM` пригоден как быстрый candidate finder, но не как
единственное финансовое доказательство из-за теоретических коллизий. Постоянный
MariaDB-снимок должен хранить устойчивый digest и служебные counts; применённый
fingerprint обновляется только после успешного commit конкретного SKU.

## Полный Java-снимок и проверка delta

Лабораторный API построил полный per-SKU снимок источников учётной цены склада
12 и повторил его без изменений:

- первый run `0a311be6-eea5-4fca-ad71-79a00ed37aed` создал baseline за 42 секунды;
- повторный run `4cf18c80-720c-4f63-b98e-4314b6a6e0d0` завершился за 43 секунды;
- оба запуска вернули один digest
  `571da399370e1b27c98d1a99fce7b5d73ba6624d93d013964eae08678aafccb3`;
- сверены 35 409 SKU, 1 447 773 учитываемых движения и 4 строки правил цены;
- результат повторного запуска: `UNCHANGED`, dirty/new/removed = 0.

Для стабильности fingerprint нельзя включать `SUM(float)`: SQL Server может
менять порядок сложения и давать незначительно различающийся результат без
изменения данных. Движения и правила цены нужно агрегировать через join с
`SCL_ARTC` и группировать по каноническому `SCL_ARTC.COD_ARTIC`. Иначе
регистронезависимая и игнорирующая конечные пробелы SQL-коллация может вернуть
разные строковые представления одного SKU, которые Java ошибочно сочтёт разными.

Rollback-only probe `317c81c3-183a-4008-900c-aa4ae811a468` подтвердил
обнаружение:

- исправления существующего движения, включая изменение задним числом;
- добавления движения;
- физического удаления движения.

Все три признака вернулись `true`, внешняя транзакция завершилась состоянием
`ROLLED_BACK`. После эксперимента run
`2d122d0d-931a-4638-8a9e-db363cd26dfc` снова вернул исходный digest и
`UNCHANGED`, то есть постоянных изменений не осталось.

Лабораторный baseline пока хранится только в памяти и теряется при рестарте.
Production-реализация должна хранить generation и per-SKU fingerprint в
MariaDB. Сравнение текущего состояния с baseline не должно автоматически
продвигать baseline: fingerprint конкретного SKU обновляется только после его
успешного перерасчёта, commit и postcheck. Поэтому dirty SKU остаётся dirty при
повторных проверках, пока его безопасно не обработали.

Рабочая схема после первого полного перерасчёта: быстрый read-only снимок всех
источников, точная диагностика и перерасчёт только dirty/new SKU, удаление
baseline для исчезнувших карточек. Полный native audit остаётся отдельной
редкой процедурой вне рабочего времени.
