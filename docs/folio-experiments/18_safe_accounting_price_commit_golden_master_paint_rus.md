# Golden-master: per-SKU commit/rollback учётных цен Paint_Rus

Дата: 2026-08-18.

База: только изолированная `Paint_Rus`, SQL Server `8.00.760`, compatibility
level 80, `SQL_Ukrainian_CP1251_CI_AS`, CP1251. Склад 12 имел
`SCLAD_R.N_2=1000`, `N_4 IS NULL`. `Paint_Ua` не использовалась.

Цель — подтвердить последовательность:

1. чистый SKU действительно проходит процедуру и commit;
2. SKU с отрицательной хронологией полностью откатывается и фиксируется в
   журнале результата;
3. последующий чистый SKU также проходит commit;
4. остатки, документы и `TMP_MOVE` не повреждаются.

## Защита эксперимента

Каждая clean-проба выполнялась одной управляемой транзакцией:

1. снимались card/movement/document/SCL_PRIC/TMP_MOVE fingerprints и физические
   остатки;
2. `SCL_ARTC.UCHET_CENA` временно менялась на контрольное значение;
3. вызывалась `dbo.LAVKA_I_UCHET_TOVAR_SAFE` ровно для одного SKU;
4. процедура должна была вернуть исходное каноническое состояние;
5. SQL сравнивал все защищённые fingerprints и настройки склада;
6. только после успешного сравнения лаборатория выполняла commit.

Перед каждым commit тот же batch успешно выполнялся с обязательным rollback.
После каждого результата состояние проверялось новым JDBC-соединением.

## Clean commit до проблемы

Тестовый SKU с двумя движениями и двумя связанными документами:

- procedure return code: `0`;
- baseline card fingerprint: `-628101885`;
- fingerprint с контрольным искажением: `175951292`;
- fingerprint после safe-перерасчёта: `-628101885`;
- состояние лаборатории: `COMMITTED`;
- run id: `e964af60-a08f-498d-a680-6d8f6f53d6b6`;
- новое соединение подтвердило исходные цену, суммы, остатки, движения и
  документы.

Следовательно, процедура действительно восстановила цену после наблюдаемого
контрольного изменения, а API зафиксировал транзакцию только после совпадения с
каноническим baseline.

## Проблемный SKU между commit

Для существующего SKU с отрицательной хронологией процедура вернула:

- journal code: `NEGATIVE_CHRONOLOGICAL_STOCK`;
- problem date: `22.04.2017`;
- return code: `0`;
- next SKU был заполнен;
- card fingerprint внутри транзакции изменился с `1544557604` на
  `-1419287589`;
- movement fingerprint, документ и `TMP_MOVE` внутри пробы не изменились;
- состояние лаборатории: `ROLLED_BACK`;
- run id: `f75da838-291c-4060-8af7-dde43de2f3d6`.

Изменившийся card fingerprint доказывает, что отрицательный сигнал приходит
после частичного DML. Независимый postcheck после rollback вернул исходный card
fingerprint и чистый `@@TRANCOUNT=0`. Поэтому проблемный SKU нельзя commit-ить;
его транзакция должна целиком откатываться, после чего оркестратор может перейти
к следующему SKU.

## Контроль остатка и служебных таблиц

До, между и после трёх сценариев совпали:

- `NACH_KOLCH`, `KON_KOLCH`, `REZ_KOLCH` всех выбранных карточек;
- количество, ключи, даты, типы и количества движений;
- fingerprints связанных `SCL_NAKL`;
- настройки склада `N_2/N_4`;
- количество строк `TMP_MOVE`: `379462`;
- максимальный `TMP_MOVE.UNICUM_NUM`: `11558`;
- fingerprint ключей `TMP_MOVE`: `2134000384`;
- `transactionBefore=0` и `transactionAfter=0` каждого завершённого запуска.

`CHECKSUM_AGG/BINARY_CHECKSUM` здесь используется как воспроизводимый
fingerprint вместе с точными row counts и отдельным сравнением бизнес-полей, а
не как криптографическое доказательство.

## Дополнительное наблюдение

Не каждый SKU без ошибки является zero-delta. Для одной чистой карточки
rollback-проба показала штатное изменение `NDS_ARTIC` с `-100` на рассчитанное
значение, тогда как учётная цена, движения, остатки и документы не менялись.
Эта проба намеренно не была закоммичена.

Следствие: production postcheck должен разрешать документированные производные
изменения `NDS_ARTIC`, `CENA_*` и `SCL_PRIC`, но отдельно защищать остатки,
структуру движений, исходные суммы документов и настройки склада. Нельзя
требовать от каждого успешного перерасчёта полной zero-delta карточки.

## Вывод

Для подтверждённого режима средней цены (`N_2=1000`, `N_4 IS NULL`) доказана
базовая схема per-SKU оркестрации:

- чистый SKU — validate и commit;
- отрицательный остаток/код безопасной остановки — rollback и warning;
- после rollback обработка следующего SKU может продолжаться;
- неизвестная ошибка или нарушение transaction boundary остаётся fail-stop.

Это подтверждает подход на `Paint_Rus`, но ещё не разрешает установку или apply
на `Paint_Ua`. Следующий обязательный шаг — сравнить exact определения штатных
процедур двух баз и подготовить отдельную Paint_Ua-safe версию при наличии
различий.
