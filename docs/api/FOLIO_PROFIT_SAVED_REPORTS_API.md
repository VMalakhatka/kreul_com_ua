# Постоянная история «Прибыли Лавки»

## Дополнение 2026-10-31: последний сохранённый результат по умолчанию

По решению владельца `GET /{month}` без `revisionId` и saved range выбирают
**последний сохранённый результат**, а не `publishedRevisionId`. Результат —
ревизия `COMPLETED` или `PROVISIONAL` с непустым `report_json`; выбирается
максимальный ID для данного `sourceDatabase × month`. Это порядок запросов,
не время завершения: позднее завершение старого запроса не вытесняет новый результат.

Правила выбора:

| История месяца | Ответ по умолчанию |
| --- | --- |
| Опубликован COMPLETED №1, затем PROVISIONAL №2 | №2, `status=PROVISIONAL`, `publishedRevisionId=1`, `published=false` |
| После №2 появилась FAILED/RUNNING попытка №3 | По-прежнему №2; `latestRevisionId=3`, `latestStatus=FAILED/RUNNING` |
| Есть только FAILED/RUNNING попытки, сохранённого результата нет | `ok=false`, `status=FAILED/RUNNING`, `revisionId=null`, `report=null`; ID попытки в `latestRevisionId` |
| Нет истории | `status=MISSING`, `revisionId=null`, `report=null` |
| Есть COMPLETED/PROVISIONAL, но нет непустого payload | `status=MISSING`, `errorCode=PROFIT_SAVED_REPORT_PAYLOAD_MISSING`, latest-метаданные сохранены |

SQL NULL, пустая строка и JSON `null` не являются результатом. Непустой повреждённый
JSON — видимая ошибка чтения, не повод незаметно выбрать старую версию или вызвать
перерасчёт. Выбор ограничен `latestRevisionId`, прочитанным для месяца: параллельно
созданная новая ревизия будет видна при следующем GET. Разные месяцы диапазона
читаются последовательно, не как единый транзакционный снимок appDB.

`?revisionId=...` остаётся явным выбором исторической версии, даже если она
PROVISIONAL/FAILED/RUNNING. FAILED может содержать диагностический report; его
нельзя подмешивать в default month или totals диапазона. Без готового результата
null не заменяется нулём. Для просмотра ошибки без результата использовать
`latestRevisionId`, для экспорта результата — возвращённый `revisionId`.

`publishedRevisionId` и `published` — отдельные метаданные публикации; они
**не обозначают выбранный текущий результат**. В `months[]` range эти два поля
добавлены без удаления прежних полей. `latestRevisionId/latestStatus` относятся
к последней попытке, а `revisionId/status` — к выбранному результату. Последний
FAILED не делает ранее сохранённый COMPLETED предварительным: предупреждение
о неудачной попытке показывается отдельно от полноты выбранного отчёта.

Нужен новый Java deploy; SQL-миграция, повторный расчёт и изменение указателей
публикации не нужны. GET только читает application DB; финансовые формулы,
неизменяемые payload, warnings, audit flags, настройка публикации и ФОЛИО не меняются.
Frontend должен сохранять пометку PROVISIONAL и использовать `totals` и
`months[].revisionId` одного ответа range, не подменяя их `latestRevisionId` или
`publishedRevisionId`. Новые результаты между запросами не меняют уже выбранные
версии экспорта/сравнения: запрашивать их только с явным `revisionId`.

Синтетический HTTP-пример (не данные production):

```json
{
  "revisionId": 2,
  "status": "PROVISIONAL",
  "publishedRevisionId": 1,
  "published": false,
  "latestRevisionId": 3,
  "latestStatus": "FAILED"
}
```

Это выдержка полей wrapper, не полный report. Полные сериализованные month/range
для frontend-проверки создаёт `FolioProfitLatestResultTest` в build-каталоге
`target/profit-latest-result-fixtures/month.json` и `range.json`: published №1,
выбранный provisional №2 (прибыль Киева 120), неудачная попытка №3. Проверяется
совпадение выбранного ID/сумм, сохранность warnings, `complete=false` и явный
исторический GET после появления следующего результата. Тест не читает ФОЛИО.

## Дополнение 2026-10-24.1: снимок настроек отбора

[Scope-settings контракт](FOLIO_PROFIT_SCOPE_SETTINGS_API.md) добавляет
`expectedScopeSettingsVersion` в calculate. Новый requestId захватывает
настройки и проверяет pin до reserve; конфликт даёт 409 без FAILED-ревизии.
Replay имеет приоритет и не обращается к текущим настройкам/каталогу.
В неизменяемом report V15 сохраняются эффективные `scopeSettings` и выбранные
названия/пути `scopeCatalog`; их копии есть в range `months[]`. Старые payload
возвращают null, а отсутствие поля в старом request не меняет его hash.
V20 хранит только общую настройку, не переписывает историю V15.
Итоги saved range остаются суммой сохранённых значений, независимо от scopes.

## Методы

Дополнение `2026-09-22.1`: [налоговые настройки и фиксация версии](FOLIO_PROFIT_TAX_SETTINGS_API.md).
`POST /{month}/calculate` принимает optional `taxSettingsVersion`. Для нового requestId
версия проверяется до резервирования ревизии; несовпадение → HTTP409
`PROFIT_TAX_SETTINGS_VERSION_CONFLICT` без нового расчёта. Прочитанные списки/версия
фиксируются один раз и сохраняются в `report.taxDetails.settings`.
Replay прежнего requestId имеет приоритет над проверкой текущей версии.
Старые запросы без поля совместимы, старый JSON без taxDetails не обогащается defaults.
V17 хранит только настройки; V15 остаётся хранилищем полного неизменяемого DTO.

Базовый путь `/admin/folio/profit-report/saved`.

- `GET ?fromMonth=2025-07&toMonth=2025-11` — включительный диапазон до24месяцев.
  Только сохранённые данные; отсутствующие месяцы не рассчитываются.
- `GET /{month}` — последний COMPLETED/PROVISIONAL с сохранённым отчётом.
  `?revisionId=...` выбирает конкретную
  ревизию этого месяца, включая предварительную/ошибочную/незавершённую.
- `GET /{month}/revisions?limit=20&beforeRevisionId=...` — metadata по убыванию ID,
  limit1..100, для следующей страницы передавать последний ID.
- `POST /{month}/calculate` — явный расчёт **одного** месяца с полным auditDTO.
  Синхронный запрос; frontend диапазон обрабатывает последовательными командами.

Ответ истории: `{ok, month, revisions, hasMore, nextBeforeRevisionId}`.
Элементы `revisions` содержат метаданные ревизии без полного `report`;
для подробностей используется GET конкретного месяца с `revisionId`.

```json
{
  "requestId": "b7a3b49e-8c04-4a6b-b250-6b9e44a76cf0",
  "kyivEmployeeCount": 4,
  "odesaEmployeeCount": 3,
  "rubToUahRate": 0.41,
  "odesaAdditionalSalary": 0,
  "kyivAdditionalSalary": 0,
  "kyivStockWarehouseIds": [1,7,12],
  "odesaStockWarehouseIds": [5]
}
```

Опциональные `odesaMasterClassIncome/Return` остаются legacy ignored параметрами.
Отсутствие и явный0 сохраняются различными. Defaults применяет прежний сервис
один раз для каждого месяца, затем сохраняются `report.inputs`. В частности,
default5000 Одессы — **на каждый месяц**, не один раз на диапазон.

С версии правил `2026-09-15.1` численность хранится в raw `request` и эффективных
`report.inputs` вместе с total, mode и долями. Counts применяются отдельно к
каждому месяцу. Старые payload не пересчитываются и не обогащаются текущими
default: отсутствующая историческая численность остаётся null. У старых запросов
без counts сериализованный формат для request_hash сохранён; повтор старого UUID
не вызывает новый расчёт. Изменение counts с тем же UUID — конфликт, как изменение
любого другого параметра. Явная legacy доля поддерживается, смешивать её с counts
нельзя. V15/LONGTEXT JSON уже достаточно: новая SQL-миграция не нужна.

## Ревизия и публикация

Wrapper: `ok`, `status`, `sourceDatabase`, `month`, `revisionId`, `requestId`,
`publishedRevisionId`, `latestRevisionId`, `latestStatus`, `published`,
`auditComplete`, `createdAt`, `completedAt`, `request` (исходные параметры),
`report` (полный неизменённый FolioProfitReportResponse или null), `errorCode`.
Статусы: `RUNNING`, `FAILED`, `COMPLETED`, `PROVISIONAL`, `MISSING`.
ok=true означает сохранённый результат, но не его полную финансовую проверку.

Неизменённые правила записи **публикации** (не выбора default GET):
первый результат, включая предварительный, доступен как опубликованный.
PROVISIONAL не заменяет ранее опубликованный отчёт. COMPLETED заменяет pointer
только при более новом revisionId. Ошибки остаются в истории и не удаляют
прежний отчёт. `latestRevisionId/latestStatus` показывают последнюю попытку,
включая FAILED/RUNNING. По умолчанию читается последний доступный результат,
даже когда опубликованная ревизия осталась прежней.
Кнопка ручного продвижения предварительного результата в v1 отсутствует.

COMPLETED требует report.complete=true и полного сохранённого аудита по
имеющимся truncationflags. PROVISIONAL включает неполные разделы, бизнес-
предупреждения, требующие проверки, или ограниченный audit. Сохраняются **все**
имеющиеся diagnostics/warnings/sections/flags, не только сводка. Если audit
ограничен500 документов, сохранение не делает его полным. Исходные legacy GET
summary/audit пока остаются live и не сохраняют результат автоматически.

POST обязательно содержит UUID requestId. Он уникален в sourceDatabase.
Повтор **того же** запроса возвращает прежнюю ревизию без обращения к ФОЛИО;
тот же UUID с иными параметрами/месяцем — конфликт. Повтор RUNNING не начинает
второй расчёт. RUNNING после потери процесса может остаться в истории: это
сохранённое состояние запроса, не доказательство активности Java. Нет
автоматического повторения/восстановления расчёта после рестарта.

При потере HTTP frontend читает revisions/GET по ID и не выдаёт новый UUID
автоматически. Команда остановки диапазона не прерывает текущий POST — только
запрещает отправку следующих месяцев. Таймаут не доказывает отсутствие commit
application DB. Если DB недоступна, нельзя объявлять результат сохранённым.

## Диапазон

Ответ: `ok`, `fromMonth`, `toMonth`, `sourceDatabase`, `complete`, `missingMonths`,
`months[]`, `totals[]`, `warnings[]`.
months — краткие wrappers выбранных последних сохранённых результатов: month/revisionId/status,
latestRevisionId/latestStatus, calculatedAt, ruleVersion, auditComplete,
inputs/cities/inventory, scopeSettings/scopeCatalog, publishedRevisionId/published
(без полного audit массива). Месяцы без готового результата имеют `revisionId=null`,
статус MISSING/FAILED/RUNNING и перечислены в `missingMonths`; их суммы не обнуляются.
Выбор и totals используют один и тот же набор сохранённых report. Полный аудит
и warnings месяца читаются через `GET /{month}?revisionId=<months[].revisionId>`.

totals по KYIV/ODESA: `city`, `baseGrossProfit`, `manualGrossAdjustments`,
`grossProfit`, `operatingExpenses`, `profit`, `openingAccountingValue`,
`closingAccountingValue`, `accountingValueChange`, `complete`.
Деньги — decimal строки/null, валюта потоков отчёта UAH. Выручка не подменяется
валовой прибылью: прежний DTO не содержит sales revenue, её новый API не выдумывает.

Правило сохранённых итогов от **24.10.2026**: все пять денежных потоков
(`baseGrossProfit`, `manualGrossAdjustments`, `grossProfit`, `operatingExpenses`,
`profit`) складываются из сохранённых месячных значений **независимо от состава
складов**. Разные, пустые или отсутствующие списки складов (включая отсутствие
исторического `inputs`) не блокируют суммы, не уменьшают `complete` и не создают
предупреждение о несопоставимости. Например, Киев `[1,7,12]` в одном месяце и
`[1,7]` в следующем — обычное сложение сохранённых сумм. Это не пересчёт месяцев
на общем наборе складов; их `inputs` остаются в ответе без изменений.

Потоки складываются только если каждый месяц содержит город и соответствующее
поле; при missing/null общий показатель null, не сумма доступных месяцев.
Явный ноль остаётся нулём. Отсутствующее поле не обнуляет другие известные итоги.
Известные предварительные суммы допускаются с `complete=false`. Полнота требует
статуса `COMPLETED` всех месяцев и наличия всех итоговых сумм и обеих границ
остатка; остальные правила статуса и публикации месячной ревизии не меняются.

Остатки: начало **первого запрошенного** и конец **последнего запрошенного** месяца,
никогда не сумма остатков.
`accountingValueChange = closingAccountingValue - openingAccountingValue`;
null только при отсутствии нужной границы, а не из-за
разного состава складов. Пропущенная граница не заменяется ближайшим доступным
месяцем. Пропуск внутри диапазона сохраняет известные крайние остатки, но потоки
становятся null и `complete=false`.
Курс и налоговая доля не усредняются: каждый месяц сохраняет свои inputs.

Форма GET-запроса не меняется; два поля публикации в `months[]` добавлены 31.10.2026.
Frontend показывает `totals` Java,
не складывает неполные данные самостоятельно и не проверяет равенство складов.
Для нового поведения нужен деплой Java; пересчитывать/публиковать месяцы заново,
менять `publishedRevisionId` или обращаться к живой ФОЛИО не требуется.

## Хранение и ограничения

`folio_profit_report_revision`: immutable terminal payload LONGTEXT JSON,
raw request JSON/hash, source/month, статус, даты, auditComplete, errorCode.
`folio_profit_report_month`: атомарный указатель опубликованной и последней
запрошенной ревизии, ключ sourceDatabase×YYYY-MM. Поздно завершившаяся старая
команда не откатывает опубликованный указатель назад. Расчёт выполняется вне
MariaDB-транзакции, только финальное сохранение+publication — одна транзакция.

Namespace базы берётся из настроенного JDBC URL без подключения к ФОЛИО.
Исправление 22.09.2026 поддерживает оба формата jTDS SQL Server:
`jdbc:jtds:sqlserver://host:1433/Paint_Ua` и
`jdbc:jtds:sqlserver://host:1433;databaseName=Paint_Ua` (имя свойства без учёта регистра).
Регистр самого имени базы сохраняется, чтобы не менять ключи исторических ревизий.
Одинаковые повторные указания допустимы; конфликт пути/свойства или нескольких
`databaseName`, пустое/небезопасное имя — `PROFIT_SOURCE_NAMESPACE_UNAVAILABLE`.
Значения других свойств в квадратных скобках не разбираются как указания базы.
Дополнительно чистый `jTDS Driver.getPropertyInfo` подтверждает, что драйвер прочитает
то же имя (без открытия соединения). JDBC URL и причины ошибок драйвера в ответ не выводятся.
Это исправляет ошибку production истории при `;databaseName=Paint_Ua`, не меняя
подключение, таблицы, существующие отчёты, правила расчёта или frontend-контракт.
После Java deploy достаточно повторить GET сохранённого месяца; пересчёт и миграция
данных для этого исправления не нужны. При отсутствии сохранённого месяца штатно вернётся MISSING.
При неопределённом имени источника запрос отклоняется, а не смешивается с Paint_Ua.
JSON содержит закрытые финансовые документы: только защищённый admin proxy,
резервное копирование appDB, не логировать payload и не публиковать raw exports.
GET истории никогда не вызывает FolioProfitReportService или DAO ФОЛИО.
Для включения нужны V15 и Java deploy; в рамках разработки миграция на prod
не применяется, deploy/commit/push отдельно по команде пользователя.
