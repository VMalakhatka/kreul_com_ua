# Profit warehouse scopes and inventory exclusions

Контракт реализации от 24.10.2026, `ruleVersion=2026-10-24.1`. Java владеет настройками и расчётом;
WordPress — формой, авторизацией пользователя и server-side proxy. До деплоя
Java новые routes/поля не считать доступными. Живые расчёты и production DDL
в рамках разработки не запускались.

Как и tax-settings, routes предназначены только для закрытого `/admin`
perimeter/VPN/proxy. В Java нет отдельной финансовой авторизации: WordPress
проверяет capability и nonce, обращается server-side. Перед публикацией
необходимо проверить защиту новых GET/PUT маршрутов; прямо из браузера их
не вызывать. Изменение кода не подтверждает состояние production-защиты.

## Endpoints и DTO

- `GET /admin/folio/profit-report/scope-settings` — текущий плоский DTO ниже;
  только application DB, без обращения к ФОЛИО и без записи defaults.
- `PUT /admin/folio/profit-report/scope-settings` — полная замена по CAS `version`;
  проверяет реальные ID/пути в read-only каталоге ФОЛИО, сохраняет только в
  application DB, возвращает тот же DTO с `version + 1`.
- `GET /admin/folio/profit-report/scope-catalog` — read-only ФОЛИО-каталог.

```json
{
  "version": 0,
  "kyivWarehouseIds": [1, 7],
  "odesaWarehouseIds": [5],
  "kyivStockWarehouseIds": [1, 7, 12],
  "odesaStockWarehouseIds": [5],
  "excludedInventoryGroupIds": [],
  "excludedInventorySubgroupIds": []
}
```

Здесь склады — JSON integer, исключения — **строковые opaque ID** из каталога.
Версия 0 — ещё не сохранено; начальные склады берутся из действующих Java
properties, поэтому пример не заменяет фактический GET. Все четыре списка
складов обязательны, непусты, уникальны, максимум 50 каждый. Пересечения Киев /
Одесса запрещены отдельно среди sales и отдельно среди stock. Совпадение sales
и stock допустимо. Два списка исключений обязательны, могут быть пустыми;
суммарно максимум 100 уникальных веток. Не создавать скрытые исключения.

## Реальные ключи каталога

```json
{
  "warehouses": [{"id": 1, "name": "Киев"}],
  "groups": [{"id": "g:...", "name": "Материалы", "path": ["Материалы"]}],
  "subgroups": [{
    "id": "g:...", "groupId": "g:...", "parentId": "g:...",
    "name": "Бумага", "level": 2, "path": ["Материалы", "Бумага"]
  }]
}
```

Источники подтверждены существующим DAO и сохранённым описанием колонок:

- `SCLAD_R.ID_SCLAD / NAME_SCLAD` — все реальные склады, не только видимые в Woo.
- `SCL_ARTC.NGROUP_TVR, NGROUP_TV2, NGROUP_TV3, NGROUP_TV4, NGROUP_TV5,
  NGROUP_TV6` — строковые уровни групп карточки на физическом складе.
  Это использованный в текущих карточках справочник путей, не Woo category IDs
  и не CRM_PRODUCTGROUPS. В данной реализации отдельный числовой FK группы
  не предполагается. Живая схема при этой доработке заново не проверялась.
  В сохранённом описании шесть колонок имеют тип `varchar(30)`, collation
  `SQL_Ukrainian_CP1251_CI_AS`; DAO сравнивает trim-значения побайтово и
  конвертирует bind-параметры в VARCHAR перед VARBINARY. Это сохраняет точные
  пути, несмотря на case-insensitive collation. Лимит DTO 255 — защитная
  верхняя граница, не утверждение о длине живых колонок.

`groups` — префиксы уровня 1, `subgroups` — префиксы уровней 2–6.
`groupId` всегда указывает на корневую группу, `parentId` — на непосредственного
родителя (для уровня 2 совпадают). Путь сохраняет промежуточные пустые уровни,
концевые пустые уровни отбрасываются. SQL trim удаляет крайние обычные пробелы;
регистр, внутренние пробелы, кириллические/латинские двойники не подменяются.
Имя — значение последнего уровня; пустое имя UI подписывает отдельно.

ID = `g:` + base64url без padding от UTF-8 компактного JSON-массива полного пути.
Максимальная длина ID — **13000 ASCII-символов**, каждого исходного уровня —
255 символов, путь 1–6 уровней. PHP проверяет тип/размер и берёт ID из каталога;
не декодирует и не нормализует его.
Frontend **не конструирует и не сравнивает ID по именам**, а использует каталог.
Ключ отличает `A / Общая` от `B / Общая`, не зависит от порядка SELECT.
Исключение группы исключает все дочерние пути; исключение подгруппы — её ветку
с потомками, но не такую же подпись под другим родителем.

Каталог не считается успешным пустым ответом при ошибке БД. При недоступном
каталоге нельзя сохранять/подменять выбор. Неизвестный выбранный ID не игнорируется.

## Ошибки и конкурентное сохранение

- HTTP 400 `PROFIT_SCOPE_SETTINGS_INVALID` — структура, версия, лимит/дубликат.
- HTTP 400 `PROFIT_SCOPE_WAREHOUSE_OVERLAP` — пересечение городов.
- HTTP 400 `PROFIT_SCOPE_WAREHOUSE_NOT_FOUND` — ID склада отсутствует в каталоге.
- HTTP 400 `PROFIT_SCOPE_GROUP_NOT_FOUND` — ветка отсутствует или выбрана не в том
  списке (уровень 1 в subgroup, уровень 2–6 в group).
- HTTP 409 `PROFIT_SCOPE_SETTINGS_VERSION_CONFLICT` — версия изменилась; перечитать
  настройки и попросить пользователя согласовать, не повторять PUT автоматически.

CAS атомарен, включая двух первых писателей версии 0. Недоступная/повреждённая
таблица настроек не заменяется defaults. Для хранения нужна application migration
`V20__folio_profit_scope_settings.sql`; ФОЛИО не изменяется.

## Новые расчёты, старые отчёты и диапазоны

В `POST /admin/folio/profit-report/saved/{month}/calculate` добавлено необязательное
поле `expectedScopeSettingsVersion` (целое >= 0). Новый frontend передаёт его
всегда. В начале batch прочитать настройки один раз и передавать одну версию
для всех месяцев: при изменении следующий месяц получает 409 **до reserve и
расчёта**. Уже сохранённые месяцы не перепубликовываются.

Java захватывает настройки один раз на новый расчёт; изменения во время чтения
источника не меняют текущий результат. Идемпотентный повтор UUID читает старую
ревизию и не проверяет текущую версию заново. Legacy payload без нового поля
по-прежнему принимается и использует текущие настройки. Добавление null-поля
не меняет исторический request hash.

Новый `report.scopeSettings` хранит **эффективный** полный DTO: версия выбранной
настройки и применённые списки. `inputs` также содержит фактические склады.
`report.scopeCatalog` — snapshot той же формы `{warehouses,groups,subgroups}`:
все использованные sales/stock склады с именами, выбранные исключения и их
родительские ветки с `path/name`. Для UI и Excel читать только этот snapshot;
не запрашивать текущий каталог при просмотре истории. Наличие родителя в
scopeCatalog не означает, что он исключён: выбор задан списками scopeSettings.
Legacy `kyivStockWarehouseIds / odesaStockWarehouseIds` в calculate/live GET
сохраняются как override только stock-складов текущего расчёта: валидируются,
не сохраняют глобальные настройки, не отменяют exclusions. `version` в snapshot
при этом относится к исходной настройке, overrides видны в сохранённом request.
Новый UI должен опускать эти overrides, если используются общие настройки.
Невалидные/пересекающиеся overrides теперь отклоняются до расчётных чтений,
а не маскируются предварительным результатом секции INVENTORY. При сохранённом
calculate невалидный override даёт FAILED-ревизию с кодом ошибки без расчёта
источников; pin-конфликт по-прежнему возвращает 409 до резервирования ревизии.

Старые `report.scopeSettings=null / report.scopeCatalog=null` означают «не сохранялось»; нельзя дописывать
текущие настройки в старые ревизии. GET истории/диапазона не читает текущую ФОЛИО.
Итоги диапазона продолжают складывать сохранённые значения без сравнения scopes.
В `saved` range поля `months[].scopeSettings` и `months[].scopeCatalog` также
содержат metadata выбранной сохранённой ревизии; для старого/отсутствующего
payload они null. Полный report остаётся доступен через GET revision.

## Границы влияния и МК

Sales-списки выбирают gross margin соответствующего города. Исключения групп
затрагивают **только** opening/closing inventory и связанные counts, не gross,
МК, расходы или налоги. Отбор по текущей карточке `SCL_ARTC` применяется одинаково
к начальному остатку и всем историческим движениям этого SKU × склад до дат
отчёта. Это не историческая реконструкция смены группы. Неклассифицированные
товары не исключаются автоматически; только явное совпадение выбранной ветки.

МК остаются на неизменных складах **1 (Киев), 5 (Одесса)** независимо от настроек.
Коррекция убирает МК из base только там, где склад МК действительно попал в
выбранный sales-список, затем относит чистый МК в свой город ровно один раз.
Даже если склад 5 попал в sales Киева, МК Одессы не должен одновременно остаться
в gross Киева и добавиться Одессе. Exclusions остатков не влияют на эту коррекцию.
При перекрёстном выборе складов `cities[].manualGrossAdjustment` уже содержит
вычет МК из фактического города base и включение в родной город. Не прибавлять
`masterClassesByCity` повторно. Поля МК summary `grossProfitAlreadyInBase` и
`adjustment` описывают собственный город; для итогов городов использовать
готовые `cities[]`, а не реконструировать перекрёстный перенос во frontend.

Все SQL-чтения совместимы с SQL Server 2000; NOLOCK/read-only, ограниченный
таймаут. Новая настройка не превращает месячный отчёт в транзакционный снимок
живой ФОЛИО.

## Проверки и запуск

Unit/MockMvc: `FolioProfitScopeSettingsTest`, `FolioProfitScopeSqlTest`,
`FolioProfitScopeSettingsDaoTest`, `FolioProfitScopeSettingsControllerTest`,
`FolioProfitScopeReportTest`, дополненный `FolioProfitHistoryServiceTest`.
Проверяются CAS/conflict, строгие типы, полные пути, bind-параметры,
inventory-only exclusions, МК при перекрёстном выборе складов, неизменяемость
истории и старого hash, отсутствие чтений источника при replay.

`FolioProfitScopeSettingsMariaDbTest` по умолчанию выключен. Для отдельной
одноразовой локальной MariaDB на loopback:13370 используются opt-in
`-Dfolio.profit.scope.test.port=13370` и переменная `WP_SCOPE_TEST_PASSWORD`.
Тест создаёт/удаляет только собственную случайную схему `profit_scope_test_*`,
проверяет Flyway V20, persistence и гонки INSERT/UPDATE; каталог ФОЛИО всегда
mock. Не направлять на application/production БД. Наличие теста не означает,
что миграция проверена на production-версии MariaDB.

Синтетический JSON для frontend можно получить из `FolioProfitScopeReportTest`
через `-Dfolio.profit.scope.fixture.output=/tmp/folio-profit-scope-response.json`.
Это сериализация настоящего Java DTO с тестовыми источниками, не live-расчёт.
