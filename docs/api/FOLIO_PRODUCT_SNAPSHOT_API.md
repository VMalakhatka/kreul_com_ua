# Снимки товаров ФОЛІО и экономические показатели

## Назначение

Сервис читает склад ФОЛІО без изменения документов и учётных цен и публикует
согласованный снимок в MariaDB. Он решает две разные задачи:

1. обнаруживает новые, изменённые и физически удалённые карточки/движения;
2. заранее рассчитывает экономические показатели товара за 12–36 месяцев;
3. с schema v5 сохраняет компактную историю физического наличия по дням.

Карточки и метрики строятся по ключу `sourceDatabase + warehouseId + sku`.
Второй слой сохраняет активную проекцию строк движения за горизонт снимка по
ключу `sourceDatabase + warehouseId + movementRecno`. Предыдущее поколение
движений заменяется только внутри успешной MariaDB-транзакции.

## Запуск

```http
POST /admin/folio/accounting-prices/snapshot/refresh
Content-Type: application/json

{
  "warehouseId": 5,
  "horizonMonths": 24
}
```

Параметры:

- `warehouseId` — обязателен;
- `horizonMonths` — необязателен, допустимо `12..36`, по умолчанию `24`.

Ответ `202 Accepted` означает только принятие фоновой задачи. Результат нужно
получать через:

```http
GET /admin/folio/accounting-prices/snapshot/status
```

Фазы: `QUEUED`, `SOURCE_CAPTURE`, `PUBLISHING`, `COMPLETED`, `FAILED`.

После перезапуска Java незавершённое поколение больше не выдаётся как реально
работающее. Пока нового запуска ещё нет, status endpoint возвращает:

```text
running = false
status = INTERRUPTED
phase = RECOVERY_REQUIRED
errorCode = PRODUCT_SNAPSHOT_INTERRUPTED_BY_RESTART
```

Это означает, что активного процесса и MSSQL-сессии снимка уже нет. Оператор
должен повторить `POST .../snapshot/refresh`. Новый запуск помечает старое
`BUILDING` поколение ошибочным, очищает его staging и сохраняет прежний
опубликованный снимок до успешного завершения нового.

Начиная с миграции V10 чтение движений выполняется потоком с пакетом не более
300 строк. Movement facts и рассчитанные метрики сначала записываются в
служебные таблицы `*_stage` по `generation_id`. Java не держит полный список
движений и все месячные метрики склада в heap. После успешного чтения активные
таблицы заменяются из staging одной транзакцией MariaDB. При ошибке staging
удаляется, а прежний активный снимок остаётся доступным.
Во время чтения журнал периодически пишет `movementFacts`, `monthly` и
`heapMiB=used/max`; одновременно продлеваются MariaDB lease и heartbeat
поколения. После неожиданного завершения следующий запуск помечает оставшееся
`BUILDING` поколение ошибочным и очищает его staging.

`analyticsSchemaVersion=2` означает, что поколение содержит movement fact и
разделение `regular/one_off`. После применения миграции V9 старое активное
поколение остаётся с версией `1`; фронт не должен трактовать его новые нулевые
колонки как рассчитанный нулевой спрос.

## Состояния SKU

- `UNVERIFIED` — товар вошёл в первый baseline; корректность его старой
  учётной цены ещё не доказана успешным перерасчётом;
- `NEW` — SKU появился после baseline или вернулся после удаления;
- `DIRTY` — карточка, движение или правило цены изменилось;
- `REMOVED` — карточка исчезла из ФОЛІО;
- `FAILED` — ранее зафиксирована ошибка проверки/перерасчёта; состояние липкое;
- `VERIFIED` — наблюдаемый fingerprint совпал с fingerprint, подтверждённым
  успешным commit и postcheck.

Первый запуск намеренно создаёт `UNVERIFIED`, а не `VERIFIED`.

После успешного point/full/native apply Java снимает fingerprint внутри той же
MSSQL-транзакции после postcheck и публикует `applied_digest` в MariaDB только
после подтверждённого commit. Если текущий `observed_digest` уже совпадает,
строка сразу становится `VERIFIED`; иначе это делает следующий snapshot,
который независимо перечитывает ФОЛІО. Диагностированный apply, который не был
зафиксирован, переводит неподтверждённую строку в `FAILED` и сохраняет
`last_error`. Обычный preview состояния не меняет.

MariaDB и MSSQL не образуют распределённую транзакцию. Если запись
`applied_digest` не удалась после MSSQL commit, перерасчёт остаётся успешным, но
API добавляет warning `SNAPSHOT_CONFIRMATION_NOT_RECORDED`; до следующего
snapshot/повторной проверки товар нельзя считать подтверждённым для
инкрементального прохода.

## Таблицы MariaDB

### Технический слой

- `folio_product_snapshot_generation` — один запуск одного склада;
- `folio_product_snapshot_item` — текущее состояние каждого SKU;
- `folio_product_snapshot_change` — история `BASELINE/ADDED/CHANGED/RESTORED/REMOVED`;
- `folio_product_snapshot_lock` — межпроцессная аренда на время построения.

Fingerprint включает значимые поля карточки `SCL_ARTC`, агрегаты всех
учитываемых не-счетовых движений `SCL_MOVE`, их хронологию/исходные и учётные
суммы, а также правила `SCL_PRIC`. Поэтому обнаруживаются коррекция задним
числом, новое движение и физическое удаление строки.

### Экономический слой

- `folio_product_movement_fact` — активные строки движения за горизонт с
  исходным документом, контрагентом, текущим поставщиком SKU и независимыми
  классификациями движения, спроса, оплаты и сегмента клиента;
- `folio_product_metric_monthly` — помесячные остатки, приходы, продажи,
  себестоимость, валовая прибыль, возвраты, оборачиваемость и GMROI;
- `folio_product_metric_current` — актуальный остаток и готовые показатели
  примерно за 1/3/12/24 месяца;
- `folio_product_metric_alert` — активные и снятые сигналы риска.

Пустые месяцы для карточки без остатка и движения не записываются. Это не
означает пропуск товара: карточка остаётся в `snapshot_item` и
`metric_current`.

### Физическое наличие (schema v5, миграция V13)

`folio_product_availability_monthly` хранит одну строку SKU × физический склад ×
месяц, включая месяцы без движений. `*_stage` содержит строящееся поколение.
Обе таблицы принадлежат product snapshot; публикация и очистка выполняются в той
же MariaDB-транзакции, что и метрики/ACTIVE generation. Ошибка публикации
оставляет предыдущие строки активного склада. Другие склады не удаляются.

Расчёт использует существующий независимый входящий остаток
`NACH_KOLCH + движения до горизонта` и все `affectsStock=true` движения горизонта.
Восстановленный итог сверяется с `physicalQuantity` (абсолютный допуск 0.000001).
Расхождение либо скрытая учётная карточка дают `DATA_INCOMPLETE`, а не оценку
процента. Это реконструкция по текущей версии документов: исправление задним
числом изменит историю при следующем refresh. Совпадение итогов не доказывает
отсутствие взаимно компенсирующих ошибок в исходных документах.

Память ограничена дневными дельтами одного SKU и малым staging-пакетом масок;
полный массив `все товары × все дни` не создаётся. Перед публикацией проверяется
число товаров, для которых построена история. День снятия снимка ещё не окончен:
его движения участвуют в сверке текущего остатка, но его EOD не выдаётся известным.

Состав групп в снимке не хранится. Правила MIN_TVRZAP, структура масок,
ограничения истории и HTTP-контракт описаны в
[инструкции v5](FOLIO_PRODUCT_AVAILABILITY_FRONTEND_V5.md).
Миграция не меняет ФОЛІО и не пересчитывает учётную цену; после деплоя необходимо
последовательно обновить снимки используемых физических складов.

`folio_product_snapshot_item` и `folio_product_metric_current` сохраняют
`current_supplier` из текущего `SCL_ARTC.DOP2_ARTIC` и `supplier_state`.
Это поставщик карточки на момент снимка, а не исторический контрагент документа.
Фактический контрагент строки хранится отдельно в movement fact.

### Независимые классификации движения

- `movement_class` определяет экономический смысл: продажа, возврат, приход,
  перемещение, сборка, брак, внутреннее потребление, реклама, корректировка,
  резерв или неклассифицированное движение;
- `stock_direction` (`IN/OUT/NONE`) определяется техническим движением, а не
  одним `VID_DOC`;
- `demand_mode=ONE_OFF_ORDER` для `*РАЗОВАЯ`; такая продажа остаётся в
  фактической выручке и валовой прибыли, но
  `affects_planning_demand=false`;
- `payment_terms` хранит `PREPAYMENT`, отсрочки `30/60/90/180` дней и другие
  подтверждённые условия. Условия оплаты не изменяют класс и направление
  движения;
- `customer_segment` хранит `RETAIL/NON_RETAIL/UNKNOWN/NOT_APPLICABLE`.
  Сырой односимвольный `_PARTNER.MY_ORGANIZ` сохраняется отдельно как
  `organization_type`. Не подставлять сюда `SCL_NAKL.MY_ORGANIZ`: это полное
  имя получателя документа, а не тип контрагента. Если партнёр не найден,
  `organization_type` остаётся пустым, а сегмент — `UNKNOWN`;
- `current_supplier` — текущий поставщик карточки на дату поколения;
  `counterparty_*` — исторический контрагент конкретного документа.

Финансовые поля `sales_*` включают регулярные и разовые продажи. Поля
`regular_*` используются для покрытия запасом, дефицита и планирования заказа.
Поля `one_off_*` показываются отдельно. Разовый заказ не делает товар ликвидным
и не увеличивает рекомендацию повторной закупки.

## Подтверждённые формулы и границы

- продажа подтверждается классификатором по техническому типу, возврату,
  контрагенту и специальным операциям; перемещение, сборка, брак, расходники,
  реклама и корректировка не считаются продажей только потому, что это расход
  `Р`;
- выручка: `SCL_MOVE.SUM_PREDM`;
- себестоимость: `SCL_MOVE.SUM_UCHET`;
- валовая прибыль: `SUM_PREDM - SUM_UCHET`;
- возвраты сохраняются отдельно и не маскируются обычной продажей;
- текущая доступность: `KON_KOLCH - REZ_KOLCH`;
- капитализация: `UCHET_SUM`, а при его нулевом значении —
  `KON_KOLCH * UCHET_CENA`;
- средний капитал за месяц в первой версии — среднее начальной и конечной
  учётной стоимости месяца;
- оборачиваемость: `себестоимость продаж / средний капитал`;
- GMROI: `валовая прибыль / средний капитал`;
- покрытие: `доступный остаток / средняя регулярная продажа за день`; разовые
  заказы из знаменателя исключены.

Показатели `30/90/365/730` строятся из месячных корзин, поэтому это
оперативная аналитика, а не бухгалтерский отчёт с точностью до отдельного дня.
Потерянные продажи из данных ФОЛІО не выводятся: отсутствие остатка не
доказывает неслучившийся спрос.

## Сигналы

- `DATA_ISSUE` — отрицательный остаток либо ненулевой остаток с нулевой
  учётной ценой после появления движений;
- `STOCKOUT` — есть продажи, но доступного остатка нет;
- `LOW_MARGIN` — отрицательная валовая прибыль;
- `ONE_OFF_ONLY_STOCK` — есть остаток, но недавний спрос состоит только из
  разовых заказов;
- `DEAD_STOCK` — товар лежит, последняя продажа старше 180 дней;
- `OVERSTOCK` — расчётное покрытие больше 180 дней;
- `DEMAND_FADING` — продажи текущего календарного месяца меньше половины
  предыдущего месяца при достаточном предыдущем спросе;
- `NEW` в текущей метрике — нормальная новая карточка без движений и не ошибка.

## Безопасность и эксплуатация

- ФОЛІО читается внутри `REPEATABLE_READ`; MariaDB публикуется отдельной
  атомарной транзакцией;
- используется тот же application lock, что и Java-перерасчёт учётных цен;
- настольная ФОЛІО этот lock не соблюдает, поэтому первый большой baseline
  лучше запускать вне активной работы менеджеров;
- snapshot поддерживает среднюю учётную цену `SCLAD_R.N_2=1000`
  (`includeTax=false`) и `SCLAD_R.N_2=1100` (`includeTax=true`), только при
  `N_4 IS NULL`;
- режим учёта находится в `SCLAD_R.N_2`; в `NSF_ORG` такого поля нет;
- при ошибке предыдущие опубликованные данные MariaDB остаются доступными;
- миграция V9 не заполняет историю задним числом: после deploy нужен один новый
  полный snapshot каждого участвующего склада; удалять старые поколения и
  сбрасывать состояния `VERIFIED/DIRTY` не нужно;
- endpoint не запускает `I_UCHET_TOVAR` и не изменяет ФОЛІО.

Для неподдержанного режима terminal status дополнительно возвращает:

```json
{
  "status": "FAILED",
  "errorCode": "PRODUCT_SNAPSHOT_ACCOUNTING_MODE_UNSUPPORTED",
  "accountingRawCode": 1001,
  "accountingMode": "LIFO",
  "recommendation": "Exclude this warehouse ...; do not change N_2 automatically"
}
```

Фронт должен показать эти поля как диагностику конфигурации и не предлагать
оператору автоматически исправлять `SCLAD_R.N_2`.

Настройки:

```properties
LAVKA_FOLIO_PRODUCT_SNAPSHOT_ENABLED=true
LAVKA_FOLIO_PRODUCT_SNAPSHOT_HORIZON_MONTHS=24
LAVKA_FOLIO_PRODUCT_SNAPSHOT_QUERY_TIMEOUT_SECONDS=600
LAVKA_FOLIO_PRODUCT_SNAPSHOT_LOCK_TIMEOUT_MS=5000
LAVKA_FOLIO_PRODUCT_SNAPSHOT_LEASE_SECONDS=3600
```

Дата и время снимка используют общую бизнес-зону ФОЛІО
`lavka.folio.balance-snapshot.zone` (по умолчанию `Europe/Kyiv`).
