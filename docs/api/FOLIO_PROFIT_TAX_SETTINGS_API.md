# Постоянные налоговые фирмы — Java contract 2026-09-22.1

## Область и хранение

Настройки относятся к отчёту «Прибыль Лавки», не к ФОЛИО и не к налоговому законодательству.
Одна постоянная конфигурация на application MariaDB (`wpDataSource`), **без дат действия**.
Миграция [V17](../../src/main/resources/db/wp/migration/V17__folio_profit_tax_settings.sql)
создаёт `folio_profit_tax_settings`: singleton `id=1`, `version`, JSON-массивы
`retail_firm_codes` / `wholesale_firm_codes`, `updated_at` (UTC). В ФОЛИО ничего не записывается.
GET при пустой таблице возвращает defaults версии 0 и не создаёт строку.
Ошибка чтения/повреждённая сохранённая конфигурация **не заменяются defaults**.

Endpoint доступен только через существующий закрытый `/admin` perimeter/VPN/proxy.
Отдельной финансовой авторизации в Java-модуле нет. WordPress проверяет capability
и nonce server-side; браузер не должен обращаться к Java напрямую.

## GET /admin/folio/profit-report/tax-settings

Ответ без envelope:

```json
{
  "version": 0,
  "retailFirmCodes": ["МИХНФОП", "МАЛАФОП"],
  "wholesaleFirmCodes": ["КУЗНФОП", "КОНДФОП"]
}
```

## PUT /admin/folio/profit-report/tax-settings

Полная замена обоих списков, тело той же формы. `version` — версия последнего GET;
первая успешная запись возвращает 1, последующие увеличивают её на 1.
Это optimistic compare-and-set одним SQL statement; конкурентный первый INSERT
также имеет ровно одного победителя. Даже сохранение тех же списков повышает версию.

- Обязательны version и оба массива. `[]` допустим и отключает распределение пула.
- Не более 100 кодов в каждом списке; код 1–64 Unicode букв/цифр, `_` или `-`.
- trim/uppercase. Исторические ASCII `MALAFOP` / `KONDFOP` нормализуются в
  `МАЛАФОП` / `КОНДФОП`, чтобы одна фирма не попала в два пула через alias.
- Дубликат после нормализации: HTTP 400 `PROFIT_TAX_SETTINGS_INVALID`.
- Пересечение списков: HTTP 400 `PROFIT_TAX_FIRM_OVERLAP`.
- Нет обязательного значения/неверный список или версия: HTTP 400
  `PROFIT_TAX_SETTINGS_INVALID`; malformed JSON / дробная, строковая или
  не помещающаяся в Long версия отклоняется общим HTTP 400 JSON handler.
- Устаревшая версия: HTTP 409 `PROFIT_TAX_SETTINGS_VERSION_CONFLICT`.
  Прочитать настройки заново и дать пользователю разрешить конфликт, не перезаписывать автоматически.
- Потеря ответа не доказывает отсутствие сохранения. После транспортной/DB ошибки
  сделать GET и сверку версии/обоих списков. Не повторять PUT автоматически.

## Расчёт и фиксация версии кампании

[Saved calculate](FOLIO_PROFIT_SAVED_REPORTS_API.md) принимает дополнительный
optional `taxSettingsVersion` (неотрицательное JSON целое):

```json
{
  "requestId": "856127de-bf07-4909-9e25-291151b69daa",
  "kyivEmployeeCount": 4,
  "odesaEmployeeCount": 3,
  "taxSettingsVersion": 2
}
```

WordPress делает один GET настроек перед запуском диапазона и передаёт **одну и ту же
версию** всем месяцам кампании. Для нового requestId Java проверяет ожидаемую версию
**до резервирования ревизии и чтения ФОЛИО**. При несовпадении возвращает 409 с кодом
выше; ревизия FAILED/RUNNING не создаётся. Кампанию следует остановить и предложить
новый запуск с явно принятыми настройками, не переключать их посреди диапазона.

После проверки Java использует один immutable снимок списков/версии до конца месяца.
PUT во время расчёта не меняет уже захваченную конфигурацию. Проверка не блокирует
сохранение настроек на всё время чтения ФОЛИО; следующий месяц обнаружит смену версии.
Без поля (старые клиенты) каждый новый расчёт использует текущие настройки.
Live GET `/profit-report` и `/audit` также захватывают текущие настройки один раз.

Lookup существующего requestId выполняется **раньше** проверки текущей версии.
Тот же UUID и payload возвращает историческую ревизию без ФОЛИО и без чтения настроек,
даже если версия уже изменилась. Другая версия в payload с тем же UUID —
`PROFIT_REQUEST_ID_CONFLICT`. Отсутствующее поле не меняет legacy request_hash.

## Бизнес-правила и аудит

1. Прежний классификатор сначала распознаёт налог по точному коду `НАЛОГИ`.
   Само упоминание фирмы не превращает аренду/зарплату в налог.
2. Периоды, M−1/M/M+1 и явные маркеры вне окна не изменены. Дат действия фирм нет:
   учитываются **все** подходящие документы выбранного месяца, не один последний.
3. Код фирмы ищется целым токеном в `purposeCode`, `expenseCode`, `name`,
   `documentClass`, без учёта регистра. Не искать фирму в примечании периода.
   Legacy ASCII aliases поддерживаются только для соответствующего настроенного кода.
4. Ровно одна найденная фирма: retail → по каждому документу работники/legacy share,
   wholesale → полностью Киев. HALF_UP до копеек по каждому документу; Киев получает
   остаток после Одессы. Не округлять один общий пул вместо документов.
5. Нет совпадений или найдено несколько разных настроенных фирм → `UNALLOCATED`.
   Сумма и документы сохраняются; влияние на прибыль 0, предупреждение
   `UNKNOWN_TAX_POOL`, `complete=false`. Остальные разделы продолжают считаться.
6. Платёж учитывается один раз по `paymentId`, не номеру документа. Идентичные копии
   убираются; конфликтующие копии одного ID дают EXPENSES UNAVAILABLE с кодом
   `PROFIT_PAYMENT_DUPLICATE_CONFLICT`, неизвестные итоги не становятся нулями.

## Новый report.taxDetails

```json
{
  "settings": {
    "version": 0,
    "retailFirmCodes": ["МИХНФОП", "МАЛАФОП"],
    "wholesaleFirmCodes": ["КУЗНФОП", "КОНДФОП"]
  },
  "retailAmount": "21.00",
  "wholesaleAmount": "49.00",
  "unallocatedAmount": "16.00",
  "unallocatedDocuments": []
}
```

В этом схематическом примере массив документов опущен для краткости; реальный ответ
при ненулевой нераспределённой сумме содержит соответствующие `DocumentLine`.
Все суммы — UAH до городского распределения. `unallocatedDocuments` — **полный**
реестр выбранных UNALLOCATED-налогов, независимо от `includeDocuments` и лимита
обычного audit. Здесь нет truncation; сохраняются также предварительно включённые
документы с проблемным периодом и их periodStatus. Поля документа: ID/номер/дата,
resolvedMonth, stream, склад, исходные признаки, суммы/валюта/курс и allocations.
`accountingTreatment=UNALLOCATED`, `expenseLineId=SHARED_TAX_UNALLOCATED`,
`profitImpact=kyivAllocation=odesaAllocation=0`, `includedInProfit=false`.

**Недоступный источник — не пустой реестр:** если EXPENSES UNAVAILABLE, все три суммы
null и `unallocatedDocuments=[]`; показывать «данные недоступны», не «неизвестных налогов нет».
Если настройки недоступны, `taxDetails.settings=null`, `sections.TAX_SETTINGS=UNAVAILABLE`,
expense-разделы недоступны, прочие независимые разделы продолжаются. Ошибка настройки
для saved calculate обнаруживается до резервирования новой ревизии.

Legacy `controls.taxPools` сохраняет ключи `MALAFOP` (вся розница), `KONDFOP`
(весь опт), `UNKNOWN` (UNALLOCATED). Это совместимые имена пулов, не фильтры единственной фирмы.
Stable lineId `KYIV_TAX_MALAFOP`, `ODESA_TAX_MALAFOP`, `KYIV_TAX_KONDFOP`,
`ODESA_TAX_KONDFOP` неизменны; ОПТ Одессы 0. `filters.purposeCodes` содержит
**реальные списки из taxDetails.settings**. Для этих четырёх строк `[]` означает
отключённый пул, а не «все фирмы».

## История, проверки и выкладка

Полный DTO, включая `taxDetails.settings`, хранится в неизменяемом JSON ревизии V15.
PUT не изменяет старые отчёты; старый JSON без taxDetails возвращает null, не defaults.
Для отображения/экспорта старой ревизии запрещено подставлять актуальный GET настроек.
Миграция V17 нужна только для постоянной конфигурации, не для переписывания истории.

Профильные unit/MVC-тесты: `mvn -Dtest='FolioProfit*Test' test`.
`FolioProfitTaxSettingsMariaDbTest` — opt-in только `127.0.0.1:13370` с
`-Dfolio.profit.tax.test.port=13370` и приватным `WP_TAX_TEST_PASSWORD`; создаёт и удаляет
собственную случайную БД `profit_tax_test_*`, проверяет V17 migrate/validate/repeat,
Unicode, persistence и конкурентный первый INSERT/UPDATE. Не направлять на приложение.
JSON fixture генерирует `FolioProfitTaxReportTest` через
`-Dfolio.profit.tax.fixture.output=/private/tmp/folio-profit-tax-settings-fixture.json`.
Он полностью синтетический: 6 уникальных налогов, розница21, опт49, UNALLOCATED16;
в расходы Киева61, Одессы9. Это тест контракта, не сверка живых документов.

Для запуска необходим новый Java deploy с V17; он отдельно под контролем оператора.
Ни наличие кода, ни успешные тесты не означают, что миграция применена в production.

Проверено 22.09.2026: 104 unit/MVC/история/периоды теста прошли вместе с package;
5 opt-in DB-тестов в этом прогоне пропущены. Отдельно 2 теста V17 на изолированной
MariaDB 10.6.19 прошли (включая CAS гонки); тестовые базы удалены, контейнер остановлен.
Живые документы ФОЛИО и production не читались и не изменялись.
