# Физическое наличие и отсутствие товара: контракт Java → WordPress v5

Обновлено: 2026-09-06. Владелец: Java product snapshot / product analytics.
Исходное требование: WordPress `docs/api/FOLIO_PRODUCT_AVAILABILITY_BACKEND_TASK.md`.
Фронтенд в рамках этой реализации не изменялся.

## Включение после деплоя

1. Деплоить Java с успешной Flyway V13
   `V13__folio_product_availability_history.sql` в MariaDB WordPress.
2. По очереди выполнить существующий
   `POST /admin/folio/accounting-prices/snapshot/refresh`
   с `{"warehouseId":1,"horizonMonths":36}` для каждого используемого физического
   склада. Дождаться `ACTIVE / COMPLETED / analyticsSchemaVersion=5`.
   SQL-установка процедур в ФОЛІО и apply учётных цен для этого не нужны.
3. Вызвать `POST /admin/folio/product-analytics/capabilities` с выбранными
   `sourceDatabase` и `warehouseIds`. До `compatibleGeneration=true`,
   `filters.dailyStockout.supported=true` и
   `features.availability.supported=true` процент отсутствия не показывать.
4. Проверить несколько товаров по движениям ФОЛІО, затем включить экран/экспорт.

Новые маски не появятся от одной миграции. Если часть складов не обновлена,
смешивание версий блокируется `INCOMPATIBLE_GENERATIONS`; если все старые —
`ANALYTICS_SCHEMA_TOO_OLD`. Отсутствующий ACTIVE снимок — `SNAPSHOT_NOT_READY`.
Это ошибки запроса целиком, не нулевое наличие. Неподдерживаемые учётные режимы
складов по-прежнему исключаются: эта доработка не меняет `N_2`.

## Что означает показатель

Basis только `PHYSICAL_END_OF_DAY`: физический остаток в конце завершённого
календарного дня. История резервов не заявлена. Внутридневное отсутствие,
после которого к вечеру был приход, в этой версии не видно.

- остаток > 0 — доступен;
- остаток <= 0 — отсутствует; отрицательный дополнительно даёт warning;
- текущий `MIN_TVRZAP=0` — склад для этого SKU неприменим;
- текущий `MIN_TVRZAP>0`, в том числе дробный — применим;
- `MIN_TVRZAP=NULL` или < 0 — политика не подтверждена.

Порог MIN определяет применимость, а не доступность: при MIN=5 и остатке=1
товар доступен. MAX не участвует в проценте. Сетевой запрет закупки по складу 7
остаётся отдельным `networkOrderPolicy`: он не исключает автоматически другие
физические склады из истории наличия.

Истории MIN и даты включения товара в ассортимент нет. Поэтому ко всему периоду
применяется **текущая** политика с warning `CURRENT_POLICY_APPLIED_TO_PERIOD`.
Для новой карточки нельзя утверждать, что она должна была продаваться до её
появления. Это ограничение отображать оператору. Для гарантированно исторической
ассортиментной оценки потребуется отдельная история политики/даты ввода SKU.

Группа доступна в день, если остаток > 0 хотя бы у одного применимого участника.
Пример 30 дней: один склад доступен дни 1–20, другой дни 21–30. Физические
проценты 66.67 и 33.33, группа 100.00, отсутствие группы 0 дней. Не складывать
и не усреднять дни или проценты участников.

## Запрос: существующий POST /admin/folio/product-analytics/query

```json
{
  "sourceDatabase": "Paint_Ua",
  "warehouseIds": [1, 7],
  "period": {"from": "2026-08-01", "to": "2026-08-31"},
  "calculation": {
    "abcBasis": "GROSS_PROFIT",
    "includeReturns": true,
    "availability": {
      "enabled": true,
      "basis": "PHYSICAL_END_OF_DAY",
      "minimumStockEligibility": "CURRENT_POLICY_GT_ZERO",
      "presentation": "WAREHOUSES_AND_GROUPS",
      "warehouseGroupsRevision": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "warehouseGroups": [
        {"code": "KYIV_SHARED", "name": "Київ", "warehouseIds": [1, 7],
         "availabilityMode": "ANY_ELIGIBLE_MEMBER"}
      ],
      "groupCode": "KYIV_SHARED",
      "filter": {"stockoutPercentFrom": 10, "availabilityStatus": ["MEASURED"]}
    }
  },
  "sort": [{"field": "stockoutPercent", "direction": "DESC"}],
  "page": {"size": 50, "cursor": null}
}
```

Ревизия из примера — заглушка. WordPress передаёт настоящий SHA-256 текущей
нормализованной глобальной конфигурации taxonomy `location` /
`lavka_folio_warehouses`. Java проверяет формат 64 hex, возвращает его lowercase;
не читает taxonomy самостоятельно и не подменяет её своей конфигурацией.

Группы должны быть непустыми, с уникальным `code` (1–64 ASCII буквы/цифры/`_-`),
имя до 200 символов. Все участники входят в `warehouseIds` верхнего уровня.
Пересечение разных групп запрещено. Повторы ID внутри группы убираются, ID
сортируются, группы сортируются по коду. Неизвестный mode/basis/presentation —
HTTP 400 `INVALID_AVAILABILITY`. Ревизия обязательна только при наличии групп.
Для фильтра по одному складу группы/ревизию можно не передавать.

`enabled=false` или отсутствие блока сохраняет прежний расчёт без наличия.
Запрос фильтра при `enabled=false` отклоняется. Старые сценарии можно выполнять
без изменения; блок добавляется WordPress только при включении новой функции.
Состав групп не сохранять в сценарии: разрешать коды из актуальной глобальной
настройки при каждом новом выполнении.

### Контекст и отборы

Внутри `calculation.availability` выбрать **одно**:

- `warehouseId: 1` — физический склад;
- `groupCode: "KYIV_SHARED"` — переданная группа;
- ни одного: при одном выбранном складе он используется автоматически;
  при нескольких общая строка имеет `CONTEXT_REQUIRED`, без числовых значений.

Детализация всех физических складов и всех переданных групп возвращается
независимо от выбранного общего контекста. Неявного объединения всего списка нет.

Вложенный `filter` поддерживает:

| Поле | Правило |
|---|---|
| `availabilityPercentFrom / availabilityPercentTo` | включительные границы 0..100 |
| `stockoutPercentFrom / stockoutPercentTo` | включительные границы 0..100 |
| `availabilityStatus` | список точных статусов ниже, OR внутри списка |

Между заданными ограничениями — AND. Пустой список статусов не ограничивает.
Числовой фильтр автоматически исключает неизвестные и неприменимые значения,
поскольку их проценты NULL. Для фильтра/сортировки контекст обязателен.
Верхнеуровневый `sort[].field` расширен значениями `availabilityPercent`,
`stockoutPercent`, `availabilityStatus`; direction ASC/DESC. NULL проценты идут
после чисел; SKU используется для однозначного порядка. Отбор и сортировка
выполняются **в MariaDB до пагинации**, включая total/productCount и ABC-базу.

Фильтры экономических движений (операция, продажи/разовые, контрагент и т.д.)
не изменяют физическую историю. Для неё уже учтены все stock-affecting движения,
включая перемещения и корректировки. Нельзя вычесть перемещения из наличия,
даже если их правильно исключили из коммерческого спроса.

## Ответ

`rows[].availability` — выбранный контекст. `warehouseBreakdown[].availability`
— каждый физический склад; `warehouseGroupBreakdown[]` содержит `code`, `name`,
`warehouseIds`, `availabilityMode` и `availability` каждой группы.
`context.warehouseGroupsRevision` и `appliedFilters.calculation.availability`
содержат фактически применённую ревизию/нормализованные группы.

Поля каждого объекта `availability`:

| Поле | Значение |
|---|---|
| `status`, `basis` | качество результата и PHYSICAL_END_OF_DAY |
| `eligible` | true для MEASURED, false для NOT_APPLICABLE, иначе null |
| `minimumStock` | текущий MIN для физического склада; для группы null |
| `periodDays` | число календарных дней в запросе, обе даты включительно |
| `eligibleDays` | periodDays для MEASURED, 0 для NOT_APPLICABLE, иначе null |
| `availableDays`, `stockoutDays` | подтверждённые дни, только MEASURED |
| `availabilityPercent`, `stockoutPercent` | дни / periodDays × 100, два знака; иначе null |
| `warnings` | CURRENT_POLICY_APPLIED_TO_PERIOD, NEGATIVE_PHYSICAL_STOCK, INCOMPLETE_DAILY_HISTORY |

| Статус | Поведение UI |
|---|---|
| `MEASURED` | показывать дни и проценты |
| `NOT_APPLICABLE` | «Не входить до асортименту»; не показывать 0% или 100% |
| `POLICY_NOT_CONFIRMED` | «Не підтверджено мінімальний запас» |
| `DATA_INCOMPLETE` | «Недостатньо даних»; не вычислять приблизительно |
| `PERIOD_OUTSIDE_HORIZON` | нужен другой период/более глубокий снимок |
| `SNAPSHOT_NOT_READY` | обновить снимок отсутствующего склада |
| `CONTEXT_REQUIRED` | выбрать физический склад либо группу для общей колонки |

Если у SKU нет карточки на одном из выбранных физических складов, его
warehouseBreakdown всё равно присутствует, `metrics/orderPolicy` могут быть null,
availability — DATA_INCOMPLETE. Такой склад не считается автоматически MIN=0.
Для группы неполный/неизвестный применимый участник делает результат неполным,
даже если другой участник доступен: первая версия выбирает консервативное правило.
При всех исключённых участниках результат NOT_APPLICABLE.

API сохраняет строгую проверку периода всего экономического отчёта: вне общего
горизонта ACTIVE складов запрос целиком отклоняется HTTP 400 `INVALID_PERIOD`
с `earliestAllowed/latestAllowed`; метрики из неполного периода не выдаются.
День `asOf` снимка ещё не является завершённым EOD. Включение его в период
даёт DATA_INCOMPLETE для применимого SKU. Для процентов выбирать `to` не позднее
минимальной `asOf` всех участников **минус один день**. Каждый склад может иметь
свою дату снимка; общая история групп ограничена их общим завершённым периодом.

`metrics.coverageDays` и экономические alerts остаются отдельными показателями.
Не смешивать качество наличия со статусами учётной проверки
UNVERIFIED/NEW/DIRTY/FAILED/VERIFIED/REMOVED.

## Экспорт и повтор запроса

CSV/XLSX собирает PHP по server-side `/query`, не браузер и не MS SQL.
Следующая страница использует `nextCursor` и **тот же** запрос/конфигурацию.
Курсор v5 привязан к фильтрам, периоду, сортировке, группе/ревизии и всем
поколениям выбранных и справочных складов (политика7/транспорт9).
Изменение входов даёт 409 `ANALYTICS_CURSOR_EXPIRED`. Сбросить выгруженные части
и предложить повторить экспорт, не продолжать другим поколением. Курсор до v5
не использовать. Внутри одной страницы используется repeatable-read MariaDB.

В экспорт включать статус вместе с числами, basis, предупреждения, физические
и групповые детали, период, generation IDs и warehouseGroupsRevision. NULL не
превращать в 0. Изменение состава группы не требует нового product snapshot.

## Физическое хранение и контроль качества

V13: `folio_product_availability_monthly` и `folio_product_availability_monthly_stage`.
Строка содержит generation_id/source_database/warehouse_id/sku/month_start и:

- `known_mask`: подтверждённые завершённые дни;
- `available_mask`: дни с физическим остатком > 0;
- `negative_mask`: дни отрицательного остатка;
- `quality`: RECONCILED либо DATA_INCOMPLETE;
- `reconciliation_difference`: восстановленный текущий остаток минус физический.

Бит 0 — день 1, бит 30 — день 31. Все маски хранятся в BIGINT; биты вне месяца
не используются. Дни без движений наследуют остаток; нулевая маска AVAILABLE при
полной KNOWN означает настоящее отсутствие. Нулевая KNOWN — неизвестность.
При расхождении входящего остатка + всех дельт с текущим остатком маски KNOWN
сбрасываются. Таблица хранит не количества по дням, а каноническое состояние
наличия — достаточное для точных объединений. Для карточки без движений месяцы
также записываются. До 36 строк на SKU за горизонт, а не до 1096 daily rows.

Публикация масок, остальных проекций и ACTIVE поколения атомарна. При ошибке
сохраняется прежний снимок. ФОЛІО читается существующим согласованным capture;
обновления документов, остатков и учётных цен не выполняются. Read-only capture
может удерживать блокировки чтения; это не обещание отсутствия нагрузки.

## Проверки и приёмка

Автотесты: реконструкция, отсутствие движений, отрицательный остаток, високосный
день, незавершённый день, расхождение остатков; валидация групп и курсоров.
Изолированный интеграционный тест MariaDB содержит 10 синтетических SKU ×
2 склада: complementary masks, MIN=0/null, неполная история/карточка,
фильтрация до пагинации, частичный месяц и откат неуспешной публикации.

Тест запускается только явно с `FOLIO_AVAILABILITY_TEST_PORT`, использует
`127.0.0.1`, пустой пароль и БД `availability_test` в одноразовом контейнере.
Не направлять его на рабочую MariaDB. Unit-тесты внешних БД не требуют.

2026-09-06 выполнена дополнительная автоматическая сверка на архивной Paint_Rus:
10 общих SKU складов 9/20, июнь 2014 (фактический последний месяц истории этой
копии), 20 карточек, 600 дневных остатков. Независимый SQL суммировал движения
от начального остатка до каждой даты; Java строила историю от входящего остатка
месяца и дневных дельт. Все 20 итоговых остатков сошлись и все 600 состояний
совпали. Guard `strictIsolation=true`, SQL Server 8.00.760 / compatibility80,
результат `ROLLED_BACK`, `@@TRANCOUNT` после 0. Бизнес-таблицы не изменялись,
Paint_Ua не использовалась. Проверка файла результата воспроизводится offline
тестом `FolioAvailabilityLabEvidenceTest` с `FOLIO_AVAILABILITY_LAB_EVIDENCE`;
сырые данные в Git не включаются. Эта проверка старой копии не доказывает
полноту документов или производительность всех складов Paint_Ua.

Ручной gate перед использованием в закупочных решениях: 10 SKU на двух
физических складах сверить с документами и остатками ФОЛІО на контрольные даты,
включая приход/расход в один день, перемещение, отрицательный остаток и новый
товар. Автоматические синтетические проверки не заменяют эту операторскую сверку.

Для работы фронту подключить `lavka-woo` и `folio-inventory-profit-planning`;
при проверке источника — `work-with-folio-mssql`. Основной общий контракт:
[FOLIO_PRODUCT_ANALYTICS_API.md](FOLIO_PRODUCT_ANALYTICS_API.md).
