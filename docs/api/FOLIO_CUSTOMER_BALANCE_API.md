# API баланса с клиентом (аналог 7-го отчёта ФОЛИО)

Подробные требования к frontend, внешний вид в стиле старого Excel-отчёта, TypeScript-типы и правила отображения находятся в [`FOLIO_CUSTOMER_BALANCE_FRONTEND.md`](FOLIO_CUSTOMER_BALANCE_FRONTEND.md).

Понятная инструкция для менеджеров, в каком документе и поле ФОЛИО ставить `РЕЛ` и `ПРД`, находится в [`FOLIO_BALANCE_MARKERS_FOR_MANAGERS.md`](../business/FOLIO_BALANCE_MARKERS_FOR_MANAGERS.md).

## Назначение и источник расчёта

Endpoint формирует сверку с одним клиентом по логике штатного 7-го отчёта ФОЛИО и рассчитывает итоговые показатели из Excel-шаблона `docs/Отчеты Фолио/7Й чистый.xls`.

Источники, изученные перед реализацией:

- `docs/Отчеты Фолио/Сверка с покупателем 7й отчет.doc` — настройка и состав 14 колонок;
- `docs/Отчеты Фолио/7й пояснение для покупателей.doc` — бизнес-смысл итогов;
- `docs/Отчеты Фолио/7Й чистый.xls` — точные формулы итогов, отсрочки, предоплаты и просроченной отсрочки;
- `dbo.I_DOLG_DOC` — штатная процедура ФОЛИО, подтверждённая read-only разбором определения Paint_Ua.

API не пишет в ФОЛИО. Процедура создаёт только локальные временные таблицы и читает активный контур с `NOLOCK`.

Знаки и порядок строк сверены с выгрузкой штатного 7-го отчёта от 2026-08-13: входящие банк/касса возвращаются положительными суммами, а внутри одной даты платёжные документы идут перед накладными.

Денежные значения старых полей `float` округляются на границе API до двух знаков, чтобы в JSON не появлялись артефакты наподобие `-9284.9800000065`.

## Endpoint

```http
GET /admin/folio/customer-balance
```

Пример:

```http
GET /admin/folio/customer-balance?partnerShortName=БОНД АНН&dateFrom=2026-01-01
```

За весь доступный период:

```http
GET /admin/folio/customer-balance?partnerShortName=БОНД АНН
```

Параметры:

| Параметр | Обязательный | Правило |
|---|---:|---|
| `partnerShortName` | да | точное краткое имя `_PARTNER.N_USER`, не полное имя; максимум 8 символов |
| `dateFrom` | нет | начальная дата отчёта в ISO-формате `yyyy-MM-dd`; без параметра отчёт строится за весь доступный период |
| `warehouseIds` | нет | повторяемый query-параметр; без него выбираются **все склады**, как требует инструкция 7-го отчёта |
| `includeServicePayments` | нет | соответствует `I_DOLG_DOC.Show_zv`; по умолчанию `true` |

`dateTo` снаружи не принимается: конечная дата отчёта всегда равна текущей дате Java-сервера. Эта же текущая дата используется для определения действующей и просроченной отсрочки. Если `dateFrom` не передана, backend использует минимальную дату SQL Server `1753-01-01`, то есть диапазон равен всему доступному активному периоду до сегодня.

Ограничение старой процедуры: `dateTo` преобразуется в полночь и сравнивается через `<=`. Большинство документов ФОЛИО хранится на `00:00:00`, но запись с ненулевым временем в конечный день может не попасть в штатный отчёт. API сообщает об этом предупреждением `LEGACY_DATE_TO_MIDNIGHT`, а не изменяет незаметно каноническую логику процедуры.

Пример выбранных складов:

```http
GET /admin/folio/customer-balance?partnerShortName=БОНД АНН&dateFrom=2026-01-01&warehouseIds=7&warehouseIds=1
```

Для списка складов применяется `mode_multi=2`: документ включается, только если все его строки находятся в выбранном наборе. Для канонической сверки список не передавать — инструкция требует все склады.

## Бизнес-формулы отчёта

Обозначения совпадают с колонками шаблона:

```text
accountingBalance = openingBalance
                    + expenseTotal
                    - receiptTotal
                    - bankPaymentTotal
                    - cashPaymentTotal

deferredAmount = сумма H,
                 если basis начинается с "РЕЛ"
                 и controlDate > текущей даты

prepaymentAmount = сумма J + K, если note начинается с "ПРД"

overdueDeferredAmount = сумма H,
                        если basis начинается с "РЕЛ"
                        и строка уже не относится к будущей отсрочке

commonDebt = accountingBalance + prepaymentAmount

payableNow = commonDebt - deferredAmount
```

`commonDebt` не включает предоплату как погашение старого долга: платёж с `ПРД` сначала попадает в штатные колонки оплаты, затем его влияние исключается прибавлением `prepaymentAmount`. Сама предоплата остаётся отдельной зарезервированной суммой на будущую поставку.

В старом Excel-шаблоне техническая формула действующей отсрочки проверяла только будущую контрольную дату. Это даёт ложную отсрочку для обычных накладных, потому что `CONTRLDATE` в них не является контролируемым признаком. Бизнес-инструкция имеет приоритет: без префикса `РЕЛ` в «Основании» накладная не является ни действующей, ни просроченной отсрочкой.

Excel использовал `DAYS360()` и извлекал год из текстовой даты. API сравнивает настоящие календарные даты, но дата применяется **только вместе с бизнес-маркером `РЕЛ`**. Действующая отсрочка существует, когда `basis` начинается с `РЕЛ` и `controlDate > текущей даты`. В день наступления срока сумма уже не считается будущей отсрочкой.

`overdueDeferredAmount` — справочная сумма накладных с просроченным маркером `РЕЛ`. Она уже входит в `commonDebt/payableNow` и повторно к долгу не прибавляется.

## Какие записи нужны для правильного расчёта

### Отсрочка / реализация

Для оператора ФОЛИО: `РЕЛ` ставится в поле **Основание расходной накладной**, не в счёте. Вместе с ним обязательно заполняется поле **Контр.срок**.

| Что | Поле ФОЛИО | Требование | Подтверждение |
|---|---|---|---|
| контрольный срок | `SCL_NAKL.CONTRLDATE` | реальная дата оплаты/сверки | процедура + колонка A шаблона |
| маркер отсрочки/реализации | `SCL_NAKL.OSNOVANIE` | текст должен начинаться с `РЕЛ`, например `РЕЛ Реализация ...` | формула `LEFT(F,3)="РЕЛ"` |
| сумма | `SCL_NAKL.SUM_POR` и штатные строки/распределения | не подменять ручной Java-формулой | `I_DOLG_DOC` |
| дата счёта | `SCL_NAKL.SCH_DATE` | попадает в колонку N | `I_DOLG_DOC` |

Для суммы «на отсрочке/реализации» обязательны **оба** условия:

1. `OSNOVANIE` начинается с `РЕЛ`;
2. `CONTRLDATE` позже даты состояния отчёта.

Одна будущая контрольная дата без `РЕЛ` не является отсрочкой: в обычных накладных это поле не контролируется и не может самостоятельно менять сумму «к оплате».

Когда срок прошёл, но `РЕЛ` не снят, сумма появляется в `overdueDeferredAmount` и включается в текущую задолженность. Когда товар с реализации/отсрочки оплачен и документ больше не нужно контролировать, оператор обязан удалить `РЕЛ` из поля **Основание**, иначе документ продолжит отображаться как просроченный.

### Предоплата

Для оператора ФОЛИО: `ПРД` ставится в поле **Примечание входящего платёжного документа** — банковского или кассового. В самом счёте, расходной накладной или поле «Основание» этот маркер не ставится.

| Что | Поле ФОЛИО | Требование | Подтверждение |
|---|---|---|---|
| маркер | `SCL_PLAT.DOCUMN_POR` | примечание платежа начинается с `ПРД`, например `ПРДПредоплата` | `I_DOLG_DOC.PRIMS_PLAT` + формула `LEFT(M,3)` |
| вид оплаты | `SCL_PLAT.NOT_NAL` | предоплатой может быть как кассовый (`0`), так и банковский (`1`) платёж | бизнес-правило |
| входящий платёж | `SCL_PLAT.TYPE_POR=0` | процедура преобразует его в положительное значение колонки оплаты | код `I_DOLG_DOC` |
| связь оплаты с документом | `SCL_PMOV.UNICUM_PLT → SCL_PLAT`, `SCL_PMOV.UNICUM_NUM → SCL_NAKL` | разнесение должно выполняться штатным механизмом ФОЛИО | процедура и схема |

В исходном Excel-шаблоне обнаружена ошибка: формула `IF(LEFT(Mn,3)="ПРД",Kn,0)` учитывает только кассу. Правильная формула должна учитывать любой платёжный документ:

```text
IF(LEFT(Mn,3)="ПРД", Jn + Kn, 0)
```

API использует исправленное бизнес-правило: если примечание платёжной строки начинается с `ПРД`, в предоплату входит сумма `bankPayment + cashPayment`. Поэтому банковская и кассовая предоплаты обрабатываются одинаково.

Когда предоплаченный товар поставлен и платёж должен участвовать в обычном взаиморасчёте, оператор обязан удалить `ПРД` из поля **Примечание** платёжного документа. Иначе сумма будет продолжать отображаться как зарезервированная предоплата и не будет погашать текущий долг.

Не записывать вручную только `SUM_POR` или только комментарий. На долг также влияют `SCL_PMOV`, `OPLATA_SCH`, `OPLTDATE`, направление платежа и учётность движения; их должен поддерживать штатный workflow ФОЛИО.

### Клиент и склады

- клиент документа: `SCL_NAKL.BRIEFORG = _PARTNER.N_USER`;
- клиент платежа: `SCL_PLAT.ORG_PREDM = _PARTNER.N_USER`;
- для канонического 7-го отчёта выбираются все склады;
- процедура читает активные `SCL_NAKL/SCL_MOVE/SCL_PLAT/SCL_PMOV`, архив автоматически не включается.

## Что ещё нужно подтвердить golden-master сравнением

До объявления API полной заменой штатной печатной формы надо на копии Paint_Rus сравнить один и тот же клиент/период:

1. все 14 колонок и порядок строк;
2. начальное и конечное сальдо;
3. наличный и банковский платёж обоих направлений;
4. частично разнесённую оплату;
5. будущую и просроченную отсрочку;
6. `ПРД` на самостоятельном и связанном платеже — отдельно для кассы и банка;
7. многоскладской документ;
8. поведение архивных документов.

Причина: `I_DOLG_DOC` использует `NOLOCK`, старые `float` и внутреннюю сортировку только по типу документа; API нормализует строки хронологически и поэтому должен быть сверён с конкретной настройкой 7-го отчёта.

# Общий административный отчёт должников

## Endpoint

```http
GET /admin/folio/customer-debtors
```

Endpoint возвращает клиентов, для которых рассчитанная на текущую дату сумма к оплате строго больше заданного порога:

```text
payableNow > minPayable
```

При `minPayable=100.00` клиент с `payableNow=100.00` не входит, а клиент с `100.01` входит.

Пример:

```http
GET /admin/folio/customer-debtors?minPayable=100.00&types=П,Д,К&limit=50&offset=0&sort=payableNow_desc
```

## Параметры

| Параметр | Обязательный | По умолчанию | Правило |
|---|---:|---|---|
| `minPayable` | нет | `100.00` | неотрицательная сумма, не более двух десятичных знаков |
| `q` | нет | пустая строка | поиск подстроки в `_PARTNER.N_USER`, `NAME_USER` или `NAMEP_USER`; максимум 100 символов |
| `types` | нет | `П,Д,К` | список односимвольных кодов `_PARTNER.MY_ORGANIZ`; `all` отключает фильтр типа |
| `limit` | нет | `50` | от `1` до `200` |
| `offset` | нет | `0` | целое число не меньше нуля |
| `sort` | нет | `payableNow_desc` | сейчас поддерживается только `payableNow_desc` |

Период с frontend не передаётся. Endpoint читает активный предварительно рассчитанный снимок за весь доступный активный период от `1753-01-01` до `asOfDate` снимка. Бизнес-дата определяется в зоне `Europe/Kyiv` (настраивается свойством `lavka.folio.balance-snapshot.zone`).

Список больше не запускает `I_DOLG_DOC` последовательно для всех клиентов внутри HTTP-запроса. Поэтому обычный запрос списка не должен упираться в timeout reverse proxy.

## Финансовая логика

`customer-debtors` не содержит второй версии финансовых формул. Оба endpoint используют общий `FolioCustomerBalanceCalculator`:

- `GET /admin/folio/customer-balance` — подробный отчёт одного клиента;
- `GET /admin/folio/customer-debtors` — сводные итоги многих клиентов.

Поэтому сохраняются те же правила знаков, банковских/кассовых платежей, `РЕЛ`, `ПРД`, будущей и просроченной отсрочки:

```text
accountingBalance = openingBalance
                    + expenseTotal
                    - receiptTotal
                    - bankPaymentTotal
                    - cashPaymentTotal

commonDebt = accountingBalance + prepaymentAmount

payableNow = commonDebt - deferredAmount
```

`overdueDeferredAmount` уже входит в `commonDebt` и повторно к `payableNow` не прибавляется. Будущая `controlDate` без `basis`, начинающегося с `РЕЛ`, отсрочкой не является.

## Сортировка, пагинация и итоги

При построении снимка backend рассчитывает клиентов канонической процедурой `I_DOLG_DOC` и общим `FolioCustomerBalanceCalculator`. При чтении готового снимка MariaDB:

1. применяет фильтры `q/types` и строгий порог `payableNow > minPayable`;
2. сортирует по `payableNow DESC`, затем `partner.shortName ASC`;
3. рассчитывает общие итоги всех совпавших клиентов;
4. применяет `offset` и `limit`.

Поэтому:

- `summary.matchedClients` — количество всех клиентов после фильтра и порога;
- `summary.returnedClients` — размер текущей страницы;
- денежные поля `summary` — суммы по **всем** `matchedClients`, а не только по текущей странице.

## Управление снимком

### Статус

```http
GET /admin/folio/customer-debtors/snapshot/status
```

Ответ сохраняет прежние плоские поля для совместимости. Они описывают последнюю
генерацию. Дополнительно возвращаются два независимых объекта:

- `building` — новая генерация, которая сейчас строится; иначе `null`;
- `activeSnapshot` — последний полностью готовый снимок, из которого уже можно
  показывать отчёт; `null` только до первой успешной публикации.

Пример во время пересчёта, когда предыдущий снимок остаётся доступным:

```json
{
  "ok": true,
  "refreshAccepted": false,
  "running": false,
  "generationId": 43,
  "status": "BUILDING",
  "triggerSource": "SCHEDULED",
  "asOfDate": "2026-08-15",
  "startedAt": "2026-08-15T00:10:00.007",
  "completedAt": null,
  "totalClients": 0,
  "error": null,
  "building": {
    "generationId": 43,
    "triggerSource": "SCHEDULED",
    "asOfDate": "2026-08-15",
    "startedAt": "2026-08-15T00:10:00.007"
  },
  "activeSnapshot": {
    "generationId": 42,
    "asOfDate": "2026-08-14",
    "completedAt": "2026-08-14T21:41:25.646",
    "totalClients": 1698
  }
}
```

Возможные `status`: `NOT_READY`, `BUILDING`, `ACTIVE`, `FAILED`, `SUPERSEDED`. Во время `BUILDING` предыдущая активная генерация остаётся доступной. Новая генерация становится активной только после полного успешного расчёта и записи всех клиентов.

Фронт не должен блокировать отчёт только из-за `status=BUILDING`. Если
`activeSnapshot != null`, запрос списка должников уже безопасно читает эту активную
генерацию. Блокировать отчёт нужно лишь до первого готового снимка, когда
`activeSnapshot == null`.

### Диагностика выполнения I_DOLG_DOC

```http
GET /admin/folio/customer-debtors/snapshot/database-activity
```

Endpoint выполняет разовую read-only проверку через `sp_who2` и
`DBCC INPUTBUFFER`. В ответ намеренно не попадают логины, имена компьютеров,
программы, текст SQL и параметры клиента.

```json
{
  "ok": true,
  "checkedAt": "2026-08-15T11:30:00.000",
  "procedure": "I_DOLG_DOC",
  "state": "RUNNING",
  "detectedSessions": 1,
  "activeSessions": 1,
  "blockedSessions": 0,
  "idleSessions": 0,
  "warnings": []
}
```

Значения `state`:

- `RUNNING` — выполнение процедуры обнаружено;
- `BLOCKED` — обнаруженная процедура ждёт блокирующую сессию;
- `IDLE_SESSION` — последним запросом сессии была `I_DOLG_DOC`, но в момент
  проверки сессия `sleeping`; это может быть короткая пауза между клиентами;
- `NOT_DETECTED` — в данную миллисекунду процедура не найдена;
- `UNAVAILABLE` — SQL Server недоступен, не хватило прав либо сессии нельзя
  безопасно проверить.

Это точечная диагностика, а не источник бизнес-состояния. Её нельзя опрашивать
каждые несколько секунд и нельзя использовать для разрешения/запрета просмотра
старого активного снимка.

### Ручной полный пересчёт

```http
POST /admin/folio/customer-debtors/snapshot/refresh
```

Endpoint сразу отвечает `HTTP 202`. Полный расчёт продолжается в отдельном потоке. `refreshAccepted=true` означает, что задача принята этим экземпляром приложения; `false` — локальная задача уже запущена. Межсерверная lease-блокировка в MariaDB не позволяет двум экземплярам одновременно публиковать полную генерацию.

После первого деплоя нужно один раз вызвать `POST .../snapshot/refresh`, дождаться `status=ACTIVE` через status endpoint и только затем открывать общий список. Пока активной генерации нет, список возвращает `503` с кодом `BALANCE_SNAPSHOT_NOT_READY`.

### Обновление при запросе одного клиента

Успешный канонический запрос:

```http
GET /admin/folio/customer-balance?partnerShortName=БОНД%20АНН
```

сразу после расчёта обновляет итоговую строку этого клиента в активном снимке, если:

- `dateFrom` не задана, то есть расчёт выполнен за весь период;
- склады не ограничены;
- `includeServicePayments` не задан или равен `true`;
- активный снимок относится к текущей бизнес-дате.

Ответ подробного отчёта не зависит от записи снимка: если MariaDB временно не приняла обновление, клиент всё равно получает уже рассчитанный ответ ФОЛИО, а ошибка обновления снимка остаётся в серверном логе. Фильтрованный отчёт не заменяет общую строку снимка частичными данными. Снимок предыдущего дня также не смешивается со строками нового дня — его заменяет следующий полный пересчёт.

Если в этот момент строится новая генерация текущего дня, результат одиночного запроса также сохраняется как live override. Перед атомарной публикацией он применяется к строящейся генерации, если он новее уже рассчитанной строки. Это не даёт полной пересборке затереть более свежий расчёт клиента.

### Настройки backend

| Свойство | Значение по умолчанию | Назначение |
|---|---|---|
| `lavka.folio.balance-snapshot.scheduled-enabled` | `true` | включает ежедневный запуск |
| `lavka.folio.balance-snapshot.cron` | `0 10 0 * * *` | cron полной пересборки |
| `lavka.folio.balance-snapshot.zone` | `Europe/Kyiv` | бизнес-дата и зона расписания |
| `lavka.folio.balance-snapshot.lease-seconds` | `7200` | срок межсерверной lease; во время расчёта она продлевается |

## Ошибки

Некорректные параметры возвращают `HTTP 400` в едином problem-формате проекта:

```json
{
  "status": 400,
  "error": "Bad Request",
  "title": "Folio account validation failed",
  "path": "/admin/folio/customer-debtors",
  "code": "invalid_limit",
  "message": "limit must be between 1 and 200"
}
```

- `400` — неправильные `minPayable`, `types`, `limit`, `offset`, `sort` или формат query-параметра;
- `503` — активный снимок ещё не создан либо MariaDB недоступна;
- `500` — непредвиденная внутренняя ошибка;
- SQL и stack trace клиенту не возвращаются.

## Ограничения производительности и согласованности

`I_DOLG_DOC` не имеет режима расчёта всех партнёров. Полная фоновая генерация поэтому:

1. одним запросом выбирает кандидатов из `_PARTNER`;
2. в одном disposable MSSQL-сеансе вызывает каноническую процедуру для каждого клиента;
3. записывает новую отдельную генерацию в MariaDB;
4. атомарно переключает указатель активной генерации только после полного успеха.

При сбое предыдущий снимок остаётся активным, а не заменяется частичными данными. По умолчанию полный пересчёт запускается ежедневно в `00:10 Europe/Kyiv`. Общий HTTP-отчёт выполняет только индексированные запросы MariaDB, а запрос одного клиента по-прежнему читает ФОЛИО напрямую и может точечно освежить его строку.

Это первый надёжный вариант схемы: ежедневная полная сверка обнаруживает в том числе документы, физически удалённые без журнала. Инкрементальный анализ изменений ФОЛИО пока не используется как единственный источник истины, потому что для всех вариантов удаления/архивации нет подтверждённого неизменяемого журнала событий.
