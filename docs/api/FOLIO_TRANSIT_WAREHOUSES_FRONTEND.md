# Транспортные склады — контракт Java → WordPress v3

## Актуальное уточнение v3: запас сети ≠ поставщицкий товар в пути

Дата: 2026-09-06. Нужен деплой Java. Новых миграций/routes/флагов нет;
analyticsSchemaVersion=5, calculationVersion=3. Формат запроса, default `[9]`,
явный `[]` и хэш конфигурации не изменились.
**Правила v2 о происхождении и готовности закупки заменены этой версией.
Не использовать старый planning field для новой формулы.**

Транспортные склады содержат поставки и внутренние перемещения Киев ↔ Одесса.
Общий физический запас сети включает оба вида. Отбор товара по текущему
поставщику остаётся productFilters.currentSuppliers; контрагент прихода не заменяет
поставщика карточки и не ограничивает физический запас.

### Новые поля

В `rows[].inTransitStock.sources[]`:

- `availableForNetworkPlanningQuantity` — physicalQuantity − reservedQuantity,
  независимо от происхождения. Проверены известность, неотрицательность всех
  трёх полей и равенство разности availableQuantity. Нет карточки/снимка,
  отрицательное или несогласованное значение → null, не 0.
- `status=AVAILABLE_PHYSICAL_STOCK` или `NO_AVAILABLE_TRANSIT_STOCK` для корректного
  источника; ошибки остатков/снимков остаются прежними.
- `supplierInTransitAvailableQuantity` — подтверждённый доступный остаток от
  поставщиков, всё ещё на этом складе. Это часть физического запаса, не прибавка.
- `supplierOriginStatus` и `supplierOriginConfirmed` — отдельная диагностика.
  Весь остаток считается поставщицким при нулевом открытии и только подтверждённых
  PURCHASE_RECEIPT от Т/I с кодом контрагента. При смешанных приходах или неизвестном
  открытии количество поставщицкого остатка null, но сетевой остаток источника
  остаётся известным. Последний приход не определяет происхождение остатка.

Внутренние перемещения не называть «товаром в пути от поставщика». При смешанных
приходах текущий контракт не распределяет оставшийся запас по партиям: неизвестную
поставщицкую часть нельзя вычитать из общей и объявлять разность внутренней.
MIXED_ORIGIN также может означать корректировки, не только перемещения.

В общем `inTransitStock`:

- `availableForNetworkPlanningQuantity` — подтверждённый транспортный вклад в запас
  сети (не включает продажи), только при согласованных снимках;
- `supplierInTransitAvailableQuantity` — общий поставщицкий остаток только при
  подтверждении всех источников и согласованности снимков;
- `networkPlanningReady`, `networkPlanningStatus` — разрешение/причина запрета;
- `networkSnapshotConsistency` — status, confirmed, salesSources[], transitSources[],
  recommendation. Источники включают ID/поколение/дату/версию снимка;
- `ready/status` повторяют сетевую готовность/статус для защиты старых клиентов.

Старое `availableForPlanningQuantity` deprecated: на источнике — поставщицкая
часть; общий итог также блокируется при несогласованных снимках.
`knownAvailableForPlanningQuantity` и сумма availableQuantity — только диагностика,
не запас, автоматически разрешённый к вычитанию из закупки.

### Защита от двойного учёта и честная граница реализации

Пересечение transport IDs с любым ID продаж → TRANSIT_SCOPE_OVERLAP и общий null.
Детали источников сохраняются; список не исправляется молча.

**Существующие v5-снимки независимы. Доказательства общего среза ФОЛІО или сверки
переходов партий между срезами сейчас нет.** Одинаковые даты, близкие completedAt,
repeatable-read MariaDB и фиксированный cursor не доказывают отсутствие дубля:
отправитель мог быть прочитан до перемещения, получатель после.

Поэтому при непустом транспортном списке и готовых снимках:

```text
networkSnapshotConsistency.status = NETWORK_SNAPSHOT_CONSISTENCY_UNCONFIRMED
networkSnapshotConsistency.confirmed = false
networkPlanningReady = false
availableForNetworkPlanningQuantity = null
```

При неполных метаданных — INCOMPLETE_NETWORK_SNAPSHOTS. При ошибках остатка
networkPlanningStatus сообщает ошибку; consistency видна отдельно.
При `[]`: DISABLED, enabled=false, network quantity=0, ready=true — явное
отключение учёта, а не доказательство отсутствия товара.

Та же consistency есть в capabilities.transit / query.context.transit.
Capabilities transit.ready — только готовность метаданных, не разрешение закупки.
Новые features.configurableTransit:
supplierOriginRequiredForNetworkStock=false,
crossWarehouseSnapshotCertificationSupported=false.
Для непустого списка backend пока намеренно не выдаёт подтверждённый сетевой итог.

Следующий отдельный backend gate — сохраняемый, проверяемый согласованный
source-side срез продаж+транспорта либо сверка переходов партий между моментами
чтения. Простой последовательный refresh не является гарантированным ремонтом.
Не обходить запрет суммированием sources[], подстановкой 0 или флагом от браузера.

### Формула и задание фронту

После подтверждения согласованности:

```text
networkAvailable = availableOnSalesWarehouses + availableOnTransportWarehouses
purchaseNeed = max(0, forecastDemand + displayReserve
                     - networkAvailable - confirmedOpenSupplierOrders)
```

Бизнес-пример: прогноз15, Киев5 + Одесса3 + Приёмка2 + Транспорт1 = 11;
закупка4 без резерва витрины. Это пример формулы, не результат подтверждения
нынешних независимых снимков. Спрос не уменьшается на транспорт.

1. Требовать capability calculationVersion=3; использовать новый сетевой показатель.
2. Общий блок назвать «Запас на транспортных складах», отдельную поставщицкую
   часть — «Товар в пути от поставщика». Не требовать supplierOriginConfirmed для
   отображения физического запаса.
3. Показать количество, резерв, происхождение, поколения и consistency каждого
   источника. null — «не подтверждено», не 0.
4. При networkPlanningReady=false/null блокировать готовую рекомендацию,
   оставить просмотр и ручную сверку. Не использовать старый planning field.
5. Поставщицкий остаток не прибавлять к транспорту повторно. Java по-прежнему не
   распределяет запас между группами и не сверяет открытые заказы; уже принятые
   количества нельзя вычитать второй раз как открытый заказ.
6. Сохранять context.transit в экспорте. Cursor привязан также к calculationVersion;
   смена версии/конфигурации/любого поколения → 409 ANALYTICS_CURSOR_EXPIRED.

Проверки v3: внутренний/смешанный приход, неизвестное открытие, резервы,
отрицательные/неполные/несогласованные остатки, отсутствующие источники, пересечение
ID, отсутствие ложного подтверждения при одинаковых датах и независимых срезах,
неизменность спроса, конфигурация и поколения cursor. Живая ФОЛІО не изменялась.

## Передача конфигурации

Одинаковый блок для существующих capabilities/query:

```json
{
  "sourceDatabase": "Paint_Ua",
  "warehouseIds": [1, 7],
  "calculation": {
    "transit": {
      "warehouseIds": [9, 10],
      "configurationRevision": "11e07e7bb591992307e25655831247578120a67b9436b172b61a4df9ba743557"
    }
  }
}
```

Для query дополнительно нужны period/page/sort и прежние отборы.
Ревизия необязательна; при передаче должна совпасть с SHA-256 UTF-8 компактного
JSON отсортированных уникальных числовых ID. Неверная ревизия —
400 TRANSIT_CONFIGURATION_REVISION_MISMATCH; неверный список —
400 INVALID_TRANSIT_CONFIGURATION. До 16 уникальных положительных ID,
не более 256 входных элементов. ID не добавляются в область спроса.
Для WordPress источник списка — общая настройка lavka_transit_warehouse_ids.

Рекомендуемые skills: lavka-woo + folio-inventory-profit-planning;
для сверки документов/партий — work-with-folio-mssql.
Новых запросов в живую ФОЛІО во время отчёта нет; существующие пакетные
MariaDB-запросы по SKU страницы сохранены. Фронт в этой задаче не менялся.
