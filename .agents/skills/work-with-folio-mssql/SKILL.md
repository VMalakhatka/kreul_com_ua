# Работа с ФОЛИО на MS SQL

Работай с ФОЛИО как с унаследованной учётной системой, где фактическая схема конкретной базы важнее версии руководства. Сначала подтверждай устройство данных, затем выбирай совместимый с SQL Server 2000 и jTDS способ, а запись выполняй только при явном запросе пользователя.

## Сначала выбери режим

1. **Чтение или диагностика** — не изменяй файлы, схему и данные. Можно исследовать код, документацию и выполнять безопасные `SELECT`/метаданные, если доступ к базе уже предоставлен.
2. **Изменение Java-модуля** — меняй только репозиторий; не считай это разрешением запускать запросы записи в живой ФОЛИО.
3. **Изменение данных или схемы ФОЛИО** — требуется явный запрос пользователя именно на запись. Сначала выполни проверки из [safe-sql-playbook.md](references/safe-sql-playbook.md), покажи точную область воздействия и обеспечь восстановление.
4. **Эксперимент на Paint_Rus** — читай [experimental-validation.md](references/experimental-validation.md). Для автоматизированного SQL через локальную лабораторию дополнительно читай [lab-api.md](references/lab-api.md). По умолчанию выполняй `ROLLBACK`; сохраняющее изменение делай только в явно заданном сценарии после проверки restore и изоляции базы.

Если режим неясен, продолжай в режиме чтения. Не расширяй запрос «разобраться» до исправления живой базы.

## Соблюдай иерархию доказательств

При конфликте источников используй следующий порядок:

1. схема и поведение текущей живой базы, подтверждённые чтением метаданных или воспроизводимым экспериментом;
2. текущий работающий код и тесты проекта;
3. проектные документы `docs/business` и `docs/api` с пометкой `подтверждено`;
4. `docs/00_DATABASE_CATALOG.md` и документация производителя;
5. гипотезы, комментарии и сходство названий.

Не превращай предположение в факт. В ответе разделяй **подтверждено**, **вывод** и **нужно проверить**. Если руководство расходится с `sp_help` или фактической вставкой, следуй живой схеме и зафиксируй расхождение.

## Рабочий процесс

### 1. Найди точный контекст

- Ищи таблицу, поле, endpoint и Java-метод через `rg` в `docs`, `src/main`, `src/test` и `jtds-1.3.1-dist`.
- Определи, какая база участвует: первичная ФОЛИО/MS SQL или вторичная WordPress/MariaDB. Не смешивай их транзакции и DAO.
- Найди владельца транзакции, ключи строк, ограничения длины, типы и существующие паттерны проекта.
- Никогда не копируй в ответ или Skill URL, логины и пароли из конфигурации или рабочих таблиц.
- Перед добавлением выгрузки схемы или SQL-определений запусти `python3 .agents/skills/work-with-folio-mssql/scripts/check_no_secrets.py <путь>`; если найдена потенциальная утечка, остановись, не показывай совпавшее значение и используй только очищенную копию.

### 2. Подтверди схему

Для изменения записи проверь таблицу через `sp_help`, индексы через `sp_helpindex`, типы и длины через `INFORMATION_SCHEMA.COLUMNS`. Уточни:

- настоящий первичный/уникальный ключ и `IDENTITY`;
- `NULL`/`NOT NULL`, длину `varchar`, значения по умолчанию;
- связи, триггеры и побочные таблицы;
- кириллические константы и CP1251-совместимость;
- смысл счётчика, денежного поля и даты.

Не проектируй вставку только по Java DTO или старому руководству.

### 3. Пройди проверку совместимости

- Пиши T-SQL, который поддерживает SQL Server 2000; не используй `OFFSET/FETCH`, `ROW_NUMBER()`, sequence и другие новые возможности без доказательства поддержки.
- Сохраняй jTDS 1.3.1 как текущий совместимый драйвер. Не заменяй его Microsoft JDBC автоматически.
- Для generated key оставайся на том же JDBC-соединении.
- Используй `BigDecimal` для количества, цены и суммы; не вноси дополнительную ошибку `double`, даже если старое поле имеет тип `float`.
- Учитывай лимит SQL Server в 2100 параметров и дроби пакетные запросы.

### 4. Реализуй минимальное изменение

- Переиспользуй `folioJdbcTemplate`, `folioNamedJdbc` и `mssqlTransactionManager` из `SpringConfig`.
- Сохраняй одну атомарную транзакцию для взаимозависимых таблиц ФОЛИО.
- Для конкурентных изменений используй условный `UPDATE`, проверку количества строк и только необходимые `UPDLOCK, HOLDLOCK`.
- Предпросмотр должен оставаться чтением: без резервирования номера, блокировок обновления и скрытых записей.
- Не заполняй неизвестные поля «похожими» значениями и не трогай `SCL_NS`/`SCL_NR` без нового подтверждения.
- Соблюдай идемпотентность внешних команд и откатывай всю операцию при любой ошибке.
- Не переписывай штатный алгоритм учётной цены в Java: сначала автоматизируй precheck/postcheck, а exact штатный recalculation route подтверждай на Paint_Rus.

### 5. Проверь результат

- Сначала выполни локальные unit-тесты затронутого сервиса/DAO, затем сборку проекта.
- Не запускай интеграционный тест против живой ФОЛИО без явного разрешения и изолированных тестовых данных.
- Для записи сравни снимки до/после, количество изменённых строк, суммы, резерв и видимость документа в UI ФОЛИО.
- Проверь повтор команды, конфликт параллельных запросов, CP1251, кириллические символы-двойники, граничные длины и дату на полуночи.
- Если общая Maven-сборка падает из-за старого JaCoCo/JDK или внешнего окружения, отдели эту проблему от результата изменения и сообщи точную команду и ошибку.

## Непереговорные ограничения

- Не выполнять запись в живую базу из диагностического запроса.
- Не считать старую копию безопасным стендом только по имени: проверять `DB_NAME`, SQL Server 8.x, compatibility 80, CP1251, права login, изоляцию и восстановление перед каждым циклом записи.
- Не делать массовый `UPDATE`/`DELETE`, DDL, выдачу широких прав или `KILL` без точной цели и явного разрешения.
- Не использовать `db_owner`; выдавать сервисному пользователю только нужные действия по конкретным таблицам.
- Не сравнивать кириллические `С/Р/П` с латинскими `C/P`; сверять кодовые точки.
- Не считать `SCL_NAKL.UNICUM_NUM` видимым номером документа.
- Не считать `KON_KOLCH` доступным остатком и не менять его при обычном счёте.
- Не полагаться на MySQL-команду `SET NAMES utf8mb4` для соединения с ФОЛИО/MS SQL.
- Не публиковать мутирующие `/admin` или `/sync` endpoints без проверки внешней аутентификации и авторизации.
- Не хранить в Skill или Git сырые выгрузки с паролями, токенами, адресами серверов, строками подключения, приватными ключами или инфраструктурными реквизитами.
- Не коммитить `.rpt` экспериментов Paint_Rus: переносить только обезличенные воспроизводимые инварианты.

## Формат результата

Для анализа или изменения кратко сообщи:

1. что подтверждено и каким источником;
2. что изменено либо какой SQL предлагается;
3. какие совместимость и риски учтены;
4. чем проверено;
5. что осталось неизвестным и как безопасно это подтвердить.

Если получено новое воспроизводимое знание о ФОЛИО, предложи дополнить подходящую карточку `docs/00_DATABASE_CATALOG.md` или документ `docs/business`/`docs/api`, указав источник: документация, живая схема, код либо эксперимент.
