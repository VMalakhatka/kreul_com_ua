## Назначение

Используй эксперимент, когда схема и SQL-определение не доказывают полный бизнес-процесс: создание приходной/расходной накладной, платежи, задолженность, партии, архивы или учётные цены.

Не учи модель по одному случайному production-документу. Сравнивай одно контролируемое действие штатного клиента с точечными состояниями до/после.

## Стенд Paint_Rus

Пользователь обозначил `Paint_Rus` как заброшенную около полугода копию. Это делает её кандидатом на стенд, но не доказывает изоляцию или восстановимость. В старых именах файлов встречается написание `Paint_RUS`; точное имя базы для новых guard/API — `Paint_Rus`.

Перед первой записью:

1. проверить `DB_NAME() = 'Paint_Rus'` в том же соединении;
2. подтвердить версию, compatibility, collation, схему и определения целевых объектов отдельно от Paint_Ua;
3. исключить другие пользовательские/интеграционные сессии;
4. создать backup и доказать восстановление на отдельной копии;
5. использовать синтетического партнёра с `N_USER`, начинающимся на `TST`, тестовый товар и изолированный склад;
6. на согласованном общем instance использовать SQL-login без server roles и без доступа к другим user databases; VPN и loopback-only API являются внешней границей текущего стенда, а отдельная disposable VM/instance остаётся более сильным будущим вариантом;
7. не хранить server, login, password или API token в Skill, SQL-файлах, отчётах, shell history или Git.

Read-only комплект расположен в `docs/folio-experiments`. Он имеет exact database guard и не выполняет штатные процедуры записи/перерасчёта.

## Автоматизированный SQL

Локальный модуль `folio-rus-lab` даёт Codex управляемый доступ к произвольному локальному T-SQL в копии `Paint_Rus`. Перед использованием полностью прочитай [lab-api.md](lab-api.md).

- Начинай с `health` и `preflight`; не продолжай при ошибке guard или fixed server role.
- Для исследования используй `ROLLBACK`. Не обещай откат, если procedure изменила границу транзакции или API вернул outcome unknown.
- `COMMIT`/`SELF_MANAGED` допустимы только для явно согласованного узкого эксперимента с проверяемыми postconditions. Никогда автоматически не повторяй такой запуск.
- В одной итерации меняй один фактор. После изменения получай after-снимок отдельным read-only запросом и сверяй результат штатным UI/отчётом.
- Не читай локальный `.env` и не проси пользователя присылать его содержимое. CLI сам получает только API-token из защищённого локального файла.

После любого изменения комплекта запусти `python3 .agents/skills/work-with-folio-mssql/scripts/validate_experiment_pack.py`. Валидатор запрещает DML/DDL и допускает только два подтверждённых read-only вызова задолженности.

## Golden-master цикл

1. Назначить уникальный `experiment_id` до 30 символов.
2. Запустить preflight и проверить ручной backup/restore gate.
3. Сохранить минимальный baseline по документу, товару, остатку, цене, номеру и платежным связям.
4. Выполнить ровно одно действие через штатный UI ФОЛИО либо один заранее разобранный SQL-сценарий через lab API.
5. Сохранить after с теми же ключами.
6. Сверить штатный UI/отчёт, SQL before/after, return/OUT/rowsets и блокировки.
7. Повторить сценарий либо получить независимую сверку штатным отчётом.
8. Только затем исправить Java-модель/Skill и добавить regression test.

Не запускать неизвестную procedure «для проверки», даже внутри `ROLLBACK`: nested commit, DDL, external call или session state могут пережить ожидаемый откат. Сначала прочитать разрешённое определение/зависимости и подготовить точные before/after postconditions.

## Матрица сценариев

Изолировать каждый случай:

- `П`/`Р`/`С` × учитываемый/неучитываемый;
- один склад, затем многоскладской документ/перемещение;
- без партии, затем партия/срок, если реально используются;
- без платежа, частичная оплата, полная оплата, аванс;
- возврат/сторно;
- коррекция задним числом;
- архив/восстановление;
- средняя/LIFO/FIFO/фиксированная/партионная учётная цена;
- одинаковая дата прихода/расхода, отрицательный остаток, отсутствующий курс;
- успех, ожидаемый отказ и повтор одного действия.

Сначала закрывай реально нужный компании поднабор. «Все возможности ФОЛИО» не является конечным тестовым сценарием.

## Перенос знания

Для каждого вывода фиксируй:

- дату, базу, версию и exact сценарий;
- ключи синтетических сущностей;
- ожидаемые и фактические таблицы/дельты;
- UI/отчёт, которым подтверждён результат;
- ограничения и непроверенные ветки.

В Skill переносить только обезличенный инвариант. Raw `.rpt` держать локально и сначала проверять `scripts/check_no_secrets.py`. Не переносить имена, телефоны, адреса, operational counts или определения с чувствительными literals.

Если эксперимент опровергает текущую модель, не усредняй результаты: пометь старое правило как относящееся к Paint_Ua/конкретному account flow, добавь новое правило с областью применимости и тест.

## Стоп-условия

Остановить запись/перерасчёт при любом условии:

- база не `Paint_Rus`;
- восстановление backup не проверено;
- есть неизвестные параллельные сессии;
- схема/процедура отличается от исследованной и не разобрана;
- precheck нашёл отрицательную хронологию, несогласованные партии, нулевое количество, остаточный `TMP_MOVE` или отсутствующий курс;
- непонятен expected row count/область изменения;
- штатный UI вернул ошибку после частичных изменений;
- после действия осталась транзакция или блокировка.
