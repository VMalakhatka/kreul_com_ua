## Как пользоваться

Эта карта — быстрый ориентир, а не замена метаданным. Перед записью открой карточку таблицы в `docs/00_DATABASE_CATALOG.md`, затем проверь живую схему. Поля ниже относятся к текущей исследованной базе Paint_Ua; точное покрытие снимка от 2026-08-11 смотри в [live-database-snapshot.md](live-database-snapshot.md).

## Основные таблицы

| Таблица | Подтверждённая роль | Критичные ключи/связи |
|---|---|---|
| `SCL_NAKL` | шапка складского документа/счёта | PK `UNICUM_NUM`; `TYPE_DOC` — тип; FK склада |
| `SCL_MOVE` | строки складского документа | PK `RECNO IDENTITY`; FK документа, товара/склада и склада |
| `SCL_ADDN` | дополнительные реквизиты документа | PK/FK `UNICUM_NUM`; требуется для полноценной видимости/формы счёта в UI |
| `SCL_ARCN`/`SCL_ARCR`/`SCL_ARCM` | исторические архивные аналоги шапки/дополнения/строк | архивный документ имеет отдельное влияние на отчёты и остатки |
| `SCL_PLAT`/`SCL_ADDP`/`SCL_PMOV` | платёж, его доп. реквизиты и распределение по товарам/документам | `UNICUM_PLT`; оплата не сводится к одному flag |
| `SCL_ARTC` | товар по складу, физический и доступный остаток | `(COD_ARTIC, ID_SCLAD)` |
| `NSF_ORG` | штатные счётчики видимых номеров по виду документа | PK `(NAME_USER, ID_SCLAD)`, `N_3` |
| `_PARTNER` | справочник контрагентов | `N_USER` — стабильное короткое уникальное имя |
| `_PARTNER_PL` | дополнительные строки партнёра | PK `RECNO_PARTPLAT IDENTITY`, FK `N_USER -> _PARTNER`; one-to-many |
| `_RECLAMA` | справочник источников информации (роль по документации) | `SIGNIFIC varchar(30) NOT NULL`, live unique nonclustered PK; FK/CHECK/default нет |
| `ALL_ARTC` | общий справочник товаров | PK `COD_ARTIC`; `PLUS_ARTIC bigint IDENTITY`, но без unique/index |
| `img_prod` | дополнительные изображения товара | clustered PK `id IDENTITY`; логическая связь через `PLUS_ARTIC` без FK/index |
| `LAVKA_FOLIO_ACCOUNT_REQUESTS` | локальная таблица идемпотентности счетов | PK `EXTERNAL_REQUEST_ID varchar(64)`; hash уже есть, но nullable и не используется Java |
| `folio_product_media_requests` | идемпотентность media apply во второй MariaDB | не находится в MS SQL и не входит в общую транзакцию ФОЛИО |

## Живые ключи и ограничения

На исследованном наборе таблиц подтверждены PK/FK и отдельные unique indexes, но нет CHECK и UQ constraints. Особенно важно:

- `SCL_NAKL` имеет только nonclustered PK по `UNICUM_NUM`; фильтры списка по дате, типу, складу или партнёру не покрыты отдельным индексом;
- `SCL_MOVE` имеет индексы `(UNICUM_NUM, NAME_PREDM, ID_SCLAD)` и `(NAME_PREDM, DATE_PREDM, ID_SCLAD)`, но нет подтверждённой уникальности `(UNICUM_NUM, NUM_PREDMT)`;
- `SCL_MOVE.UNICUM_NUM -> SCL_NAKL`, `SCL_ADDN.UNICUM_NUM -> SCL_NAKL`;
- `SCL_MOVE.(NAME_PREDM, ID_SCLAD) -> SCL_ARTC.(COD_ARTIC, ID_SCLAD)`;
- `SCL_NAKL`, `SCL_MOVE`, `SCL_ARTC` имеют FK к `SCLAD_R` по складу;
- `ALL_ARTC.PLUS_ARTIC` и `img_prod.PLUS_ARTIC` не индексированы и не связаны FK;
- `LAVKA_FOLIO_ACCOUNT_REQUESTS.UNICUM_NUM numeric(18,0)` не связан FK с `SCL_NAKL.UNICUM_NUM float(53)`;
- `_RECLAMA` имеет единственный индекс `pk__RECLAMA_1`, unique nonclustered PK по `SIGNIFIC`; FK в любую сторону и CHECK не найдены.

Не рассчитывай на БД для проверки положительного количества, неотрицательного резерва или согласованности номера строки: эти инварианты должны быть проверены приложением и общей транзакцией.

## Ключевые поля документов

### `SCL_NAKL`

- `UNICUM_NUM` — внутренний технический идентификатор; выделять конкурентно-безопасно.
- `N_PLAT_POR` — видимый числовой номер документа, в текущей схеме `float NOT NULL`.
- `TYPE_DOC` — для счёта кириллическая `С` U+0421.
- `DATE_P_POR` — дата документа; записывать на полночь.
- `STND_UCHET` — признак учёта; влияет на резерв.
- `ID_SCLAD` может быть `NULL` у многоскладского документа; склад тогда задаётся в строках.
- `VID_DOC` — бизнес-вид операции, не технический тип. В данных встречались `*ПРЕДОПЛАТ`, `*ПЕРЕМЕЩЕНИЕ`, `*РАЗОВАЯ`; выбирать из подтверждённого справочника/конфигурации, не угадывать.
- `DOPN_SCHET` — фактическая длина `varchar(5)`; комментарий API должен укладываться.
- `COD_VALUT` — живой `varchar(4)`; не ограничивай модель Java только `Integer`, пока не доказано, что все допустимые коды числовые.
- `ORGANIZNKL` — полное имя плательщика, до 50.
- `MY_ORGANIZ` — полное имя получателя, до 50.
- `BRIEFORG` — короткое имя плательщика, до 8.

### `SCL_MOVE`

- `RECNO` — в живой схеме `IDENTITY`; старое руководство, где он описан иначе, для этой базы неверно.
- `TYPDOCM_PR` — должен совпасть с `SCL_NAKL.TYPE_DOC`; для счёта кириллическая `С`.
- `DATE_PREDM` — дата строки; нормализовать на полночь вместе с шапкой.
- `BALL1`…`BALL5` — производные значения из карточки товара × количество, не пользовательский ввод.
- Остальные производные реквизиты строки копировать из подтверждённых шапки/товара согласно mapping; не заполнять догадками.

### `SCL_ADDN`

Для видимого в UI счёта запись требуется в той же транзакции, что шапка и строки. Фактические максимумы текущего контракта:

| Значение | Максимум |
|---|---:|
| город плательщика | 28 |
| директор | 75 |
| бухгалтер | 75 |
| телефон | 20 |
| условия/адрес доставки | 150 |

Остальные подтверждённые ограничения API: пользователь ФОЛИО 20, source/additional info 30, вид цены/договора 10, `VID_DOC` 20.

## Партнёры

Семантика `_PARTNER` подтверждена документацией структуры и текущим API:

- `N_USER` — уникальное короткое имя организации; использовать как `id`/`shortName`, копировать в `SCL_NAKL.BRIEFORG` и `SCL_MOVE.ORG_PREDM`;
- `NAME_USER` — полное имя; копировать в `SCL_NAKL.ORGANIZNKL` и формы;
- `NAMEP_USER` — имя для платёжных документов; может быть пустым и не является shortName;
- `MY_ORGANIZ` и другие признаки фильтруют собственные/внешние организации согласно текущему DAO.

Не выводи телефон или город из `_PARTNER_PL`, пока связь и поле не подтверждены для текущей базы.

FK `_PARTNER_PL.N_USER -> _PARTNER.N_USER` подтверждён, но не правило выбора строки: отношение допускает несколько записей партнёра, а в снимке таблица была приблизительно пустой. Не вводи `JOIN`, который случайно размножит партнёров.

Не переносить одинаково названные flags между документами: например, исторически `NOT_NAL=1` у складского документа означал наличный, а у платежа — банковский документ.

## Товары и остатки

`SCL_ARTC` хранит состояние товара на конкретном складе:

- `KON_KOLCH` — физический остаток; обычный счёт его не меняет;
- `REZ_KOLCH` — свободный/доступный остаток; учитываемый счёт уменьшает, отмена или удаление возвращает;
- `COD_ARTIC` — артикул;
- `ID_SCLAD` — склад.

Не переносить семантику старых Java entity с `double` в новые денежные/количественные операции: использовать `BigDecimal`.

## Партии и несохранённые документы

- `SCL_NS` и `SCL_NR` имеют PK по `RECNO` и unique business-key indexes по товару, складу, пользователю, партии и сроку; обе таблицы имеют FK к `SCL_ARTC`.
- `SCL_SROK` имеет поля `ARTICUL`, `ID_SCLAD`, nullable `PARTIA`/`SROK`, остатки и ценовые/производные поля; PK нет, есть только nonunique индекс `(ARTICUL, ID_SCLAD, PARTIA, SROK)`.
- `sysdepends` подтверждает: `A_TR_GET_NS` связан с `SCL_NS`/`SCL_NR` и вызывает `A_TR_CHANGE_NS`, который меняет `SCL_NS`; NR-пара аналогично меняет `SCL_NR`.
- В агрегированном живом снимке ни одна группа строк `SCL_MOVE` не имела заполненных `PARTIA` или `SROK`, а `SCL_SROK` была приблизительно пустой.

Последний факт описывает текущие данные, а не возможность системы. Штатные procedures поддерживают партии/сроки; не распространяй direct Java flow без партий на новый товар или другую базу без отдельной проверки.

## Изображения

- `ALL_ARTC.COD_ARTIC varchar(20)` — ключ товара.
- `ALL_ARTC.S50 varchar(50) NULL` — имя главного изображения.
- `ALL_ARTC.PLUS_ARTIC bigint IDENTITY NOT NULL` — локальный числовой идентификатор/связь; отдельного unique/index нет.
- `img_prod.id int IDENTITY` — ключ строки gallery.
- `img_prod.PLUS_ARTIC bigint NULL` — связь с товаром.
- `img_prod.image varchar(100)` — basename изображения.
- `img_prod.sort_order int NULL` — порядок.

В `img_prod` нет подтверждённого unique constraint и встречаются реальные дубликаты. Обновляй gallery по `id` вместе с expected old filename/sort, а не только по имени файла.

## Локальные расширения из XLS

Лист `Таблицы` описывает нестандартные поля/таблицы конкретной организации:

### `ALL_ARTC`

- `DESCRIPTION` — текст до 5000, описание для сайта;
- `PLUS_ARTIC` — уникальный счётчик, аналог внутреннего SKU;
- `FASOVKA_KALM` — числовая оптовая фасовка;
- `PR_CENA` — признак перерасчёта розничной цены.

### Локальные таблицы

- `ALL_CENA` — украинские/рублёвые цены и связь базового артикула (`ARTIC`, `ARTIC_BAZA`, `PR_BAZA`, `CENA_UA`, `CENA_RUB`); лист помечает как используемую только в Украине.
- `ALL_OBR` — связь товара и образца через `ALL_ARTC.PLUS_ARTIC`; также помечена для Украины.
- `ALL_RAZBORKA` — родитель/компонент, количество, уровень, валюты, цены и транспортные доли.
- `ALL_RAZBORKA_SLOJ` — связь родителя/ребёнка, количество, доли цены и признак транспорта.

Эти сведения показывают намерение локального расширения, но тип, nullability, индекс и реальное наличие всё равно подтверждай через живую схему.

## Расхождения и неизвестное

- Руководство описывало `SCL_MOVE.RECNO` не как identity; живая вставка и метаданные доказали `IDENTITY`.
- Старый каталог часто документирует `UNICUM_NUM`, `UNICUM_PLT`, номера, цены и количества как `float(53)`; проверяй целочисленность и диапазон перед преобразованием, а сумму — по правилам округления ФОЛИО.
- Минимальные `SCL_NAKL` + `SCL_MOVE` записывались, но не показывались в UI; добавление `SCL_ADDN` подтвердило требуемую триаду.
- Метаданные зависимостей подтверждают связь `A_TR_GET_NS/CHANGE_NS` с `SCL_NS` и `A_TR_GET_NR/CHANGE_NR` с `SCL_NR`; GET-процедуры могут менять состояние через CHANGE. Обычное сохранение готового счёта эти таблицы не заполняло: не включать их в обязательную триаду и не изменять без полного текста процедур и нового эксперимента на копии.
- Не все поля `_PARTNER_PL` надёжно сопоставлены телефону/городу.
- Значения `VID_DOC` зависят от бизнес-операции; не задавать универсальное значение по одному примеру.
- Исправленные `01_live_colums_corect.rpt`/`02_index_correct.rpt` закрыли схему `_RECLAMA`: `SIGNIFIC varchar(30) NOT NULL`, `PLANIR float NULL`, `CHAR10 varchar(10) NULL`, `INT1 int NULL`; PK по `SIGNIFIC`, defaults/FK/CHECK нет.
