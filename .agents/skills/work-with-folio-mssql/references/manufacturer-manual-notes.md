## Охват и ограничения источника

`FolProf1.DOC` — ФОЛИО-WinСклад 7.57/7.57E Client–Server, издание 11, книга 1, август 2008; явно заявляет SQL Server 2000/2005 и MSDE 2000. Охватывает установку, справочники, склады, товары, организации, складские и платёжные документы, реестры и журнал движения.

`FolProf2.DOC` — версия 7.5/7.5E, издание 10, книга 2, август 2008; титул называет SQL Server 7.0/2000 и MSDE, а накопленные разделы также упоминают SQL Server 2005. Охватывает отчёты, обмен, перенос периода, права, конфигурацию, backup/restore, отраслевые модули, CRM и «Заказ-Поставка».

Это накопительные функциональные руководства разных версий, а не DDL текущей базы. Они объясняют поведение клиента и бизнес-смысл, но типы, ключи, triggers и фактическую версию подтверждай отдельно.

## Склады и товары

Подтверждено руководством:

- каждый логический склад имеет свой справочник товаров и партий;
- артикул программно уникален только внутри одного склада; одинаковый код в разных складах исторически мог обозначать разные товары;
- в многоскладском документе склад находится у каждой товарной строки, а склад шапки может быть пуст;
- товар документа обязательно выбирается из справочника;
- имя товара — до 200 символов, артикул — до 20;
- товар имеет группу и до пяти уровней подгрупп;
- физический и свободный остатки расчётные; свободный остаток равен физическому минус резерву;
- фасовка читается из текущей карточки, а не сохраняется независимым snapshot документа. Изменение фасовки может изменить отображение старого документа;
- положительная фасовка означает число учётных единиц в упаковке; отрицательная переключает алгоритм пересчёта.

Источник: FolProf1 §§4.1–4.4, 5.1.3.1, 7.3.2.5, печатные с. 37–42, 62–64, 166–168; FolProf2 §10.29.

Практический вывод: для `SCL_ARTC` и товарной строки почти всегда требуется составной контекст `(COD_ARTIC, ID_SCLAD)`. Не ищи складской товар только по артикулу, если задача не относится к подтверждённому глобальному `ALL_ARTC`.

## Организации и партии

Организации:

- справочник общий для всех складов базы;
- минимально нужны полное и краткое имя;
- краткое имя уникально и является бизнес-идентификатором в документах/взаиморасчётах;
- если оно пусто, старый клиент формирует его из первых 8 символов полного имени;
- изменение краткого имени может оставить старые документы под прежним идентификатором и разделить одну организацию в отчётах;
- основная карточка может иметь несколько дополнительных карточек платёжных реквизитов и адресов.

Это согласуется с текущим mapping `_PARTNER.N_USER` → shortName, но генерацию первых 8 символов не воспроизводи в интеграции без явного бизнес-решения: сначала ищи существующего партнёра.

Партии:

- справочник партий отдельный для склада;
- партия формируется из приходного документа и не является обычным ручным справочником;
- её определяют название и срок годности;
- остаток партии меняется при сохранении документов;
- резерв партии отдельно не хранится, а рассчитывается по счетам;
- при партионном учёте прямой SQL документа может требовать больше связей, чем текущий простой account flow.

Источник: FolProf1 §§5.3, 5.4.1–5.4.4, 7.5, печатные с. 85–106, 203–215; FolProf2 §10.4.2.

## Документы и остатки

Штатные типы включают приход, расход, счёт, сборку и платёжные документы.

- учитываемые и неучитываемые приход/расход меняют физический остаток; признак учёта определяет участие накладной в расчёте учётной цены;
- учитываемый счёт уменьшает свободный остаток, неучитываемый счёт не резервирует;
- сборка списывает комплектующие и приходует готовый товар;
- архивные документы исключены из текущих остатков, журнала и отчётов;
- сохранение документа может касаться шапки, строк, остатков, партий, резервов, учётных сумм и платёжных связей;
- специальный сетевой резерв до сохранения использовал служебные `SCL_NR`/`SCL_NS`; «грязные» строки могли давать ложную нехватку.

Источник: FolProf1 §§7, 7.8, 9.1.3, 7.3.2.3, печатные с. 135–136, 165, 225–235, 277–280.

Не обобщай account flow на приход, расход, сборку или партионный документ. Для каждого типа сначала восстанови весь транзакционный контур штатного клиента.

## Нумерация и специальные значения

Руководство указывает:

- пользовательский номер документа — до 9 цифр;
- дополнительный номер — до 5 буквенно-цифровых символов;
- исторически номер при сохранении мог формироваться как `max + 1`;
- сочетание номер + дата + тип клиент проверяет, но оператор мог разрешить дубликат;
- поэтому пользовательский номер/дата/тип не являются надёжным PK;
- устойчивый внутренний идентификатор шапки — `UNICUM_NUM`.

Текущая интеграция использует живо подтверждённый штатный `NSF_ORG.N_3`, а не буквально старый описанный `max + 1`. Это пример, где фактическое поведение текущей базы выше руководства.

Особые бизнес-значения из руководства:

- платежи с номером `0` могут быть служебными при возврате/сторно;
- документы переноса долгов могут иметь номер `0`, дату до начала нового периода и специальное основание;
- `Доп.Рег.Номер = СТОП` мог блокировать выбор организации;
- товар с примечанием `СКРЫТЫЙ` нельзя добавлять в документ;
- назначение `ДОПРАСХ` обозначает статью дополнительных расходов;
- тип грузополучателя мог кодироваться как `#<краткое имя>#<номер доп.реквизитов>`;
- в `CHAR10` справочника операций использовались кириллические `Р`, `П`, `С`, `Б`.

Не нормализуй нули, пустые строки, `NULL`, `+`, `#...` или возвратные flags без понимания их исторической семантики.

## Учётные цены

ФОЛИО поддерживала среднюю, FIFO, LIFO, прямую партионную, справочную цену и режим без расчёта.

Критичные правила руководства:

- документы обрабатываются хронологически;
- при одинаковой дате приход считается раньше расхода;
- полный перерасчёт мог не учитывать время создания;
- коррекция задним числом пересчитывает последующие расходы;
- участвуют только учитываемые накладные;
- отрицательный остаток может помешать расчёту;
- начальный остаток товара при партиях должен совпасть с суммой начальных остатков партий.

Источник: FolProf1 §6.3, печатные с. 120–126.

Любая коррекция старого прихода/расхода потенциально затрагивает последующую историю. Не предлагай точечный `UPDATE` цены или количества без анализа перерасчёта.

## Методика внедрения и переиспользование полей

`Metodica2.doc` показывает, что конфигурации ФОЛИО активно переиспользовали общие поля под локальные процессы:

- партия могла означать место хранения, вид работы или серийный номер;
- `Балл` мог означать объём либо дополнительное количество;
- источник информации мог хранить менеджера;
- места хранения могли моделироваться партиями, а перемещение — сборкой с отрицательной строкой источника и положительной строкой назначения;
- производство также использует отрицательные комплектующие и положительное готовое изделие; отходы могут приходоваться по нулевой цене;
- счёт резервирует товар, промежуточный виртуальный склад может означать собранный заказ, расход с него — фактическую отгрузку;
- в сводных отчётах внутренние перемещения надо исключать, иначе оборот завышается;
- скрытые параметры `Cursclad.ini` меняют округление, цены, налоги, права и обязательность полей;
- `PriceByFasov` может сохранять цену повышенной точности, чтобы упаковки не давали расхождение суммы;
- МУЛЬТИСЕРВЕР мог использовать Publisher/Subscriber: запись только на Publisher, отчётный Subscriber отстаёт.

Следствие: имя поля не гарантирует его локальную семантику. Перед новой интеграцией фиксируй настройки конкретного рабочего места, роль сервера и образцы штатных документов этой организации.

## Исторический каталог структуры

`Структура7.doc` описывает версии 7/7E, издание 12, январь 2006. В нём 191 объект: WinСклад — 59, CRM — 58, Заказ-Поставка — 23, Бухмастер — 51. Это исторический широкий каталог, а не перечень объектов текущей Paint_Ua.

Ключевые структурные сведения:

- ядро документа: `SCL_NAKL` (52 поля), `SCL_ADDN` (39), `SCL_MOVE` (44);
- архивные аналоги: `SCL_ARCN`, `SCL_ARCR`, `SCL_ARCM`;
- платежи: `SCL_PLAT`, дополнительные реквизиты `SCL_ADDP`, товарное распределение оплаты `SCL_PMOV`;
- товары/остатки: `SCL_ARTC` с логическим ключом артикул + склад, `ALL_ARTC` с общими полями, `SCL_SROK` с партиями;
- партнёры: `_PARTNER.N_USER varchar(8)` как короткий ID и несколько `_PARTNER_PL` на одну карточку;
- `SCL_NAKL.ID_SCLAD` и `SCL_PLAT.ID_SCLAD` могут быть `NULL` у многоскладского документа;
- `SCL_MOVE` дублирует дату, тип, организацию, flags и суммы шапки;
- `SCL_NAKL.SUM_POR` логически равна сумме активных `SCL_MOVE.SUM_PREDM`;
- полная/частичная оплата зависит от `SCL_PMOV`, оплаченного количества и flags строки; изменение одного флага недостаточно;
- `NOT_NAL=1` имеет разный смысл: для `SCL_NAKL` это наличный документ, для `SCL_PLAT` — банковский. Не делай общий enum по имени колонки;
- отрицательный налог означает «в том числе», а `NULL` у освобождённого товара не равен нулевой ставке;
- исторические `UNICUM_NUM`/`UNICUM_PLT`, номера, цены и количества часто документированы как `float(53)`.

Колонки `P` и `M` в старом каталоге похожи на primary/mandatory, но документ их не расшифровывает и содержит противоречия. Он не даёт полный набор defaults, FK, indexes, triggers или identity. Не генерируй DDL из P/M.

Отделяй документационные опечатки и отсутствующие модули от текущей схемы. Например, на текущем снимке имя `COTIRVAL`, а в Markdown-каталоге встречается `COTRIVAL`; многие `BH_*`, ячеечные и SCM-таблицы из книги отсутствуют, зато текущая база содержит `EXP*`, custom `ALL_*`, `img_prod`, `NSF_ORG`.

## Генератор отчётов

`gen_10.doc` (2002) нужен для задач старых `.rpt` форм:

- серверные таблицы версий 7/7E подключались через каталог/alias `FolioMain`;
- SQL выполнялся компонентом `TQuery`, параметры задавались как `:name`;
- `DataSource1` — временная таблица текущего документа, её нельзя использовать как ведущую для `TQuery`;
- `UNICUM` равен ключу только для сохранённого либо загруженного и не изменённого документа; иначе он `0`;
- `UNICNAKL`/`UNICPLAT` дают ключ текущего документа из реестра;
- `SUM_UCHET`/`SUM_UCVAL` временного документа достоверны только после сохранения;
- порядок выполнения отдельных текстовых элементов непредсказуем; зависимые выражения должны находиться в одном элементе;
- формат числа зависит от региональных настроек Windows и точности ФОЛИО.

Не переносить выражения QuickReport и типы временной `DataSource1` напрямую в SQL DDL или Java DTO. Для отчёта проверяй сохранённость документа, региональные настройки и реальный dataset формы.

## Обмен и интеграция

Старый обмен использует Paradox/dBase IV. Ограничения DBF:

- имя поля до 10 символов;
- логические `T/F` отображаются в `1/0` базы;
- типы `C`, `N 20.4`, `L`, `D` описывают exchange-файл, а не SQL DDL;
- наличие `NAME_PREDM` могло переключать import с позиционного на именное сопоставление;
- успешный import удалял строки из исходного DBF, а иногда и сам файл.

Складские и платёжные документы нужно передавать согласованно: отдельный платёж может потерять товарную связь и создать двойной учёт оплаты. После удалённого обмена товары/партии пересчитывались, но учётные цены могли требовать отдельного перерасчёта.

Источник: FolProf2 §§11.1–11.4, печатные с. 80–100.

## Legacy-администрирование

Руководства отражают старую среду Delphi 7, BDE/DB-Library и настройки, чувствительные к локали:

- SQL Login рекомендовался с языком `English` для дат;
- SQL scripts с русским текстом могли требовать OEM-кодировку;
- для старых `prc_all.sql` `SET QUOTED_IDENTIFIER` требовалось выключать;
- встречаются устаревшие `image`, `float`, `varchar`, `IDENTITY`;
- тип MS SQL `timestamp` в этих схемах означает rowversion, а не дату;
- backup SQL Server 2000 нельзя восстановить на SQL Server 7.

Для Java из этого следуют безопасные правила: передавай даты типизированными параметрами, не строками; исследуй collation/code page; не запускай старые SQL scripts с современной кодировкой и defaults без просмотра; проверяй procedures/triggers после restore/update.

## Как применять эти сведения

1. Используй руководство, чтобы понять штатный бизнес-сценарий и найти связанные сущности.
2. Отделяй DBF exchange-layout от SQL DDL.
3. Подтверждай наличие и типы через метаданные текущей базы.
4. Сравнивай с фактическим SQL Java-модуля.
5. При конфликте записывай расхождение; для текущей инсталляции следуй живой схеме.
6. Для нового типа документа сначала исследуй штатное сохранение на копии базы и diff всех связанных таблиц, а не адаптируй только account INSERT.
