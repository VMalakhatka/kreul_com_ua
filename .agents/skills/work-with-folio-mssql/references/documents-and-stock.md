## Инварианты счёта

Полноценный счёт ФОЛИО — согласованный набор:

1. шапка в `SCL_NAKL`;
2. одна или несколько строк в `SCL_MOVE`;
3. дополнительные реквизиты в `SCL_ADDN`;
4. при учитываемом счёте — согласованное изменение `SCL_ARTC.REZ_KOLCH`;
5. при внешней команде — состояние idempotency.

Все части создаются или изменяются в одной транзакции `mssqlTransactionManager`. Если одна часть не прошла, откатывается всё. Проверяй не только наличие строк, но и видимость документа в UI ФОЛИО.

## Два номера документа

Не смешивай:

- `SCL_NAKL.UNICUM_NUM` — технический ключ/связь; пользователь его не видит;
- `SCL_NAKL.N_PLAT_POR` — видимый номер счёта; числовое `float NOT NULL`.

Оба выделяются конкурентно-безопасно, но из разных источников. Внешний Woo order id не обязан совпадать с видимым номером и может храниться в предназначенном source/idempotency поле.

## Штатный видимый счётчик

Следующий видимый номер берётся из `NSF_ORG.N_3`:

- живой PK — `(NAME_USER, ID_SCLAD)`, default `N_3 = 0`;
- текущая конфигурация использует `ID_SCLAD = 0` как глобальную нумерацию;
- учитываемый счёт — суффикс `СU`;
- неучитываемый счёт — суффикс `СN`;
- также подтверждены семейства `РU`, `ПU`, `ПN` для других типов документов;
- `С/Р/П` кириллические, `U/N` латинские;
- строку ищут через `RIGHT(NAME_USER, 2)`, потому что перед кодом есть байт `0xA0`.

При apply читай `N_3` с `UPDLOCK, HOLDLOCK`, используй текущее значение и увеличивай на 1 в той же транзакции. Проверяй, что выбранная и обновлённая строка ровно одна. Preview только читает `N_3` и не резервирует номер.

Этот direct-путь подтверждён живым экспериментом для нынешней конфигурации, но не является полным эквивалентом штатной нумерации. Разобранные `I_GET_LAST_NUMBER`/`I_TEST_NUM_NAKL` учитывают год, учётность, организацию, область склада и для типа `С` архив; legacy fallback `MAX+1` всё равно имеет race. При добавлении организации, типа документа или режима счётчика сначала сверяй [core-procedure-behavior.md](core-procedure-behavior.md) и повторяй конкурентный тест.

## Штатные процедуры как ориентир

Полные определения ключевых procedures безопасно разобраны и сведены в [core-procedure-behavior.md](core-procedure-behavior.md). Используй их как behavioral oracle, но не как готовый вызываемый API.

- `INSERT_NAKL2` имеет 100 параметров и широкий workflow документов, transfers, corrections, партий, цен и платежей. Критично: внутренний commit происходит до вставки `SCL_ADDN` и части платёжных/справочных действий; ошибка может вернуться после частично сохранённого документа.
- `I_RZV_NEUCH` преобразует/делит/объединяет неучитываемые счета, но почти все чтения делает с `NOLOCK`, а резерв уменьшает без достаточного условного update. Текущий Java conflict при нехватке — другая, более строгая бизнес-политика.
- `I_DELETE_NAKL` затрагивает архив, партии, платежи и остатки; вложенный rollback способен откатить внешнюю транзакцию, а одна restore-ветка неатомарна. Прямое удаление/отмена Java не доказано эквивалентным.
- `A_TR_GET_NS/NR` вызывают CHANGE и реально мутируют `SCL_NS`/`SCL_NR`; операции не атомарны, количество `numeric(18,0)`, а NR содержит недостижимую party-ветку.
- `A_POTBOR_PARTIA*`, `ins_partys`, `I_SAVE_PARTY` и `i_uchet_add` образуют отдельный партионно-учётный контур с cursors/temp state и широкими side effects без общей собственной транзакции. Direct Java flow без `PARTIA`/`SROK` нельзя автоматически применять к партионному товару.

Агрегат текущей базы показывает, что во всех исследованных группах `SCL_MOVE` поля `PARTIA` и `SROK` пусты, а `SCL_SROK` приблизительно не содержит строк. Это объясняет, почему direct Java flow без партий соответствует нынешним данным, но не отменяет партионные процедуры и не является гарантией для нового товара/другой базы.

Перед изменением create/update/delete/cancel сначала читай готовые карточки, а после изменения базы повторно выгружай определения процедурой из [views-and-procedures.md](views-and-procedures.md). Любой новый путь сравнивай с UI на восстановимой копии. Наличие procedure не означает, что её безопасно вызывать из Java.

## Атомарное создание

Перед реализацией сверь точные колонки с `docs/api/ACCOUNT_WRITE_MAPPING.md`. Безопасная последовательность по инвариантам:

1. проверить idempotency key и хэш канонического payload; тот же ключ с другим хэшем — conflict; живые колонки `REQUEST_HASH` и `EXTERNAL_DOCUMENT_NUMBER` уже есть, хотя текущий Java их не использует;
2. проверить партнёра, товар, склад, длины, тип документа и вид операции;
3. для preview выполнить обычные чтения, рассчитать результат и завершить без записи;
4. для apply открыть serializable-транзакцию;
5. конкурентно выделить технический ключ и штатный видимый номер;
6. вставить `SCL_NAKL` с нормализованной датой;
7. вставить каждую строку `SCL_MOVE`, получив `RECNO` на том же JDBC-соединении;
8. вставить `SCL_ADDN` с подтверждёнными реквизитами;
9. изменить резерв только для учитываемого режима, условным SQL;
10. пересчитать и сверить суммы, зафиксировать idempotency и commit.

Точный порядок шагов внутри транзакции может следовать текущему сервису, но ни один инвариант не должен остаться частично применённым.

## Учёт и резерв

Для учитываемого счёта (`STND_UCHET`/режим accounted):

```sql
UPDATE dbo.SCL_ARTC
SET REZ_KOLCH = REZ_KOLCH - ?
WHERE COD_ARTIC = ?
  AND ID_SCLAD = ?
  AND REZ_KOLCH >= ?
```

Успех — изменена ровно одна строка. Ноль строк означает отсутствующий товар/склад или недостаточный свободный остаток; откатывай транзакцию и возвращай явный conflict, а не отрицательный резерв.

Неучитываемый счёт не меняет `REZ_KOLCH`. Обычный счёт не меняет `KON_KOLCH`. Для чтения preview не используй update locks.

В order flow проекта статусы Woo `processing` и `on-hold` создают учитываемый счёт; `pc-draft` — неучитываемый. Поток создания счетов не должен принимать `completed` только потому, что это «более поздний» статус. Недостающий остаток может формировать отдельный физический неучитываемый счёт с `sourceInfo = нет на складе`, без изменения резерва.

## Добавление строки в существующий счёт

Не создавай строку только из request DTO и глобальных defaults. Безопасный apply в одной транзакции:

1. заблокировать точную шапку, убедиться, что документ существует, активен, имеет ожидаемый кириллический `TYPE_DOC` и допускает mutation;
2. прочитать шапку и подходящую существующую строку как источник наследуемых `TYPE_DOC`/`TYPDOCM_PR`, даты, партнёра, склада, валюты, договора, `STND_UCHET`, cash/return flags и других производных реквизитов;
3. проверить `(COD_ARTIC, ID_SCLAD)`, единицы, цену/количество, CP1251 и длины;
4. для учитываемого документа условно зарезервировать delta в `SCL_ARTC.REZ_KOLCH`; ноль изменённых строк — conflict и полный rollback;
5. вставить `SCL_MOVE` с наследованными и пересчитанными полями, получив `RECNO` через generated keys/fallback на том же connection;
6. пересчитать `SCL_NAKL.SUM_POR` по активным строкам и проверить арифметику;
7. сохранить idempotency результата, если операция вызывается внешней командой;
8. после commit перечитать счёт и резерв теми же ключами.

Не увеличивай `NSF_ORG.N_3`, не выделяй новый `UNICUM_NUM` и не вставляй новый `SCL_ADDN`: это тот же документ. Не принуждай строку к `accounting=true` или другим defaults, если шапка говорит иначе.

Источник значений разделяй явно:

| Источник | Что брать |
|---|---|
| request | SKU, количество, warehouse только при согласованной многоскладской политике, цена только по подтверждённому контракту API |
| `SCL_NAKL` | тип/дата документа, партнёр, учёт, cash/return, валюта, договор, вид операции и другие реквизиты шапки |
| существующая `SCL_MOVE` | установившийся набор дублируемых line flags, формат номера строки и поля, которых нет в шапке |
| `SCL_ARTC`/ценовые справочники | карточка товара, единица, баллы и цена, если бизнес-правило не разрешает цену request |

Перед кодом составь точную колонка-за-колонкой матрицу по живой схеме и `ACCOUNT_WRITE_MAPPING.md`. Не подменяй неизвестную валютную/розничную сумму нулём.

Для всех add/update/delete/cancel путей сначала проаудируй существующие lock reads и выбери один порядок. Рекомендуемая база: idempotency command → шапка → строки по возрастанию `RECNO`/диапазон номера → остатки по `(ID_SCLAD, COD_ARTIC)`. Затем используй его во всех путях; локально «правильная» обратная последовательность создаёт deadlock.

`NUM_PREDMT`/порядковый номер строки выделяй под защищённым range-read с проверенным индексом. Не делай безблокировочный `MAX()+1`; gap сам по себе обычно не требует повторного использования номера.

Если `SCL_NAKL.ID_SCLAD IS NULL` или строки относятся к разным складам, нельзя брать склад первой строки. Контракт должен либо требовать `warehouseId`, либо запрещать add, либо выводить склад из однозначного бизнес-правила.

Для idempotency мутации строки существующей таблицы создания документа может быть недостаточно. Нужны как минимум scope/`operation_type`, `document_id`, внешний ключ, `payload_hash`, состояние и replay result с `RECNO`; DDL такого расширения согласуется отдельно.

Исторически `STND_UCHET=0` использовался и для исходно неучитываемого документа, а текущая cancel-операция также обнуляет его. Не выводи состояние «отменён» только из одного флага: используй подтверждённый audit/idempotency marker либо сначала уточни модель состояния.

## Изменение и удаление

- При увеличении количества учтённой строки дополнительно уменьши `REZ_KOLCH` на delta условным update.
- При уменьшении верни положительную delta в `REZ_KOLCH`.
- При удалении строки или всего учтённого счёта верни зарезервированное количество.
- Пересчитай `SCL_NAKL.SUM_POR` и все производные суммы/баллы.
- Блокируй изменяемую строку документа и остаток в одном стабильном порядке, чтобы уменьшить риск deadlock.
- Не удаляй idempotency-запись молча. Если повторный request ссылается на уже удалённый документ, возвращай явный конфликт.

## Preview и идемпотентность

Preview обязан быть чистым чтением:

- не увеличивает `NSF_ORG.N_3`;
- не резервирует `UNICUM_NUM`;
- не меняет `REZ_KOLCH`;
- не создаёт строки idempotency;
- не берёт `UPDLOCK`/`TABLOCKX` только ради прогноза.

Для apply внешний request id стабилен при точном повторе одного payload. Изменённый payload должен получить другой ключ или явный conflict. Одновременные повторы не должны создать два документа.

Не считай текущую реализацию автоматически достаточной: таблица уже содержит nullable `REQUEST_HASH varchar(64)`, но код его не читает/не пишет. Исправь протокол DAO/service без DDL, проверь конфликт изменённого payload и ограничь итоговый `EXTERNAL_REQUEST_ID` максимумом 64.

## Поля и границы

Проверяй до открытия транзакции:

| Поле API/смысл | Поле ФОЛИО | Максимум/правило |
|---|---|---|
| тип счёта | `TYPE_DOC`, `TYPDOCM_PR` | кириллическая `С`, 1 символ |
| visible document number | `N_PLAT_POR` | только числовое значение |
| comment | `DOPN_SCHET` | 5 |
| operation kind | `VID_DOC` | 20, значение из подтверждённой конфигурации |
| payer full name | `ORGANIZNKL` | 50 |
| receiver full name | `MY_ORGANIZ` | 50 |
| payer short name | `BRIEFORG` | 8 |
| Folio user | соответствующее поле mapping | 20 |
| source/additional info | соответствующие поля mapping | 30 |
| price/contract type | соответствующее поле mapping | 10 |
| payer city | `SCL_ADDN` mapping | 28 |
| director/accountant | `SCL_ADDN` mapping | 75 |
| phone | `SCL_ADDN` mapping | 20 |
| delivery text | `SCL_ADDN` mapping | 150 |

Окончательное имя колонки бери из `ACCOUNT_WRITE_MAPPING.md` и живой схемы, а не из краткого API-псевдонима.
