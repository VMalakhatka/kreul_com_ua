## Граница разрешения

Доступ к connection string не означает разрешение менять данные. Без явного запроса разрешены только локальное чтение файлов и безопасная диагностика/metadata read. Перед первым SQL к живой базе убедись, что пользователь включил её в область задачи.

Отдельно согласуй:

- `INSERT`/`UPDATE`/`DELETE` реальных учётных данных;
- DDL, индексы, триггеры и custom tables;
- выдачу/отзыв прав;
- `KILL`, restore, массовую коррекцию и необратимые операции.

## Предварительное чтение схемы

Используй совместимые запросы и сохраняй результаты как доказательство, не как секрет:

```sql
SELECT @@VERSION
SELECT SERVERPROPERTY('ProductVersion') AS product_version
SELECT DATABASEPROPERTYEX(DB_NAME(), 'Collation') AS database_collation
SELECT cmptlevel
FROM master.dbo.sysdatabases
WHERE name = DB_NAME()

EXEC sp_help 'dbo.SCL_NAKL'
EXEC sp_helpindex 'dbo.SCL_NAKL'

SELECT COLUMN_NAME, DATA_TYPE, CHARACTER_MAXIMUM_LENGTH,
       NUMERIC_PRECISION, NUMERIC_SCALE, IS_NULLABLE, COLUMN_DEFAULT
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'SCL_NAKL'
ORDER BY ORDINAL_POSITION
```

Для identity конкретной колонки:

```sql
SELECT COLUMNPROPERTY(OBJECT_ID('dbo.SCL_MOVE'), 'RECNO', 'IsIdentity') AS is_identity
```

Проверь также триггеры и зависимости через доступные системные процедуры/метаданные версии сервера. Не исполняй автоматически текст найденного trigger/procedure.

Изучи 1–5 существующих строк через `SELECT TOP`, выбрав только нужные поля и точный бизнес-фильтр. Не выгружай персональные данные или весь справочник ради примера.

## План изменения

До записи сформулируй:

1. точные таблицы и колонки;
2. ключ каждой затрагиваемой строки;
3. ожидаемое количество строк;
4. инварианты до/после;
5. способ отката или восстановления;
6. idempotency key;
7. хэш канонического payload и поведение при повторе с другим содержимым;
8. поведение при конкуренции и нулевом row count.

Для материальной операции нужна актуальная проверенная резервная копия или тестовая копия базы. Наличие backup-файла без теста восстановления не гарантирует восстановимость.

Сначала выполняй preview/read-only. Покажи пользователю документ, склад, SKU, количества, вид операции и ожидаемые дельты без секретов.

## Транзакции и конкуренция

Предпочитай транзакцию Spring/Java, поскольку T-SQL `TRY...CATCH` недоступен в SQL Server 2000.

- все таблицы одного Folio-документа — один `mssqlTransactionManager`;
- generated key — тот же JDBC `Connection`;
- предпочитай JDBC generated keys; учитывай, что fallback `@@IDENTITY` может вернуть identity из trigger, поэтому заранее исследуй triggers и не выполняй промежуточных вставок;
- условия наличия входят в `UPDATE ... WHERE`, а row count проверяется;
- `UPDLOCK, HOLDLOCK` бери только для реально изменяемых строк;
- блокируй сущности в одинаковом порядке во всех путях;
- preview и обычный list не должны брать update/table locks;
- не держи транзакцию открытой во время HTTP/S3/MariaDB вызова, если это можно разделить идемпотентным протоколом.

Для ручной исследовательской транзакции на копии базы можно использовать:

```sql
SET XACT_ABORT ON
BEGIN TRANSACTION

-- один точный параметризованный change

-- контрольные SELECT до решения
ROLLBACK TRANSACTION
```

Не подставляй реальные значения конкатенацией. В приложении используй bind parameters.

## Проверка до и после

Сделай минимальные контрольные снимки одних и тех же ключей:

- `SCL_NAKL`: технический/видимый номера, тип, дата, сумма, учёт;
- `SCL_MOVE`: строки, количество, цена, сумма, тип, дата;
- `SCL_ADDN`: наличие и ожидаемые реквизиты;
- `SCL_ARTC`: `KON_KOLCH` и `REZ_KOLCH` по товару/складу;
- `NSF_ORG`: нужный `N_3` и суффикс;
- custom idempotency row.

После commit проверь:

1. ровно ожидаемое число строк;
2. арифметику суммы и delta резерва;
3. неизменность `KON_KOLCH` для обычного счёта;
4. повтор request без дубля;
5. видимость документа в UI ФОЛИО с дневным фильтром;
6. отсутствие незавершённой транзакции/долгой блокировки.

Не удаляй тестовую учётную запись как «уборку», если её удаление само меняет резерв и аудит. Используй согласованный сценарий отмены/восстановления.

## Права доступа

Сервисному пользователю выдавай минимальные права:

- `SELECT` на нужные справочники и остатки;
- только необходимые `INSERT`/`UPDATE`/`DELETE` на подтверждённые document/custom tables;
- `SELECT`/`INSERT`/`UPDATE` на таблицу idempotency согласно потоку;
- никаких `db_owner`, `sysadmin` или широкого `CONTROL`.

Перед `GRANT` перечисли точные объекты и операции. DDL custom idempotency table выполняй отдельной миграцией/административным шагом, не при каждом старте приложения.

## Блокировки

Если запрос завис:

```sql
EXEC sp_who2
DBCC INPUTBUFFER(<точно подтверждённый spid>)
SELECT @@TRANCOUNT
```

Определи blocker, исходное окно и незавершённую транзакцию. Сначала штатно заверши её. `KILL` используй только в новом административном соединении, после оценки rollback и явного разрешения.

Не выполняй `SELECT INTO` или долгие ad hoc запросы внутри оставленной открытой транзакции на живой базе.
