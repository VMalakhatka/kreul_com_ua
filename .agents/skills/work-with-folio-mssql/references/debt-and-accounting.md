## Область доказательств

Сведения подтверждены read-only разбором полных определений целевых procedures из снимка Paint_Ua от 2026-08-11 и сверкой параметров/зависимостей. Поведение `I_UCHET_TOVAR` дополнительно подтверждено воспроизводимыми golden-master вызовами на изолированной Paint_Rus с внешним `ROLLBACK`; остальные процедуры ради выяснения назначения не выполнялись. Raw-определения не переносить в Skill: полный экспорт содержит чувствительный литерал в другом объекте.

Фактическое имя процедуры валютных продажных цен — `B_ARTC_VRECALC`, не `B_ARTIC_VRECALC`.

## Задолженность клиента

### `I_DOLG_DOC`

Процедура только читает постоянные таблицы: партнёров, активные документы/строки, платежи, распределения `SCL_PMOV`, склады и курсы. Она создаёт локальные временные таблицы, но не записывает бизнес-данные.

- Начинает с исходного долга партнёра и рассчитывает сальдо на начало периода по платежам, накладным и распределённым оплатам.
- Возвращает подробный rowset и OUT: рублёвое/валютное начальное сальдо и код валюты.
- `credit` и `bank` в активном коде не рассчитываются; инициализируй их перед вызовом и не трактуй как доказанный результат.
- `dolg_only` фактически не действует: ветка закомментирована.
- Архивные таблицы не читает.
- Почти все чтения используют `NOLOCK`; результат может объединять разные моменты времени.
- Явных business error codes нет. Деление при нулевом количестве и преобразование даты могут завершиться SQL-ошибкой.

### `I_DOLG_HIS`

Читает активный контур и возвращает более короткую историю. Для неучитываемого товарного движения отдельно вычитает нетоварный остаток платежа, поэтому формула не полностью совпадает с `I_DOLG_DOC`.

- `dolg_only=1` возвращает OUT без подробного rowset;
- `dolg_only<>1` возвращает упрощённый rowset и начальное сальдо;
- `check_move` в активном теле не используется;
- последовательные чтения не образуют согласованный snapshot;
- архивные документы не входят автоматически.

Не считай процедуры взаимозаменяемыми и не заменяй их формулой `SUM(документы)-SUM(платежи)`. Сначала выбери канонический штатный отчёт и сверяй процедуру с ним на Paint_Rus.

### Контракт параметров

- `S_ID` — один `SCLAD_R.ID_SCLAD`; `NULL` означает, что одиночный склад не задан.
- `str_id` — список вида `,7,12,` без пробелов. Это membership-строка, не SQL.
- `date1/date2 char(10)` — строго `dd.mm.yyyy`; procedure делает `SET DATEFORMAT dmy`. Верхняя граница включительна только до переданной полночи.
- `org varchar(8)` — точный `_PARTNER.N_USER`, не полное имя.
- `mode_multi=0` фильтрует по складу шапки; `1` включает многоскладской документ при совпадении хотя бы одной строки; `2` — только когда все строки входят в набор.
- `Show_zv=1` показывает служебные платежи с номером `0`; на OUT-сальдо не влияет.

Для jTDS обработай все result sets/update counts через `getMoreResults()`, затем читай OUT и return status. Используй отдельное disposable connection из-за session-level `DATEFORMAT`.

### Знаки и бизнес-маркеры 7-го отчёта

Правила ниже подтверждены выгрузкой штатного 7-го отчёта от 2026-08-13, текущим Java API и его regression-тестами. Не нормализуй все суммы через `ABS()`: знак является частью направления движения.

- Начальное сальдо сохраняет знак, возвращённый ФОЛИО.
- Положительная сумма расходной накладной увеличивает долг клиента.
- Отрицательная товарная сумма является приходом/возвратом: в отдельной колонке API показывается её модуль, а из долга она вычитается.
- Входящие банковские и кассовые платежи штатный отчёт возвращает положительными; они уменьшают долг и вычитаются ровно один раз.
- Отрицательный платёж нельзя превращать в положительный: при формуле `- payment` он естественно увеличивает долг, что сохраняет направление возврата/исходящего движения.
- Технический баланс ФОЛИО: `accountingBalance = openingBalance + expense - receipt - bankPayment - cashPayment`.
- Внутри одной даты платежи обрабатываются раньше накладных, как в штатной выгрузке.

Маркер `РЕЛ` в начале `SCL_NAKL.OSNOVANIE` обязателен для отсрочки/реализации. Будущая `CONTRLDATE` без `РЕЛ` не создаёт отсрочку. Действующая отсрочка требует `РЕЛ` и дату позже даты отчёта; оставшийся `РЕЛ` после наступления срока означает просроченную отсрочку. После полной оплаты товара с реализации/отсрочки оператор должен удалить `РЕЛ`, иначе документ продолжит отображаться как просроченный.

Маркер `ПРД` в начале примечания платёжного документа означает предоплату независимо от вида оплаты. Сумма предоплаты равна `bankPayment + cashPayment` с сохранением знаков. Старую Excel-формулу, учитывавшую только кассу, не воспроизводи. Предоплата не погашает старый долг и показывается отдельно: `commonDebt = accountingBalance + prepaymentAmount`, `payableNow = commonDebt - deferredAmount`. После поставки предоплаченного товара оператор должен удалить `ПРД`, иначе платёж продолжит считаться зарезервированной предоплатой.

Полный контракт и происхождение формул находятся в `docs/api/FOLIO_CUSTOMER_BALANCE_API.md`; требования к отображению — в `docs/api/FOLIO_CUSTOMER_BALANCE_FRONTEND.md`.

### Инкрементальный снимок задолженности

Для быстрого общего отчёта допустим снимок в интеграционной БД, но «инкрементальный» здесь означает **найти затронутого партнёра и заново выполнить для него каноническую `I_DOLG_DOC`**, а не арифметически прибавить изменение отдельной строки.

Подтверждено живой схемой и read-only разбором штатных procedures:

- `SCL_NAKL` и `SCL_PLAT` имеют `CREATEDATE`, `CORRDATE`, `WHO_CORR`;
- у `SCL_MOVE` и `SCL_PMOV` собственных `CREATEDATE/CORRDATE` нет;
- у `_PARTNER` нет общего времени изменения полей, включая начальный долг;
- на основных `SCL_*` таблицах нет change-log triggers; найденные triggers относятся к CRM;
- отдельные procedures меняют строки, распределения и признаки оплаты в шапке без обновления `CORRDATE`;
- `I_DELETE_PLAT` физически удаляет `SCL_PMOV`, `SCL_ADDP`, `SCL_PLAT`, поэтому удаление нельзя обнаружить запросом `CORRDATE > watermark`;
- обновление `CORRDATE` в `I_CORR_HEAD`/`I_CORR_DOP_FARM` зависит от `SCL_CONFIG.ModifDateReest` и может быть отключено;
- даже без записи в БД результат меняется при переходе `CONTRLDATE` документа с маркером `РЕЛ` через дату отчёта.

Поэтому до golden-master проверки всех UI-операций не объявляй `CORRDATE` полноценным CDC. Безопасный гибрид:

1. хранить в интеграционной БД итоговый снимок по партнёру, последний нормализованный набор ключей/владельцев/финансовых полей источника, фактический watermark чтения и ближайшую будущую `CONTRLDATE`;
2. дешёвым сканированием сравнивать ключи и fingerprints активных документов, платежей, распределений и архивов; при переносе документа между клиентами помечать грязными старого и нового владельца;
3. при любом различии полностью пересчитывать только грязного клиента через `I_DOLG_DOC` и атомарно заменять его снимок;
4. инвалидировать снимок в начале дня, когда наступила сохранённая `CONTRLDATE`, даже если таблицы не менялись;
5. периодически выполнять полный контрольный пересчёт как аудит до тех пор, пока экспериментом не доказано полное обнаружение создания, коррекции, распределения, удаления и архивирования.

Не переносить watermark в будущее на `23:59:59`. Хранить отдельно `asOfDate` отчёта и реальное `sourceReadUntil`, полученное по времени SQL Server после завершённого чтения: иначе изменения, внесённые позже в тот же день, будут пропущены.

Количество строк и максимальные `CREATEDATE/CORRDATE` используй только как дешёвый smoke-check, не как доказательство целостности. Надёжнее хранить manifest и детерминированные fingerprints финансово значимых строк: тип сущности, технический ключ, владелец-партнёр и нормализованные поля, влияющие на `I_DOLG_DOC`. Текущий compact projection считывай в стабильном порядке, хешируй в Java (`SHA-256`) и сравнивай с предыдущим manifest. Так обнаруживаются физическое удаление, delete+insert при неизменном количестве, перенос между клиентами и изменение строки без даты коррекции. Не полагайся на одну SQL-сумму `CHECKSUM`: возможны коллизии, а legacy `float`, `NULL`, пробелы и CP1251 требуют явной канонизации.

Для общего фонового обновления один set-based проход компактных source-полей и группировка/hashing в Java обычно существенно дешевле последовательного вызова `I_DOLG_DOC` для каждого партнёра. После сравнения вызывай procedure только для изменившихся партнёров. Для изменений, выполняемых собственным Java API, дополнительно сразу записывай dirty marker, но не считай его полным источником изменений: ручной клиент ФОЛИО обходит Java.

## Штатный перерасчёт

ФОЛИО уже содержит алгоритмы учётной цены. Не воспроизводи их в Java: автоматизируй предварительную диагностику, штатный запуск после подтверждения конкретного UI workflow и контроль результата.

| Процедура | Назначение | Критичное ограничение |
|---|---|---|
| `I_PERERS_UCH` | монолитный перерасчёт средней/LIFO/FIFO/фиксированной цены | собственная транзакция есть, но error checking/rollback неполны |
| `I_UCHET_TOVAR` | порционный перерасчёт с INOUT-прогрессом | общей транзакции нет; нужно читать `art/new_art/otr_date/n_cur/n_tot` |
| `I_UCHET_1_TOVAR` | один склад/товар, включая партии | меняет `SCL_ARTC`, `SCL_MOVE`, `SCL_PRIC`, `SCL_SROK`, использует persistent `TMP_MOVE` |
| `i_uchet_add` | apply/undo/rebuild/calculate внутри document workflow | нет собственной транзакции и надёжного error signalling |
| `I_SET_UCH_PRICE` | ручная установка учётной и производных продажных цен | может выдать rowset `-1`, продолжить и затем выдать `0` |
| `B_ALL_CALC_ARTIC` | перерасчёт `KON_KOLCH/REZ_KOLCH` | это остатки, не учётная цена; обработка rollback/commit дефектна |
| `B_ARTC_VRECALC` | валютные продажные цены | не себестоимость; `SWHERE` включается в dynamic SQL, внешний ввод запрещён |

Подтверждённые режимы: `0` средняя, `1` LIFO, `2` FIFO, `3` сохранить настройку, `4` фиксированная/прямая цена, `5` партии в `I_UCHET_1_TOVAR`.

`i_uchet_add` с `mode=2` и полный `I_UCHET_TOVAR` нельзя считать
взаимозаменяемыми. Проверенный точечный `mode=2` заново собирает итоговую
учётную цену из уже сохранённых в движениях `SUM_UCHET/SUM_UCVAL` и
пересчитывает последующие расходы. Штатный полный маршрут дополнительно
восстанавливает учётные суммы приходов из исходных сумм документа, налогов и
текущей настройки `uch_nal`. Golden-master точечного route подтверждает
исправление `SCL_ARTC` при корректных суммах движений, но не доказывает
эквивалентность кнопке полного перерасчёта ФОЛИО.

### Golden-master полного маршрута `I_UCHET_TOVAR`

На изолированной Paint_Rus подтверждён exact callable-контракт: процедура имеет
11 параметров в порядке `n_group`, `id_sclad`, `usredn`, `uchet_rsc`,
`period_rsc`, `uch_nal`, затем INOUT `art`, `n_cur`, `n_tot`, `new_art`,
`otr_date`; JDBC отдельно читает return status. Нельзя читать OUT до полного
дренирования всех result sets/update counts jTDS.

- Один вызов является временной порцией примерно на 10 секунд и может изменить
  несколько SKU. Количество SKU и граница порции не являются стабильным
  контрактом; продолжение определяется только возвращёнными `art/new_art`.
- `n_cur` отражает прогресс текущей порции и сбрасывается между вызовами, поэтому
  общий прогресс накапливает вызывающая сторона. `n_tot` устанавливается первым
  вызовом и далее обязан оставаться тем же; завершение подтверждается только
  суммарным `n_cur = n_tot` и пустым продолжением.
- Полный маршрут действительно восстанавливает входные `SCL_MOVE.SUM_UCHET` и
  `SUM_UCVAL` по исходным суммам приходного документа, налогам и настройкам,
  после чего пересчитывает карточку товара. Это функциональное отличие от
  `i_uchet_add(mode=2)`, который опирается на уже сохранённые в движениях
  учётные суммы.
- При отрицательном хронологическом остатке процедура возвращает проблемные
  `art`, `otr_date` и продолжение только **после** частичных DML по проблемному
  товару. Внешний rollback golden-master полностью восстановил снимок. Поэтому
  неожиданную отрицательную порцию нельзя commit-ить и нельзя продолжать с её
  `new_art`.
- Отдельный rollback golden-master подтвердил безопасный способ пропуска
  **заранее диагностированного** SKU для режима `N_2=1000`: внутри той же
  транзакции создать временную строку `TIP_TOVR` с неиспользуемым `SIGNIFIC` и
  `CHECK_SAVE=0, SHOW_OSTATOK=0`, временно присвоить этот тип проблемной
  `SCL_ARTC`, вызвать `I_UCHET_TOVAR`, затем восстановить исходный `TIP_TOVR`
  товара и удалить служебную строку до выхода из транзакции. При вызове с
  `art=problemSku` процедура не выполнила DML товара, вернула `otr_date=NULL` и
  перешла к следующему SKU. Несуществующая в справочнике метка не работает:
  строка `TIP_TOVR` обязательна.

Безопасный native-full протокол — строго двухпроходный:

1. До процедуры детерминированно проиграть хронологию движений в том же порядке
   и собрать первый блокирующий эпизод каждого SKU: отрицательный остаток,
   нулевой знаменатель средней цены либо неоднозначный legacy sort key.
2. Для каждого вызова во внешней транзакции временно скрыть весь этот набор
   через служебный `TIP_TOVR`; каждый preview-вызов всегда завершать rollback.
3. Если exact preflight завершился без новых `otr_date`/SQL errors, повторить
   маршрут для apply с тем же набором пропусков. Перед каждым commit проверять
   OUT-контракт и защищённые исходные поля фактически обработанного диапазона.
4. Известные пропуски возвращать как warnings с документом, `RECNO`, количеством
   до/после и логировать отдельно; они не блокируют перерасчёт остальных SKU.
5. Если неожиданный отрицательный остаток, разрыв транзакции или drift обнаружен уже во
   втором проходе, rollback текущей порции и немедленная остановка. Ранее
   подтверждённые commits означают частичный результат; не возобновлять его
   автоматически по одному лишь курсору или журналу приложения.

Для первого релиза подтверждена только средняя учётная цена:
`SCLAD_R.N_2 = 1000`, `SCLAD_R.N_4 IS NULL`, один склад за запуск. FIFO, LIFO,
фиксированная цена и партии не обобщать из этого эксперимента. Настройки склада
нужно блокировать и повторно сверять в каждой порции.

`TMP_MOVE` в legacy-базе может содержать большое количество старых строк ещё до
запуска, поэтому требование «таблица должна быть пустой» неверно. Фиксируй
baseline и проверяй только изменения в области запуска. В проверенном среднем
режиме (`N_2=1000`) native route не изменил baseline `TMP_MOVE`; это наблюдение
не переносить на другие методы учёта.

Диагностика отрицательного остатка должна показывать не только SKU и дату из
`otr_date`, а полную хронологию до первой проблемной операции: начальное
количество, количество перед движением, идентификатор/тип/дату документа,
`RECNO`, количество движения, остаток после него и величину дефицита. При одной
дате сохраняй порядок, соответствующий штатной процедуре, и помечай упрощённую
диагностику как неподтверждённую, если встречены возвратные/необычные движения.

Некоторые ошибки возвращаются через OUT/rowset, а не return code. Procedures используют session state (`DATEFORMAT`, `ROWCOUNT`, курсоры, `ANSI_NULLS`) и точный курс валюты на дату. Helper курса рекурсивен и не защищён от циклической зависимости валют.

## Контроль ошибок

Перед штатным перерасчётом на копии:

1. подтвердить точную базу, восстановимый backup, отсутствие других сессий и `@@TRANCOUNT=0`;
2. сохранить настройки `SCLAD_R.N_2/N_4`, `ANSI_NULLS` и выбранную область склад/группа/товар;
3. проверить нулевые количества в учитываемых движениях и целочисленность legacy float-ключей;
4. найти первую дату отрицательного хронологического остатка, считая приход раньше расхода при одной дате; при наличии возвратных движений остановить упрощённую проверку и разобрать точную ветку procedure;
5. в партионном режиме сверить товарный остаток с суммой партий;
6. проверить наличие точных валютных курсов;
7. снять baseline `TMP_MOVE` и проверить его изменение в области запуска; не
   требовать пустую таблицу, потому что legacy-строки могут существовать до
   перерасчёта;
8. сохранить `SCL_ARTC`, затрагиваемые `SCL_MOVE`, `SCL_PRIC`, `SCL_SROK` до запуска.

После перерасчёта повторить те же запросы и сверить:

- физический/свободный остаток;
- `SUM_UCHET`, `SUM_UCVAL` строк;
- `UCHET_SUM`, `UCHET_SMVL`, `UCHET_CENA`, `UCHET_VALT` товара;
- производные `SCL_PRIC` и партии `SCL_SROK`;
- отсутствие остаточных строк `TMP_MOVE`, открытой транзакции и долгих блокировок;
- все OUT, rowsets, UI-сообщения и return status.

Готовые read-only проверки находятся в `docs/folio-experiments/04_accounting_price_control.sql`.

## Граница автоматизации

- Read-only задолженность можно автоматизировать после golden-сверки с отчётом ФОЛИО.
- Контроль ошибок цен можно автоматизировать независимо от запуска перерасчёта.
- Подтверждённый native route `I_UCHET_TOVAR` автоматизировать только через
  полный rollback-preflight и второй exact apply-проход с fail-stop проверками;
  не заменять его простым циклом `EXEC` и не продолжать после отрицательной
  порции.
- На Paint_Ua по умолчанию оставлять preview + явное подтверждение оператора. Не выполнять прямой `UPDATE` цены как «исправление».

## Карточка клиента Paint_Rus

Живая схема Paint_Rus от 2026-08-12 подтверждает цепочки чтения:

- клиент `_PARTNER.N_USER` → `SCL_NAKL.BRIEFORG` для счетов/накладных;
- клиент `_PARTNER.N_USER` → `SCL_PLAT.ORG_PREDM` для платежей;
- `SCL_PMOV.UNICUM_PLT` → `SCL_PLAT.UNICUM_PLT` и `SCL_PMOV.UNICUM_NUM` → `SCL_NAKL.UNICUM_NUM` для распределений оплаты.

В проверенном агрегате `SCL_PMOV` не обнаружены orphan-ссылки на платёж или документ, но существуют старые документы/платежи без соответствующей строки `_PARTNER`; поэтому lookup клиента и выборка активности должны использовать точный `N_USER`, а не inner join, который молча скроет legacy-строки.

Read-only комплект: `docs/folio-experiments/08_client_search.sql`, `09_client_activity.sql`, `10_document_full_detail.sql`, `11_payment_full_detail.sql`. В `09` кириллическая `Р` означает расходную накладную, кириллическая `С` — счёт. `10` раскрывает документ, строки, дополнительные реквизиты и связанные оплаты; `11` раскрывает платёж, его дополнительные реквизиты, распределения и связанные документы. `TYPE_POR` оставлять raw до golden-master проверки его направления по штатному журналу платежей. Не выдавать `_PARTNER.DOLG` за рассчитанный периодный баланс.
