## Источник и безопасность

Выводы ниже получены read-only разбором `docs/contentr_full.rpt` и сверены с `04_depandenses.rpt`/`05_module_paramert.rpt`. Полная выгрузка содержит 4763 куска для всех 262 объектов: 222 procedures, 33 views и 7 triggers; дубликатов и пропусков частей нет.

При восстановлении дополняй каждый не последний `definition_fragment` до 200 символов: старый текстовый отчёт обрезал пробелы на границах. Точные конечные пробелы последнего блока неизвестны, но SQL-семантика и параметры сохраняются.

Raw-файл не прошёл secret scan: обе находки относятся к `dbo.B_VIEW_SCLAD_GRP1`. Не открывай и не цитируй соответствующие literals, не переноси определение в Git/Skill. Ниже сохранены только обезличенные бизнес-выводы; procedures не выполнялись.

## Товарное view

`dbo.card_tov_export` — read-only view из 21 поля:

- берёт все строки `SCL_ARTC` склада `ID_SCLAD = 7`;
- опционально присоединяет `ALL_ARTC` по `COD_ARTIC`;
- возвращает SKU, имя, группы, main image, размеры/вес, описание и raw `DEPARTAM AS status`;
- не возвращает цену, остаток или gallery;
- не фильтрует active/status и не гарантирует порядок.

Java может читать это view, но не должен трактовать `status` как готовый boolean, считать отсутствие `ALL_ARTC` причиной исключить складскую строку или обещать порядок без собственного `ORDER BY`.

## Нумерация документов

### `I_NSF_GET_NEW`

Пять параметров; `method` и `nsf` — INOUT. Поддерживает области склад, global, организация+склад и global+организация.

- `mode=0` рассчитывает `current+1`;
- `mode=1` записывает номер;
- `mode=2` записывает только возрастающий номер;
- `mode=4` широко меняет конфигурацию `SCLAD_R.N_3`.

Читает/меняет `SCLAD_R` и `NSF_ORG`, но не открывает транзакцию и не берёт locks. Расчёт/upsert конкурентно небезопасен. Некорректная область возвращает `-1`, обычное завершение — `0`.

### `I_GET_LAST_NUMBER`

Девять параметров, номер — INOUT; `sposob` в теле не используется. Несмотря на `GET`, может менять `SCLAD_R.N_5`.

При установленном bit `2048` процедура в транзакции читает `NSF_ORG.N_3` с `UPDLOCK`, пропускает занятые номера через `I_TEST_NUM_NAKL` и сохраняет следующий. Ключ строится из NBSP, кириллического типа, `U/N` либо пробела и, при нужном режиме, организации. Если строки счётчика нет, используется `MAX(N_PLAT_POR)+1`; архив проверяется только для типа `С`. Существующая строка защищена, fallback `MAX+1` остаётся race.

### `I_SET_LAST_NUMBER` и `I_TEST_NUM_NAKL`

`I_SET_LAST_NUMBER` имеет шесть входов:

- `mode=0` возвращает rowset с `N_3`;
- `mode=1` создаёт/обновляет счётчик и включает bit `2048`;
- `mode=2` удаляет счётчик и при необходимости выключает bit.

Есть `BEGIN/COMMIT`, но нет lock hints, error checks и явного rollback; check-then-insert гоняется.

`I_TEST_NUM_NAKL` возвращает `1` при коллизии и `0` иначе. Проверяет активные документы и только для `С` архив, учитывает год, дополнительный номер, область склада, учётность и организацию. Даже при `skip_test=1` может нормализовать `SCLAD_R.N_5`; параметры `vid_doc` и `id_perem` в теле не используются.

Не заменяй текущий direct allocator вызовом этих procedures автоматически. Сначала сравни точную область номера, archive/collision policy и конкурентный тест; direct lock по существующей строке `NSF_ORG` может быть предсказуемее legacy fallback.

## Несохранённые остатки NS и NR

`A_TR_CHANGE_NS`/`A_TR_CHANGE_NR` делают update/insert/delete в `SCL_NS`/`SCL_NR` по пользователю, складу, товару, партии и сроку. `Amount` имеет `numeric(18,0)`; ноль удаляет строку. Транзакции, locks и error result отсутствуют, поэтому update-then-insert имеет race и не поддерживает дробное количество без потери.

`A_TR_GET_NS`/`A_TR_GET_NR` имеют по семь входов и возвращают четыре поля: признак изменения, суммы несохранённых расходных/счетовых строк и `-1`. При достатке они вызывают CHANGE, поэтому GET **мутирует данные**. Проверка и запись не атомарны.

В `A_TR_GET_NR` обе ветви присваивают `HasParty=0`; party-specific ветка расходного резерва недостижима. Не вызывай это семейство из новой Java-логики без изолированного воспроизведения штатного клиента и явного решения о целочисленном количестве.

## Партии и учётная стоимость

### Подбор партий

Подтверждены шесть procedures:

- `A_POTBOR_PARTIA`;
- `A_POTBOR_PARTIA_MAX_OSTATOK` / `MIN_OSTATOK`;
- `A_POTBOR_PARTIA_MAX_SROK` / `MIN_SROK`;
- `A_POTBOR_PARTIA_SV_OSTATOK`.

Главная процедура принимает склад, артикул, количество, стратегию, `MaloTovar OUT` и дату. Стратегии включают max/min срока, max/min остатка, целые фасовки, максимальную дату не позже заданной и минимальную учётную цену; `-1` выбирает по складам, `-2` — специальный свободный остаток. Rowset возвращает партию, срок, выбранное количество, остаток и описательные поля.

Permanent tables не меняются, но используются temp tables, cursors, `SET ROWCOUNT` и `SET DATEFORMAT`. Helpers читают `SCL_SROK.OSTATOK` и разницу `SCL_ARTC.KON_KOLCH - SUM(положительных партий)` без locks. Дополнительные риски:

- `A_POTBOR_PARTIA_SV_OSTATOK` передаёт `float`-разницу через integer return status;
- стратегия `7` возвращает запрошенное количество без проверки вместимости в остаток;
- схемы rowset немного расходятся между стратегиями.

### `I_SAVE_PARTY`, `ins_partys`, `i_uchet_add`

`I_SAVE_PARTY` обновляет метаданные `SCL_SROK`; новая партия получает нулевые остатки, существующая сохраняет остаток. Нет транзакции/locks; поскольку у `SCL_SROK` нет PK/UQ, параллельный upsert может создать дубли.

`ins_partys` имеет 39 параметров и `num_predmt INOUT`. Временно увеличивает, затем уменьшает `SCL_ARTC.KON_KOLCH`, подбирает партии, вызывает `i_uchet_add`, вставляет `SCL_MOVE` и меняет `SCL_SROK.OSTATOK`. Сам транзакцию не открывает и не проверяет `MaloTovar`. В ветке `autopodbor=7` используется неинициализированное количество для NOT NULL temp-колонки.

`i_uchet_add` имеет 17 параметров; две суммы — INOUT. В зависимости от `SCLAD_R.N_2/N_4` выбирает средний, LIFO/FIFO-подобный, фиксированный либо прямой партионный учёт. Режимы: apply, undo/delete, rebuild и расчёт; даже расчёт использует persistent scratch `TMP_MOVE`.

Процедура читает/меняет `SCL_ARTC`, `SCL_MOVE`, `SCL_SROK`, `SCL_PRIC`, `TMP_MOVE`, может пересчитать последующие строки, учётные суммы и цены, но не имеет собственной транзакции/error signalling. Для скрытого типа товара ранний return оставляет outputs неприсвоенными.

## Сохранение, преобразование и удаление документов

### `INSERT_NAKL2`

Имеет 100 параметров; шесть INOUT: номер, технический ключ, товар, два количества и номер строки. Источник строк — `TMP_MOVE`. Процедура создаёт header/lines, проверяет суммы, номер, физический/свободный остаток, minimum stock и партии; вызывает numbering, delete, reconciliation, party и accounting procedures. Поддерживает corrections, archive, transfer-пары, цены, партии и payments.

В основной транзакции:

- `UNICUM_NUM = MAX+1` защищён `UPDLOCK,HOLDLOCK`;
- `SCL_ARTC` читается с `UPDLOCK`;
- приход `П` увеличивает `KON_KOLCH` и `REZ_KOLCH`;
- расход `Р` уменьшает оба;
- учитываемый счёт `С` не меняет `KON_KOLCH`, но уменьшает `REZ_KOLCH`;
- неучитываемый `С` не меняет остатки.

Критичное ограничение: `COMMIT` выполняется **до** reconciliation платежей, вставки `SCL_ADDN`, пополнения `_KONTRCT`/`_RECLAMA`/`VID_OPER` и зачётных procedures. Ошибка после commit может вернуть ненулевой код при уже сохранённом документе; `SCL_ADDN` может отсутствовать. Также присутствуют positional `INSERT INTO SCL_NAKL VALUES`, ручные offsets ключей для transfer и одна error-ветка с неинициализированным return code.

Группы return codes: `0` успех; `1` duplicate; `2` номер; `3` технический ключ; `4` нет складской строки; `5/6` KON/REZ; `7/20/21` correction; `8` minimum stock; `23–27` партия/остаток/перемещение; `30` header/sum; `31/32/66` transfer; `67` duplicate temp line; `301` transfer header; зачёт возвращает `abs(inner)+40`.

### `I_RZV_NEUCH`

Преобразует неучитываемый счёт в учитываемый, при необходимости архивирует, объединяет с существующим учитываемым или делит на учитываемую/неучитываемую части. Меняет активные и архивные документы, строки, дополнения, остатки и payment movement.

Имеет одну транзакцию; `MAX+1` защищены `UPDLOCK,HOLDLOCK`, но почти все чтения — `NOLOCK`, error checks отсутствуют. Проверки совпадений местами не ограничены текущим/целевым документом, выбор счёта не имеет `TOP/ORDER BY`, а резерв уменьшается без условия достатка. При concurrency возможны неверное объединение и отрицательный резерв.

### `I_DELETE_NAKL`

Семь параметров, `unicum_num INOUT`. Режимы: delete/undo, archive+delete, copy/archive-only; процедура меняет активные/архивные документы, остатки/партии и payment allocation, вызывает archive/payment/accounting routines.

Основной контур транзакционный; ключи защищены `UPDLOCK,HOLDLOCK`, есть rollback-ветки. Return codes: `0` успех, `1` успех с удалением платежа, `4` нет строк; ошибки `3,5,7,9,10,11,12`. Риски: курсор строк создаётся до транзакции, много `NOLOCK`, вложенный `ROLLBACK` откатывает внешнюю транзакцию. Восстановление архивного счёта коммитит раньше удаления архива, поэтому неатомарно.

### `i_sch2nakl`

Сопоставляет `TMP_MOVE` со строками счёта, уменьшает/удаляет `SCL_MOVE`, восстанавливает агрегированные суммы и пересчитывает `SCL_NAKL`. Удаление пустой шапки закомментировано. Нет собственной транзакции, locks или error signalling.

## Решение для Java-интеграции

Эти procedures — старый клиентский workflow, а не узкие CRUD API. Они используют session state, temp/persistent scratch tables, cursors, `NOLOCK`, `float`, CP1251 literals и вложенные/частичные транзакции.

- Не вызывай `INSERT_NAKL2`, `I_DELETE_NAKL`, `I_RZV_NEUCH`, `ins_partys` или `i_uchet_add` как побочное «улучшение» direct Java flow.
- Используй их как behavioral oracle: извлекай проверяемые инварианты и покрывай direct Java путь тестами/живым экспериментом на восстановимой копии.
- Если принято решение вызывать procedure, сначала зафиксируй все INOUT, rowsets, return codes, session temp state и поведение внутри внешней Spring transaction. Отдельно проверь частичный успех после внутреннего commit и влияние вложенного rollback.
- Для обычного непартионного счёта текущая минимальная атомарная Java-триада `SCL_NAKL + SCL_MOVE + SCL_ADDN` безопаснее предсказуема, если все её инварианты, остатки и idempotency держатся одной Spring transaction.
- Для партий, сложного учёта, архивов, платежей, corrections и transfers direct CRUD не доказан эквивалентным штатным procedures. Такие операции блокируй до отдельного сценария на копии базы.
